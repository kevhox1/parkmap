## §0 — Open Questions for Kevin

Seven product decisions to confirm before code starts. Recommendations are tech-lead opinions, not decisions.

**OQ-1: Drive Mode bottom card layout — full-width pinned to bottom safe area, or smaller card on right side of screen?**
The W7.5 "Park Until" pill uses `.safeAreaInset(edge: .bottom)` as a full-width pinned element. A dashboard-mounted iPhone in portrait is read from distance. Left/right chip labels are the two most important pieces of data.
Options:
- A. Full-width card pinned to bottom safe area (same pattern as Park Until pill). Maximum chip size. Consistent idiom with W7.5. Obscures the bottom 15% of the map.
- B. Compact card on the right side of the screen, overlaying the map. Smaller tap targets; harder to read from dashboard distance. Less map occlusion.
Recommendation: **Option A** — full-width bottom card. Dashboard readability beats map coverage. The map is less important while moving than the parking status text. W8.5c-follow will tune font sizes post-drive-test.

**OQ-2: Recenter button placement during Drive Mode — replace find-me icon in existing toolbar, or new button in the bottom card?**
Options:
- A. Replace the find-me toolbar button with a "Recenter" button while Drive Mode is active. Tap it to re-enable follow mode. Button disappears when follow mode is already active.
- B. A separate floating "Recenter" button above the bottom card (e.g., bottom-right, thumb-reachable), only visible when follow mode is paused.
- C. A button row inside the bottom card itself (mute toggle + recenter on same row).
Recommendation: **Option B** — floating button above the bottom card. The existing toolbar should not change meaning mid-mode (that's confusing). A floating pill that appears only when the user has dragged away is the iOS Maps idiom. Dismisses when follow mode re-engages.

**OQ-3: Mute toggle persistence — does mute state survive across Drive Mode sessions?**
The PWA persists `drivingVoiceMuted` in `localStorage` (`index.html:5812`).
Options:
- A. Persist across sessions. Start muted next time if last session was muted.
- B. Reset to unmuted on every Drive Mode start.
Recommendation: **Option A** — persist, but show a brief toast at Drive Mode start ("Voice muted — tap to unmute") if muted state is loaded, so the user knows why voice is silent. This matches PWA behavior and respects explicit user intent.

**OQ-4: Should W8.5c commentary voice respect the active W7.5 Park Until filter?**
If the user has "Park Until 9 PM" active, should the voice say "free until your departure time" (filter-aware), or always say the real-time status ("free until Thursday 9:30 AM") regardless?
The master spec §7.5 overlap section resolves this for the visual layer: "Drive Mode always shows real-time status regardless of Park Until filter state." This OQ applies specifically to the voice cue text.
Options:
- A. Always speak real-time status (matches visual card). "Free until Thursday nine thirty AM."
- B. If Park Until is active and the block is free for the full window, say "free for your stay." Requires passing `parkUntilTarget` into `DrivingContextService`.
Recommendation: **Option A** — always speak real-time status. Simpler implementation; consistent with visual card behavior already locked in master spec §7.5. Park Until filter stays a visual/scoring concern, not a voice-cue concern.

**OQ-5: What happens to the route polyline and destination pin when the user ends Drive Mode manually before arriving?**
W8.5d will handle the arrival prompt. W8.5c needs an interim behavior.
Options:
- A. Polyline and pin stay on the map until manually cleared (End Drive button). They do not auto-fade.
- B. Polyline and pin fade out automatically on End Drive tap.
Recommendation: **Option A** — stay until End Drive is tapped. The existing `endDriveMode()` in `ContentView.swift:916` already sets `activeRoute = nil` and `driveDestinationCoordinate = nil`, which causes `MapViewRepresentable` to remove both overlays. No change needed.

**OQ-6: Heading-up rotation when stopped (zero speed) — freeze on last heading, or snap to north?**
The PWA freezes at the last heading (`stabilizedHeading` returns `drivingLastGoodHeading` when `speedMs < DRIVING_HEADING_MIN_SPEED_MPS`, `index.html:6557`).
Options:
- A. Freeze at last good heading (PWA behavior). Map stays in the direction the driver was facing at the last light or stop sign.
- B. Snap to north-up when stopped for > 10 seconds.
Recommendation: **Option A** — freeze at last heading. Snapping to north while a driver is stationary at an intersection is disorienting. The driver expects the map to stay oriented the way they are facing.

**OQ-7: Default voice rate — `AVSpeechUtteranceDefaultSpeechRate` (0.5) or slightly faster?**
The master spec §5 recommends `AVSpeechUtteranceDefaultSpeechRate`. The PWA uses `rate: 1.0` (`index.html:5974`). A moving vehicle creates road noise; a slightly faster rate may reduce how long the voice competes with traffic audio.
Options:
- A. `AVSpeechUtteranceDefaultSpeechRate` (0.5) — clear and unhurried.
- B. `0.55` or `0.6` — slightly faster, reduces announcement duration by ~10–20%.
Recommendation: **Option A** — default rate for now. This is explicitly a calibration knob deferred to W8.5c-follow after the drive-test. Ship 0.5, tune after real-car feedback. Do not pre-optimize before the test.

## §1 — Summary

W8.5c delivers the full active-drive experience: continuous GPS + heading updates, heading-up map rotation with EMA smoothing, follow-mode with a recenter button, wake lock, `AVAudioSession` configuration, `AVSpeechSynthesizer` voice, voice mute toggle, the parking commentary engine (`DrivingContextService`), block-change detection, and the Drive Mode bottom card. It also resolves two carry-overs from W8.5b QA: the N-1 lift of `RecentDestinationsStore` to its own service file, and the M-2 `RouteService` protocol seam that enables view-level error injection and the deferred error-path test. A third carry-over — auth prompt before route fetch — is wired in `DriveModeDestinationView.swift` so Drive Mode cannot start until location permission is confirmed.

After W8.5c merges, a user can: tap "Drive" → enter a destination → tap "Start Drive" → see the map rotate heading-up → hear parking commentary on each block change → mute/unmute with a toolbar button → end Drive Mode and return to the normal map. The final-approach escalation strip and arrival prompt are W8.5d.

**Spec re-decomposition:** This W8.5c absorbs master spec §7 rows W8.5a (CoreLocation drive session) and W8.5c (commentary engine + voice), collapsed because continuous location is a prerequisite for the commentary engine and splitting them would leave an unshippable half-feature in each sub-PR.

## §2 — Scope

### 2.1 In scope

1. **Continuous location + heading** — `LocationService` gains `startDriveMode()` / `endDriveMode()` API. Flips to `startUpdatingLocation()` + `startUpdatingHeading()` with `desiredAccuracy = kCLLocationAccuracyBestForNavigation`, `activityType = .automotiveNavigation`, `distanceFilter = kCLDistanceFilterNone`, `pausesLocationUpdatesAutomatically = false`. Single-shot `requestAndFetchLocation()` API is preserved unchanged.
2. **Heading-up rotation** — `MapViewRepresentable` gains a `driveHeading: Double?` input. When non-nil and Drive Mode is active, sets `MKMapView.camera.heading` (or uses `MKMapCamera` with the stabilized heading). Port of `setDrivingMapRotation` and its 5-degree dead-band guard (`index.html:6584–6601`). Cleared on Drive Mode exit.
3. **EMA heading stabilizer** — Swift port of `stabilizedHeading` (`index.html:6546–6570`) with speed gate (1.8 m/s, same as PWA constant `DRIVING_HEADING_MIN_SPEED_MPS`), EMA alpha 0.35 (same as PWA `DRIVING_HEADING_EMA_ALPHA`), course-from-movement fallback via `CLLocationCoordinate2D` bearing when `CLHeading` is unreliable. Default constants are PWA parity; W8.5c-follow will tune after drive-test.
4. **Follow-mode** — on each `CLLocationManager` position update while Drive Mode is active, recenter `MKMapView` to user coordinate at a locked zoom (zoom level TBD by @designer; PWA uses zoom 18). A "Recenter" pill button appears when follow mode is paused (user dragged the map). Tapping it re-enables follow.
5. **Wake lock** — `UIApplication.shared.isIdleTimerDisabled = true` on `startDriveMode()`, `false` on `endDriveMode()`. No entitlement required.
6. **`AudioSessionManager.swift`** — new service. Configures `AVAudioSession.sharedInstance()` with `.playback` category and `[.duckOthers, .interruptSpokenAudioAndMixWithOthers]` options when Drive Mode activates. Calls `setActive(false, options: .notifyOthersOnDeactivation)` after each utterance completes (via `AVSpeechSynthesizerDelegate`). Deactivates session on Drive Mode exit.
7. **`DrivingVoice.swift`** — new service. Owns `AVSpeechSynthesizer` and `AVSpeechSynthesisVoice(language: "en-US")`. Exposes `speak(_ text: String)` and `stopImmediate()`. Voice rate: `AVSpeechUtteranceDefaultSpeechRate` (calibration deferred to W8.5c-follow). Mute state stored in `UserDefaults` key `wepark_dm_voice_muted`. `stopImmediate()` called on mute toggle (mirrors `index.html:5815`).
8. **Voice mute toolbar button** — visible only during active Drive Mode (not on the home toolbar). Placed in the bottom card's control row (or adjacent to it — per OQ-1/OQ-2 resolution). SF Symbols: `speaker.slash.fill` (muted) / `speaker.wave.2.fill` (unmuted). Mute state persists in `UserDefaults`.
9. **`DrivingContextService.swift`** — new service. Swift port of `getCurrentDrivingContext` (`index.html:5557–5587`): haversine-closest segment → block (`street|from|to`) → classify N/S/E/W sides relative to driver heading via `sideRelativeToHeading` → `ParkingRulesEngine.actionableSafetyLabel` for each side → return `DrivingContext` value type. Block-change detection: compare `blockKey = "\(street)|\(from)|\(to)"` to `lastBlockKey`; only call `DrivingVoice.speak` on change (mirrors `index.html:5905–5908`).
10. **`DriveModeBottomCard.swift`** — new view. Port of `renderDrivingContext` (`index.html:5863–5910`) minus the meta row (speed/ETA — out of scope per master spec §9). Shows: street name, Left chip (color-coded severity, label text), Right chip, mute toggle button. Uses **placeholder font sizes** (system defaults). W8.5c-follow tunes sizes after drive-test. No final-approach strip (W8.5d).
11. **`ContentView.swift` wiring** — adds `DriveModeBottomCard` as `.safeAreaInset(edge: .bottom)` when `driveModeActive == true`. Passes `locationService.driveHeading` binding to `MapViewRepresentable`. Calls `locationService.startDriveMode()` when `driveModeActive` flips to true, `endDriveMode()` when it flips to false.
12. **N-1 carry-over: `RecentDestinationsStore` lift** — move `RecentDestinationsStore` from inline-in-`DriveModeDestinationView.swift` (~90 LOC) to `Services/RecentDestinationsStore.swift`. Update imports in `DriveModeDestinationView.swift`. No behavior change.
13. **M-2 carry-over: `RouteServiceProtocol` seam** — extract a `RouteServiceProtocol` (or `RouteServicing`) with the `fetchRoute(from:to:alternatives:)` and `pickBestParkingAwareRoute(_:segments:engine:)` signatures. `RouteService` conforms. `DriveModeDestinationView` is typed against the protocol. Add the deferred `testDriveModeDestinationView_routeError_doesNotCrash` test (injecting a mock that throws `.network`).
14. **Auth prompt carry-over** — in `DriveModeDestinationView.swift`, gate the "Start Drive" button: if `locationService.isAuthorized == false && authorizationStatus == .notDetermined`, call `locationService.requestAndFetchLocation()` first and disable the button with a "Requesting location..." spinner until status resolves. Do not attempt route fetch until status is `.authorizedWhenInUse` or `.authorizedAlways`. If status is `.denied` or `.restricted`, show an informational alert (not a crash).

## §4 — Implementation Plan

The steps below are ordered to minimize the risk of shipping broken intermediate states. Steps 1-3 are mechanical and non-breaking. Steps 4-7 build the active session. Steps 8-10 are the commentary stack on top. Each step should be its own commit; the PR squashes them all.

**Step 1 — N-1 lift: move `RecentDestinationsStore`.**
Extract the `RecentDestinationsStore` class and `RecentDestination` struct from `DriveModeDestinationView.swift` into `Services/RecentDestinationsStore.swift`. Add `import` in `DriveModeDestinationView.swift`. This is a pure refactor — no behavior change, no test changes. The `AppConstants.recentDestinationsKey` constant stays in `Constants.swift` where it already lives.

**Step 2 — M-2: extract `RouteServicing` protocol.**
Define `protocol RouteServicing` with async-throws signatures matching `fetchRoute(from:to:alternatives:)` and `static func pickBestParkingAwareRoute(_:segments:engine:)`. Note: the static method is awkward on a protocol — recommend making it an instance method on the protocol (the implementation can still delegate to the static version internally). `RouteService` adds conformance. `DriveModeDestinationView` changes its `routeService` property type from `RouteService` to `any RouteServicing` (or a generic `<Service: RouteServicing>` — engineer's call on which is cleaner). Add `testDriveModeDestinationView_routeError_doesNotCrash` using a `MockRouteService` that throws `.network(message: "test")`.

**Step 3 — Auth gate in `DriveModeDestinationView.swift`.**
In `startDriveSection` (line ~371), before calling `Task { await fetchRouteAndReturn() }`, check `locationService.isAuthorized`. If `authorizationStatus == .notDetermined`, call `locationService.requestAndFetchLocation()` and disable the Start Drive button with a "Requesting location..." progress view until `locationService.isAuthorized` becomes true (wire via `.onChange(of: locationService.isAuthorized)`). If `.denied` or `.restricted`, show an alert ("Location required for Drive Mode. Enable it in Settings.") — no crash.

**Step 4 — `LocationService` drive session API.**
Add to `LocationService`:
- `private(set) var driveHeading: CLLocationDirection?` — updated from `locationManager(_:didUpdateHeading:)`. Nil when Drive Mode is not active.
- `private(set) var driveSpeed: CLLocationSpeed?` — updated from location updates during drive session.
- `private var driveModeActive: Bool = false` — internal gate.
- `func startDriveMode()` — sets accuracy to `kCLLocationAccuracyBestForNavigation`, `activityType = .automotiveNavigation`, `pausesLocationUpdatesAutomatically = false`, `distanceFilter = kCLDistanceFilterNone`, calls `startUpdatingLocation()` + `startUpdatingHeading()`. Sets `UIApplication.shared.isIdleTimerDisabled = true` on `@MainActor`.
- `func endDriveMode()` — calls `stopUpdatingHeading()`, reverts `desiredAccuracy` to `kCLLocationAccuracyHundredMeters` and `activityType = .other`, calls `stopUpdatingLocation()` then `requestLocation()` for a one-shot fix, sets `driveHeading = nil`, sets `UIApplication.shared.isIdleTimerDisabled = false` on `@MainActor`. Sets `driveModeActive = false`.
- `locationManager(_:didUpdateHeading:)` delegate method: when `driveModeActive`, apply EMA stabilization (see step 5) and publish result to `driveHeading`.

**Step 5 — EMA heading stabilizer.**
Implement `stabilizedHeading(raw:speedMps:lat:lng:)` as a private method on `LocationService` (or a free function in the same file). Algorithm is a direct Swift port of `index.html:6546–6570`:
- Speed gate: if `speed < 1.8 m/s`, return `lastGoodHeading` (may be nil on first tick).
- Course-from-movement fallback: if `CLHeading` magneticHeading is unavailable, compute bearing from previous coordinate to current coordinate using the haversine-like bearing formula (same as `bearingFromTo` at `index.html:6572–6578`). Previous coordinate stored in `prevDriveCoordinate: CLLocationCoordinate2D?`.
- EMA with circular wraparound: diff = newHeading - EMA; normalize to -180..180; EMA += alpha * diff. Alpha = 0.35 (calibration deferred to W8.5c-follow).
- Dead-band: in `MapViewRepresentable`, only apply camera rotation when heading changes > 5 degrees (port of `setDrivingMapRotation`'s diff guard, `index.html:6587–6589`).

**Step 6 — `MapViewRepresentable` heading-up rotation.**
Add `var driveHeading: Double?` to the struct's input properties. In `updateUIView`, when `driveHeading` is non-nil and differs from the currently-applied heading by > 5 degrees, create a new `MKMapCamera` copying current altitude and center, setting `heading` to the new value, and call `mapView.setCamera(_:animated: false)` (no animation — smooth update comes from EMA, not UIKit transitions). On drive exit (`driveHeading` becomes nil), create a camera with `heading = 0` to restore north-up. The Coordinator already stores a reference to the `mapView`; heading updates should go through `updateUIView`, not through a separate coordinator path, to keep the SwiftUI data flow clean.

**Step 7 — Follow-mode and recenter.**
`LocationService` exposes `var driveFollowEnabled: Bool = true`. `ContentView` subscribes to `locationService.locationUpdateCount`; when follow mode is enabled and Drive Mode is active, sets `MapViewRepresentable`'s `cameraCenter` (or equivalent) to current user coordinate at the locked drive zoom. When follow mode is disabled (user panned), show the Recenter pill button above the bottom card. Tapping Recenter sets `driveFollowEnabled = true` and snaps the camera back to user location. The recenter button hides when follow mode is already active.
Note: Pan detection — in `MapViewRepresentable`'s Coordinator, `mapView(_:regionWillChangeAnimated:)` fired by a user gesture (not programmatic) should set `driveFollowEnabled = false`. Check `animated == false` or use the `isUserAction` check pattern from existing code.

**Step 8 — `AudioSessionManager` + `DrivingVoice`.**
`AudioSessionManager.swift`: singleton with `private init()`. `func activateDriveSession() throws` configures `AVAudioSession.sharedInstance()` with `.playback` category and `[.duckOthers, .interruptSpokenAudioAndMixWithOthers]` options, then `setActive(true)`. `func deactivateAfterUtterance() throws` calls `setActive(false, options: .notifyOthersOnDeactivation)`. `func deactivateDriveSession() throws` calls `setActive(false, options: .notifyOthersOnDeactivation)` (same call, named for clarity at Drive Mode exit).

`DrivingVoice.swift`: `@Observable` class (or final class with `private init()`). Owns `AVSpeechSynthesizer`. Implements `AVSpeechSynthesizerDelegate`'s `speechSynthesizer(_:didFinish:)` to call `AudioSessionManager.shared.deactivateAfterUtterance()`.
- `var isMuted: Bool` — read from/written to `UserDefaults` key `wepark_dm_voice_muted`.
- `func speak(_ text: String)` — if muted, no-op. Try `AudioSessionManager.shared.activateDriveSession()`, then enqueue utterance with `AVSpeechSynthesisVoice(language: "en-US")` and `AVSpeechUtteranceDefaultSpeechRate`. Cancels in-flight utterance before speaking to avoid stacking.
- `func stopImmediate()` — `synthesizer.stopSpeaking(at: .immediate)`.
- Mute toggle: `set isMuted` calls `stopImmediate()` when toggled to muted.

**Step 9 — `DrivingContextService`.**
Swift port of `getCurrentDrivingContext` (`index.html:5557–5587`) + `speakDrivingContext` (`index.html:5957–5979`) merged into one service.
- Input: `CLLocationCoordinate2D`, `CLLocationDirection?` (heading), `[Segment]` (tile data), `ParkingRulesEngine` (for `actionableSafetyLabel`).
- `func update(coordinate:heading:segments:engine:date:)` — finds closest segment via haversine (reuses the existing `TileLoader`/`ParkingRulesEngine` infrastructure), classifies N/S/E/W sides relative to heading, computes `leftLabel` and `rightLabel`, updates published `currentContext: DrivingContext?`.
- Block-change detection: stores `lastBlockKey: String?`. Calls `DrivingVoice.shared.speak(buildUtteranceText(context))` only when `blockKey != lastBlockKey`.
- `func buildUtteranceText(_ context: DrivingContext) -> String` — port of `speakDrivingContext`'s text construction (`index.html:5964–5970`): "[StreetName]. Left side, [label]. Right side, [label]." Expands abbreviations (St → Street, Ave → Avenue, Blvd → Boulevard). If a side has no data, omits that side's clause entirely.
- `DrivingContext` value type: `struct DrivingContext { street: String; from: String; to: String; leftLabel: SafetyLabel; rightLabel: SafetyLabel }`. `SafetyLabel` already exists via `ParkingRulesEngine`'s output.
- The voice frequency minimum gap (equivalent to PWA's `DRIVING_VOICE_MIN_GAP_MS = 12000`) is a calibration constant. Ship with 12 seconds default; W8.5c-follow will tune.

**Step 10 — `DriveModeBottomCard` view and `ContentView` wiring.**
`DriveModeBottomCard.swift`: Takes `context: DrivingContext?` and `voiceService: DrivingVoice` as inputs.
- When `context == nil`: shows "Looking for street…" in gray.
- When `context != nil`: shows street name, two chips (Left / Right) color-coded to severity palette (green = `freeComfortably`, orange = `freeButRestrictionSoon`, amber = `meteredActive`, red = `restrictedNow`, gray = unknown). Label text below each chip. Mute toggle button (speaker icon, `speaker.slash.fill` / `speaker.wave.2.fill`) bound to `voiceService.isMuted`.
- Font sizes: use system defaults (`.headline` for street name, `.subheadline` for chip labels). W8.5c-follow post-drive-test will specify overrides.
- Chip layout: `HStack` with equal-width chips. "Left" and "Right" header labels above each chip.

`ContentView.swift` additions:
- Instantiate `DrivingContextService` and `DrivingVoice` as `@State` or inject as environment objects.
- `@State private var drivingContext: DrivingContext?`
- In `.onChange(of: locationService.locationUpdateCount)` (already exists at line ~493), when `driveModeActive == true`, call `drivingContextService.update(coordinate:heading:segments:engine:date:)` and store result in `drivingContext`.
- When `driveModeActive` becomes true: call `locationService.startDriveMode()`. When it becomes false: call `locationService.endDriveMode()`, clear `drivingContext`.
- Add `.safeAreaInset(edge: .bottom)` containing `DriveModeBottomCard(context: drivingContext, voiceService: drivingVoice)` guarded by `driveModeActive`.
- Pass `driveHeading: locationService.driveHeading` to `MapViewRepresentable`.

## §5 — Acceptance Criteria

## §7 — Risks and Known Gotchas

**R-1: `MKMapView` camera heading and `regionDidChangeAnimated` feedback loop.**
Setting `mapView.camera.heading` programmatically fires `mapView(_:regionDidChangeAnimated:)` in the Coordinator, which writes back to the SwiftUI `region` binding, which triggers `updateUIView`, which may re-apply the camera heading — a potential tight loop. Mitigation: track `lastAppliedHeading` in the Coordinator (same pattern as the PWA's `drivingLastAppliedHeading`). Only call `setCamera` when the heading has changed by > 5 degrees from the last applied value. The existing `MapViewRepresentable` already guards against region-update loops for pan/zoom (line ~286 in `updateUIView` — "Sync camera only if it diverged…"). The same guard pattern should be extended to cover heading.

**R-2: `AVAudioSession` activation on `@MainActor`.**
`AVAudioSession.sharedInstance().setCategory` and `setActive` are not documented as main-thread-safe. `DrivingVoice.speak(_:)` will be called from `ContentView`'s `.onChange(of: locationService.locationUpdateCount)` handler, which is on the main thread. The synthesizer itself must speak on the main thread. The audio session activation call should be wrapped in a try/catch and any thrown error logged (not surfaced to user — if audio session activation fails, voice simply doesn't play, which is acceptable degradation). Do not crash on `AVAudioSession` errors.

**R-3: Continuous location permission scope.**
`startUpdatingLocation()` works with `.authorizedWhenInUse` when the app is in the foreground. Since Drive Mode is a foreground-only feature in W8.5c (no background audio, no `allowsBackgroundLocationUpdates = true`), this is sufficient. However, if the user backgrounds the app during a Drive Mode session, location updates stop. The master spec §10 AC-DM.23 notes this and requires a one-time informational note. W8.5c should add that note as a `UserDefaults`-gated one-time alert on first Drive Mode start. No `allowsBackgroundLocationUpdates` entitlement is needed for W8.5c.

**R-4: `CLLocationManager` mode switching during continuous updates.**
Changing `desiredAccuracy` and `activityType` on a running `CLLocationManager` (without stopping first) is officially supported but in practice can cause a brief gap in location updates on some devices. `startDriveMode()` should call `stopUpdatingLocation()` first, reconfigure, then `startUpdatingLocation()` again. This avoids any manager state confusion when transitioning from the single-shot mode.

**R-5: GPS jitter from PWA drive-test findings (master spec §11).**
The PWA had visible lag and jitter. iOS `CoreLocation` with `kCLLocationAccuracyBestForNavigation` is significantly better (master spec §11 table). However, the simulator's GPS simulation (used for CI tests) is not representative of real-device behavior. The EMA stabilizer unit tests (AC-W85c.12) can be verified without a real device, but R1 from the master spec (GPS smoothness in practice) requires a real-device smoke before the drive-test gate.

**R-6: The S-1 fix (route polyline Z-order) under continuous tile reloads.**
W8.5b QA pass-1 found and fixed the S-1 bug: route polylines drop below parking overlays after `applyOverlayPayload` rebuilds the overlay stack. The fix re-inserts the route polyline above parking overlays after each `applyOverlayPayload` call. W8.5c introduces continuous location updates, which on every GPS fix trigger `ContentView`'s `.onChange(of: locationService.locationUpdateCount)`, which calls tile-related updates that may trigger `applyOverlayPayload`. The S-1 fix must survive this higher-frequency trigger. AC-W85c.31 is the regression test; engineer must confirm the S-1 fix path is unconditionally executed, not only on the first `applyOverlayPayload` call.

**R-7: `@Observable` + `AVSpeechSynthesizer` ownership.**
`AVSpeechSynthesizer` must not be re-created on SwiftUI view re-renders. If `DrivingVoice` is an `@State` object in `ContentView`, SwiftUI may recreate it on state changes. Recommended pattern: use `@State private var drivingVoice = DrivingVoice()` at the `ContentView` level (SwiftUI creates `@State` once per view lifetime) or store it on the `AppDelegate`/scene-level object. The `@Observable` macro on a class is safe here. The engineer should verify that `DrivingVoice` is instantiated exactly once per app session.

**R-8: No new `Info.plist` keys expected.**
`NSLocationWhenInUseUsageDescription` already exists (W5.1). `NSLocationAlwaysAndWhenInUseUsageDescription` is not needed — W8.5c is foreground-only. If the engineer discovers a need to add any new `Info.plist` key, flag explicitly and add a PlistBuddy smoke check to verify it appears in the built bundle (lesson from W8.5a's INFOPLIST_KEY bug).
