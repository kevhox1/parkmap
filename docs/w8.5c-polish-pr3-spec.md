## Summary

PR-3 re-lands the 3D camera pitch that was part of the W8.5c-polish PR (#31, reverted 2026-05-26). The polish PR shipped 210/0 tests green and broke the live app: the entire SwiftUI overlay chain — toolbar, ASP banner, Park Until pill — stopped rendering. Architecture is the point of this spec. The original implementation called `setCamera` inside `MapViewRepresentable.updateUIView`, which runs synchronously during SwiftUI's view-update cycle; mutating UIKit state there races the still-in-progress SwiftUI mount and silently drops `.safeAreaInset(...)` overlay attachments. PR-3 corrects this by driving all camera mutation from a `.onChange(of: driveModeActive)` modifier in `ContentView` — outside the update cycle — and eliminates the headless-window guard that was the original code's second architectural smell.

## §0 — Open Questions for Kevin

**OQ-1 (bisectability vs. coupling):** PR-3 (tilt) and PR-2 (auto-zoom) are separate PRs per the 3-PR plan, but they fire on the same `driveModeActive` transition and mutate the same `MKMapView.camera`. The bisectability rationale is sound — after a hard-to-diagnose regression, atomic PRs let us confirm each piece is clean independently before adding the next. But the two camera changes will ultimately live in one code path. Is the engineering cost of a two-PR seam (PR-3 sets pitch only, PR-2 later adds the zoom to the same `.onChange` handler) worth it? Lean: keep them separate. PR-3's `.onChange` handler can be designed with PR-2's zoom slot already stubbed in so PR-2 is a straight add, not a rework. Kevin should confirm before implementation starts.

**OQ-2 (animation):** Should the pitch transition be animated (smooth ease, ~0.3s) or instant? The reverted code used `animated: false` (to make camera state readable immediately in unit tests — itself an architectural smell). The spec prescribes the behavior; Kevin's preference here drives the UX. Lean: animated entry, animated exit, duration ~0.3s. Tests verify the pitch value on the resulting camera object, not the in-flight animation.

**OQ-3 (exit behavior):** On Drive Mode exit, should the pitch restore to exactly the prior pitch value (captured at entry), or always reset to 0 (flat)? Prior pitch is almost always 0 — users don't manually tilt MKMapView — so in practice the two options are equivalent. Lean: restore prior pitch for correctness, consistent with the auto-zoom restore behavior PR-2 will add. Kevin should confirm if "always reset to 0" is simpler and acceptable.

## §1 — Scope

### In

- **3D camera pitch = 30° on Drive Mode entry.** When `driveModeActive` flips false → true, animate `MKMapView` camera pitch to 30°. Rationale for 30°: MapKit silently clamps pitch to ~35° at the zoom/altitude used during Drive Mode (span ~0.005°, corresponding altitude ~99,999m); 45° in code renders as ~35° in practice. 30° is below the clamping threshold and renders faithfully. Kevin confirmed 30° (per reverted PR accepted-deviation record in `docs/qa/w8.5c-polish-pass-1-2026-05-25.md`).
- **Pitch restore on Drive Mode exit.** When `driveModeActive` flips true → false, restore the pre-Drive-Mode pitch (captured at entry) and reset heading to 0 if pitch-reset is the exit behavior Kevin confirms for OQ-3.
- **Architecture:** Camera mutation driven by `.onChange(of: driveModeActive)` in `ContentView`, NOT inside `MapViewRepresentable.updateUIView`.
- **Transition guard:** Pitch fires exactly once per false→true or true→false transition (parallel to the existing `lastAppliedHeading` dead-band pattern in `MapViewRepresentable`).
- **R-1 coexistence:** `setCamera` for pitch fires `regionDidChangeAnimated`; the existing `lastAppliedHeading` dead-band and the new transition guard must both remain intact so neither heading updates nor pitch updates re-enter in a loop.
- **No headless-window guard in production code.**
- **Live-UI smoke** before declaring done (merge-blocking per `ios-engineer.md`).

### Out (explicitly deferred)

- **Auto-zoom** (PR-2) — span/altitude change on Drive Mode entry. The `.onChange` handler this PR introduces must reserve a seam for PR-2 to slot in zoom logic without rework, but must not implement it. Tag any zoom-adjacent code `[deferred to PR-2]`.
- Distance indicator — shipped in PR-1.
- End Drive z-order — shipped in PR-1.
- Heading-up rotation — shipped in W8.5c (PR #30); must not be disturbed.
- Final approach escalation — W8.5d scope.
- Camera animation duration / feel — subject to OQ-2; default to animated unless Kevin specifies otherwise.

## §3 — Implementation Plan

This section is the architectural core. Read before writing any code.

### 3.1 The banned pattern (do not repeat)

The reverted `2df5603` called `syncDriveCamera(active:preDriveRegion:on:)` from inside `updateUIView` at line 327–337 of `MapViewRepresentable.swift`. `updateUIView` executes synchronously during SwiftUI's view-update cycle. Calling `mapView.setCamera(...)` from within it races SwiftUI's still-in-progress layout pass — the most likely cause of the silent overlay-chain drop (toolbar, banner, pill all missing in the live app despite 210/0 tests passing).

**Never mutate `MKMapView` camera state inside `updateUIView`.** If `updateUIView` must participate at all (e.g., to read a flag), it may only set a marker and dispatch the mutation asynchronously after the current cycle via `DispatchQueue.main.async`. The cleaner path — prescribed below — avoids `updateUIView` involvement entirely.

### 3.2 The prescribed pattern: `.onChange`-driven coordinator action

**Step 1 — Add an action closure to `MapViewRepresentable`.**

In `MapViewRepresentable` (the `UIViewRepresentable` struct), add an optional action closure:

```
var onDriveModeChanged: ((Bool, priorPitch: CGFloat) -> Void)?
```

Or, equivalently, expose a method on the `Coordinator` that `ContentView` can call directly. The closure approach keeps the signal unidirectional (SwiftUI → UIKit); the coordinator method approach is also acceptable. Either way, the call site is in `ContentView`, not in `updateUIView`.

**Step 2 — Wire the closure in `ContentView.makeBody` (or wherever `MapViewRepresentable` is constructed).**

When constructing `MapViewRepresentable`, pass a closure that calls into the coordinator. Since the coordinator is created by `makeCoordinator()` and not directly accessible from `ContentView`, the cleanest pattern is:

- Store a `@State private var applyDrivePitch: ((Bool) -> Void)? = nil` in `ContentView` (or a similar action-callback binding).
- In `MapViewRepresentable.makeUIView`, after creating the coordinator, stash the coordinator's `applyDriveCameraPitch` method reference into a closure that `ContentView` can hold onto — e.g., via a `Binding<((Bool) -> Void)?>` or by passing an `ActionBox` reference type.

A simpler alternative that avoids the coordinator-reference problem: use a `@State private var driveModeChangeToken: Int = 0` in `ContentView` that increments when `driveModeActive` changes, and pass both `driveModeChangeToken` and `driveModeActive` as properties to `MapViewRepresentable`. Then in `updateUIView`, check `if driveModeActive != coordinator.lastDriveModeActive` and dispatch the pitch mutation **async**:

```swift
// In updateUIView — ONLY if the token changed:
if driveModeActive != coordinator.lastDriveModeActive {
    coordinator.lastDriveModeActive = driveModeActive
    let active = driveModeActive
    let prior = priorPitch
    DispatchQueue.main.async {
        coordinator.applyDriveCameraPitch(active: active, priorPitch: prior, on: mapView)
    }
}
```

The `DispatchQueue.main.async` defers the `setCamera` call to after the current SwiftUI update cycle completes, avoiding the race. This is the async-dispatch fallback path.

**Recommended path (cleaner): pure `.onChange` in `ContentView`, no `updateUIView` involvement.**

Add a dedicated `.onChange(of: driveModeActive)` block specifically for camera pitch — separate from the existing W8.5c `handleDriveModeChange(_:)` block that manages location and audio lifecycle:

```swift
.onChange(of: driveModeActive) { _, active in
    handleDriveCameraChange(active)
}
```

In `handleDriveCameraChange(_:)`:
1. Capture `mapView.camera.pitch` into `@State private var preDrivePitch: CGFloat = 0` when `active` is true (at entry).
2. Call a method on the coordinator that applies or restores pitch to the live `MKMapView`.

The challenge: `ContentView` does not hold a direct reference to the `MKMapView` or its `Coordinator`. Solve this with a `@State private var mapViewCoordinatorActions: MapViewCoordinatorActions? = nil` where `MapViewCoordinatorActions` is a simple reference-type box (`class`) that `MapViewRepresentable.makeUIView` populates and `ContentView` receives via a `Binding`. This is the cleanest seam: `makeUIView` creates the coordinator, populates the action box, and from that point forward `ContentView` can call coordinator actions directly from `.onChange` handlers without going through `updateUIView`.

Pseudo-sketch of the action box pattern (not production code — engineer adapts):

```
// In MapViewRepresentable:
class CoordinatorActions {
    var applyDrivePitch: ((Bool, CGFloat) -> Void)?
}
var coordinatorActions: CoordinatorActions

// In makeUIView:
coordinatorActions.applyDrivePitch = { [weak coordinator] active, priorPitch in
    guard let c = coordinator, let mapView = c.mapView else { return }
    c.applyDriveCameraPitch(active: active, priorPitch: priorPitch, on: mapView)
}

// In ContentView:
.onChange(of: driveModeActive) { _, active in
    if active { preDrivePitch = coordinatorActions.captureCurrentPitch?() ?? 0 }
    coordinatorActions.applyDrivePitch?(active, preDrivePitch)
}
```

The engineer must choose one concrete mechanism. Both the action-box and the `DispatchQueue.main.async`-in-`updateUIView` paths are acceptable; the action-box is preferred because it keeps `updateUIView` free of camera logic entirely. Flag the chosen mechanism in the PR description so QA can verify it.

**What is NOT acceptable:**
- Calling `mapView.setCamera(...)` synchronously inside `updateUIView` (any code path that does this is the banned pattern).
- A `headlessWindow: UIWindow?` property on the Coordinator, or any production code that synthesizes a `UIWindowScene` for test purposes.

### 3.3 Coordinator method: `applyDriveCameraPitch`

The coordinator method (wherever it is called from) should:

1. Apply `MKMapCamera.pitch = MapViewRepresentable.driveModePitch` (30°) on Drive Mode entry. Set only pitch; do not change `centerCoordinateDistance` or `heading` (those are PR-2 and the heading dead-band respectively). Apply in a single `setCamera` call.
2. On Drive Mode exit, restore `priorPitch` (or always 0 — pending OQ-3). Apply in a single `setCamera` call.
3. Respect `animated:` per OQ-2 resolution (lean: `animated: true`, duration governed by MapKit's default animation).

The method signature (conceptual):
```
func applyDriveCameraPitch(active: Bool, priorPitch: CGFloat, on mapView: MKMapView)
```

Do not change `centerCoordinateDistance` (zoom) in this method. Leave a `// [deferred to PR-2]` comment at the altitude line so the PR-2 engineer knows exactly where to add the zoom logic without restructuring the method.

### 3.4 Transition guard (R-1 coexistence)

`setCamera` calls fire `regionDidChangeAnimated` on the `MKMapViewDelegate`. The existing W8.5c heading-up rotation (`syncDriveHeading`) already guards against this feedback loop via `lastAppliedHeading` dead-band. The new pitch code must not interfere with that guard.

Specifically:
- `applyDriveCameraPitch` fires ONCE per Drive Mode entry and ONCE per exit (transition-driven from `.onChange`). It does not fire again on subsequent `regionDidChangeAnimated` events because it is NOT called from `updateUIView`.
- The existing `lastAppliedHeading` dead-band in `syncDriveHeading` continues to operate independently. After the pitch `setCamera` fires `regionDidChangeAnimated`, `updateUIView` is called, which calls `syncDriveHeading`. The heading at that moment equals `lastAppliedHeading` (or nil if Drive Mode just started before the first heading fix), so the dead-band gate returns early and no heading camera mutation occurs.
- The engineer must verify this coexistence in a test: apply pitch, then verify `syncDriveHeading` with the same heading value as `lastAppliedHeading` skips the camera update (no loop).

**If the action-box / `.onChange` pattern is used correctly, the feedback loop cannot occur** because `applyDriveCameraPitch` is never called from `updateUIView` — only from `ContentView`'s `.onChange` handler, which fires on user-visible state transitions, not on every SwiftUI render.

### 3.5 No headless-window guard

The reverted code added `private var headlessWindow: UIWindow?` and a large `if mapView.window == nil { ... }` block inside `syncDriveCamera`. This code:
- Synthesized a `UIWindowScene` window in production to make headless `MKMapView()` unit tests work.
- Pumped the run loop with `RunLoop.main.run(until: Date(timeIntervalSinceNow: 0.15))` — 150ms of blocking the main thread on every `updateUIView` cycle that evaluated the guard (even when the guard short-circuited, it evaluated the `mapView.window` check).
- Is the strongest suspect for the "noticeable lag" Kevin reported after the revert.

**This guard must not exist in PR-3.** See §5 for the test strategy that makes it unnecessary.

## §5 — Tests

### Strategy: pure-function decision + live-UI smoke

The reverted code's test problem: `DriveCameraTests` in `W85cPolishTests.swift` instantiated a bare `MKMapView()` and called `syncDriveCamera` on it, then read `mapView.camera.pitch` to assert the value. `MKMapView` camera reads are only synchronous when the view is in a live `UIWindowScene` window. The "fix" was the `headlessWindow` guard in production code — unacceptable.

**PR-3 prescribes pattern (a): separate the decision from the mutation.**

Extract a pure function (free of `MKMapView`) that computes the target pitch:

```swift
// In MapViewRepresentable or a PitchCalculator namespace:
static func targetPitch(forDriveModeActive active: Bool, priorPitch: CGFloat) -> CGFloat {
    active ? driveModePitch : priorPitch
}
```

This function is trivially unit-testable with no `MKMapView`, no `UIWindowScene`, and no run-loop pumping:

```swift
// In DriveCameraTiltTests.swift:
func testPitchDecision_onEntry_returns30() {
    XCTAssertEqual(MapViewRepresentable.targetPitch(forDriveModeActive: true, priorPitch: 0), 30, accuracy: 1)
}
func testPitchDecision_onExit_restoresPriorPitch() {
    XCTAssertEqual(MapViewRepresentable.targetPitch(forDriveModeActive: false, priorPitch: 5), 5, accuracy: 1)
}
func testPitchDecision_onExit_noprior_returnsZero() {
    XCTAssertEqual(MapViewRepresentable.targetPitch(forDriveModeActive: false, priorPitch: 0), 0, accuracy: 1)
}
```

The actual `MKMapView.setCamera` call is a thin imperative shell around this decision. Its correctness is verified by the live-UI smoke (AC-1, AC-7), not by unit test.

**The dead-band coexistence test does NOT require MKMapView camera reads.** It tests the guard logic on `lastAppliedHeading`:

```swift
func testHeadingDeadBand_afterPitchChange_duplicateHeadingIsSkipped() {
    // Create a coordinator, set lastAppliedHeading = 90.
    // Call syncDriveHeading(90, on: mockMapView).
    // Assert camera was NOT mutated (guard fired).
}
```

Use a `MockMKMapView` subclass or a simple spy to assert `setCamera` was or was not called. This pattern needs no `UIWindowScene`.

**Minimum test count:** 4 new tests in `DriveCameraTiltTests.swift` — 3 pure-function pitch-decision tests + 1 dead-band coexistence test. The engineer may add more; the live-UI smoke is the runtime gate.

**Explicitly forbidden:** Any of the following in production code introduced by this PR:
- `if mapView.window == nil { ... }`
- `UIApplication.shared.connectedScenes`
- `RunLoop.main.run(until:)`
- `headlessWindow`
- Stashing a `UIWindow` reference on the Coordinator for test purposes

If the test requires `MKMapView` camera state verification and the pure-function approach is insufficient, the correct fix is a real `UIWindowScene` in the TEST TARGET (a `testHelper` setup that creates and tears down a window in `setUp/tearDown`), not production code that is aware of the test environment.

## §6 — Risks

### R-1 (primary): Re-breaking the overlay chain (the #31 regression class)

Any synchronous UIKit mutation inside `updateUIView` is a regression risk. The spec's prescribed architecture (`.onChange`-driven, outside the update cycle) eliminates this risk by design. The engineer must verify the chosen mechanism does not introduce any synchronous `setCamera` call from `updateUIView`.

The live-UI smoke (AC-7) is the runtime gate. A screenshot of the live app with Drive Mode active — confirming toolbar, ASP banner, and pill all render — is the evidence. "Tests pass" alone is not sufficient sign-off for this PR.

### R-2: Feedback loop (R-1 analogue for camera)

`setCamera` fires `regionDidChangeAnimated`. If the pitch application is ever triggered from `updateUIView` (directly or via a property flag read inside `updateUIView`), the transition fires on every render cycle, not just on the Drive Mode state flip. The `.onChange`-driven approach prevents this. If the async-dispatch fallback path is used instead, the transition guard (`lastDriveModeActive` flag checked inside `updateUIView`) must prevent re-dispatch on subsequent renders.

### R-3: PR-2 coupling

Tilt and auto-zoom both mutate `MKMapView.camera` on the same `driveModeActive` transition. PR-3's camera call must not set `centerCoordinateDistance` (the zoom/altitude). The `// [deferred to PR-2]` comment at that line is load-bearing: it is the seam PR-2 slots into. If PR-3 silently also changes altitude, PR-2's test coverage will be incomplete.

### R-4: `animated: true` test readability

If OQ-2 resolves to `animated: true`, unit tests cannot read the post-animation camera state synchronously (the animation hasn't completed). Tests should assert on the pitch decision function result (pure function, no animation) rather than on `mapView.camera.pitch` after calling `setCamera(animated: true)`. This is exactly why the pure-function strategy in §5 is recommended: it sidesteps the animated/synchronous tension entirely.

### R-5: `pbxproj` churn

New test file `DriveCameraTiltTests.swift`. The current project uses `PBXFileSystemSynchronizedRootGroup` for test files (consistent with how `W85cPolishTests.swift` was picked up automatically per the QA report). The engineer must verify the new file is picked up without touching `project.pbxproj`. If it is not, flag before opening the PR — do not silently edit `pbxproj`.
