## Summary

W8.5d is the first genuinely novel destination-mode feature: it adds the final-approach
experience that the master spec identifies as "the moment of value" (§1 — "two or three turns
away from their target destination" is where fear reduction happens). The polish trilogy
(PR-1/3/2) delivered the driving UI surface; W8.5d makes that surface react as the driver
closes in on their target.

When the user is within 500m of their destination, the app enters "approaching" state: voice
commentary escalates from once-per-block to a tighter cadence. A visual "Approaching
destination" strip appears. At the arrival threshold (~50m), the app fires a one-shot prompt
asking the driver to park — and if they confirm, drops the W5 pin at their actual current
location, triggering the existing W7.5 "Park Until X" sheet naturally. The arrival prompt
→ W5 pin-drop hook is the literal payoff of the parking-fear-reduction success metric
(master spec §6: "pin drop within 10 minutes of Drive Mode end" is the measurable proxy).

## §0 — Open Questions (resolve before code starts)

Kevin must confirm all six. Recommendations are included; they represent the tech-lead lean,
not final decisions.

**OQ-1: Where does the "Approaching destination" visual strip live?**

Three options:

- (a) Full-width banner directly below the ASP banner (top of screen). Visible from the
  dashboard at distance. Stacks with the ASP banner — the existing `paddingForBannerState`
  function in `ContentView.swift` handles the End Drive pill clearance and will need a new
  case for the approach strip. The `.safeAreaInset(edge: .top)` chain gains a second
  chained call while the approach strip is active.
- (b) Attached above the bottom card (`DriveModeBottomCard`). The card already has a
  `showApproachStrip: Bool` placeholder parameter (line 55 of `DriveModeBottomCard.swift`
  and the `// W8.5d placeholder:` comment in the `VStack` body, line 62). Option (b) is the
  lowest-risk attachment point: no new `.safeAreaInset` layer, the placeholder is already
  wired, the End Drive pill clearance is unaffected.
- (c) Transient toast at the top (fades after ~3s on first entry into `.approaching`,
  does not persist). Lower information value — the driver needs a persistent indicator while
  in the approach zone, not just an entry toast.

Lean: **(b)**. The placeholder in `DriveModeBottomCard.swift` already exists specifically
for this. It avoids adding a new `.safeAreaInset` layer (the regression class from reverted
PR #31 — every new overlay attachment is a live-UI smoke risk). The strip inside the card
is visible to the driver because Drive Mode auto-zooms to ~1-2 blocks (PR-2) and the bottom
card is always in the thumb zone of a dashboard-mounted phone. If (a) is chosen, the
engineer must extend `paddingForBannerState(_:)` to account for both ASP banner height AND
approach strip height in the End Drive pill offset; document the exact pixel addition in the
PR.

**OQ-2: Voice escalation — what is the new minimum gap during final approach?**

Current `DrivingContextService.voiceMinGapSeconds` is 12 seconds (hardcoded, calibration
deferred since W8.5c). During final approach, the driver is actively scanning. Options:
3s, 4s, 5s.

Lean: **4 seconds** as the shipping default. At 30 mph (typical approach speed in
Manhattan), 4s ≈ 54m between cues — about half a city block. This is aggressive but not
spammy: the driver will hear at most 2-3 cues per block rather than one. Flag this as a
calibration target for W8.5c-follow post-drive-test.

A `FINAL_APPROACH_VOICE_MIN_GAP_S = 4.0` constant replaces the hardcoded 12s in the
approaching state. The clean way to implement this is `FinalApproachService.voiceGap(for:)`
— a pure function returning `TimeInterval` by state (see §3). `DrivingContextService` reads
from this function instead of from its own hardcoded constant when Drive Mode is active.

**OQ-3: Arrival prompt UX — sheet, alert, or inline?**

Three options:
- (a) `.alert` — modal, system-style, appears over the map. Simple but can feel jarring.
- (b) Sheet matching the existing `ParkConfirmView` pattern — same `.sheet(item:)` channel,
  new `ActiveSheet.arrivalPrompt(CLLocationCoordinate2D)` case. Consistent, uses established
  patterns.
- (c) Custom inline banner at the bottom (replaces the bottom card temporarily). Avoids a
  modal interruption but cannot use the existing `.sheet(item:)` infrastructure.

Lean: **(b)**. Consistent with existing sheet patterns, reuses `ActiveSheet` enum, no new
modal layer. The engineer adds `case arrivalPrompt(CLLocationCoordinate2D)` to `ActiveSheet`
— the payload is the user's current GPS coordinate at the moment of arrival detection
(NOT the destination coordinate).

**OQ-4: Arrival threshold — how close is "arrived"?**

Options: 30m, 50m, 75m. At 50m the driver is in the block containing their destination
and is actively looking. At 30m the prompt may fire late if the destination is mid-block
and the driver turns the corner first. At 75m the prompt can fire half a block early.

Lean: **50m**. Matches the master spec AC-DM.20's "within 100m" with a tighter inner
threshold. Explicitly flag as a calibration item for Kevin's drive-test — GPS accuracy in
Manhattan (canyon effect) means 50m may feel like 80m or 30m on any given run.

**OQ-5: Pitch escalation during final approach — use the PR-3 hook or not?**

PR-3's `applyDriveCameraPitch` doc-comment explicitly notes the W8.5d reuse opportunity:
"this method is intentionally reusable for final-approach pitch escalation (e.g., increase
pitch to 60° in the final 500m) without structural change."

Options:
- (a) Keep pitch at 45° throughout Drive Mode. No change to `MapViewRepresentable`.
  Simpler; no new regression surface.
- (b) Escalate pitch to 55° (or 60°) on entry to `.approaching`, restore to 45° on exit
  from `.approaching`. Calls `coordinatorActions.applyDrivePitch?(.approaching, 45)` from
  a new `.onChange(of: finalApproachState)` handler. Adds a camera mutation `.onChange`
  handler — a new regression surface for the #31 class.

Lean: **(a)** for this PR. The visual benefit of a steeper approach pitch is speculative
without drive-test data. The cost is a new live-UI smoke regression surface. Defer pitch
escalation to W8.5c-follow once Kevin has driven the 45° tilt in a real car and has an
opinion. Document the seam in the spec so it is easy to add.

**OQ-6: What happens after the user dismisses the arrival prompt without parking?**

Options:
- (a) Stay in Drive Mode indefinitely. The End Drive pill is always tappable. The arrival
  prompt was one-shot (fires only once per Drive Mode session, on the first transition into
  `.arrived`). The driver is circling the block — do not force an end.
- (b) Auto-end Drive Mode after a configurable idle timeout (e.g., 2 minutes after arrival
  with speed < 2 mph).
- (c) Re-prompt every N seconds while in `.arrived` state.

Lean: **(a)**. Option B requires a new idle timer, Option C is irritating. The driver who
dismisses "Not yet" is still looking; the End Drive pill is always available. One-shot
arrival detection (hysteresis gate) prevents oscillation at the GPS boundary.

## §1 — Scope

### In

- **`FinalApproachService` (or equivalent pure-function module):** owns the state machine
  `finalApproachState(forDistanceMeters:) -> FinalApproachState` (`.outside`, `.approaching`,
  `.arrived`) and `voiceGap(for:) -> TimeInterval` pure functions. Testable with zero
  `MKMapView` or `AVSpeechSynthesizer` dependency.
- **`.onChange(of: driveModeDistanceMeters)` handler in `ContentView`:** computes
  `FinalApproachState` from the existing `driveModeDistanceMeters` state variable (already
  maintained by `handleLocationUpdate()` — no new GPS plumbing needed) and drives state
  transitions.
- **Voice gap escalation:** `DrivingContextService.voiceMinGapSeconds` is replaced by a
  call to `voiceGap(for: currentApproachState)` so it reads 12s in `.outside` and 4s in
  `.approaching`. In `.arrived` voice is suppressed (arrival prompt is the UI cue).
- **"Approaching destination" visual strip:** rendered inside `DriveModeBottomCard.swift`
  via the existing `showApproachStrip: Bool` parameter (see §3 for wire-up). Strip content:
  a tinted single-line text row "Approaching destination" above the street-name row. Color:
  app accent color with opacity(0.15) background, matching the chip palette language.
- **Arrival prompt:** new `ActiveSheet.arrivalPrompt(CLLocationCoordinate2D)` case. New
  `ArrivalPromptSheet.swift` view (or adapt existing `ParkConfirmView` — engineer's call,
  see §2 note). The coordinate payload is the user's GPS position at the moment the
  `.arrived` state fires, NOT the destination coordinate.
- **W5 pin-drop hook:** arrival prompt → confirm → calls
  `parkPinService.save(ParkedCar(coordinate: arrivalCoordinate, ...))` using the same logic
  path as the existing long-press → `ParkConfirmView` → `confirmPinDrop` flow. The
  `pinDropped` publisher fires, the W7.5 "Park Until X" follow-up sheet fires naturally.
  Drive Mode ends on confirm (set `driveModeActive = false`).
- **One-shot hysteresis gate:** The arrival prompt fires exactly once per Drive Mode session.
  A `@State private var arrivalPromptFired: Bool = false` flag in `ContentView` (reset on
  `driveModeActive` → false) prevents re-firing if GPS jitters around the 50m boundary.
- **Unit tests** for all pure-function decisions: `finalApproachState(forDistanceMeters:)`,
  `voiceGap(for:)`, threshold edge cases.
- **Live-UI smoke** (merge-blocking for this PR, per the ios-engineer.md norm — this PR
  touches `ContentView.swift` and `DriveModeBottomCard.swift`).

### Out — Option B framing reminder

Per master spec §9, the following are not in scope for ANY Drive Mode iOS v1.0 stream:
- Full turn-by-turn navigation ribbon or voice nav.
- ETA / distance-remaining / speed readout.
- Re-routing on deviation.
- Option B+ maneuver hint ("Turn left on Prince St" strip) — flagged by Kevin during PR-3
  smoke; separate spec needed; explicitly deferred in HANDOFF.md 2026-05-30 Changelog.
- Patrol mode — W8.5e–i.
- Pitch escalation in final approach (OQ-5 resolved as option (a) for this PR).

## §3 — Implementation Plan

This section is the architectural core. Read before writing any code. The pattern is
`.onChange`-driven — same as PR-3 and PR-2. W8.5d extends, does not parallel, those specs.

### 3.1 `FinalApproachService` — pure-function state machine

Define the state type and the decision functions in a new file. No MapKit, no CoreLocation,
no AVFoundation imports:

```
// Conceptual — not production code:
enum FinalApproachState: Equatable {
    case outside       // > approachThresholdMeters from destination
    case approaching   // approachThresholdMeters >= distance > arrivalThresholdMeters
    case arrived       // distance <= arrivalThresholdMeters
}

// Pure function — no side effects, trivially testable:
static func finalApproachState(forDistanceMeters distance: Double) -> FinalApproachState {
    if distance <= FinalApproachService.arrivalThresholdMeters    { return .arrived }
    if distance <= FinalApproachService.approachThresholdMeters   { return .approaching }
    return .outside
}

// Pure function — returns the voice cue minimum gap for a given approach state:
static func voiceGap(for state: FinalApproachState) -> TimeInterval {
    switch state {
    case .outside:    return 12.0   // matches existing DRIVING_VOICE_MIN_GAP_S
    case .approaching: return 4.0   // elevated (OQ-2 lean — confirm with Kevin)
    case .arrived:    return .infinity  // suppress voice; arrival prompt is the cue
    }
}
```

Both functions are `static` — no instance needed. The constants `approachThresholdMeters`
and `arrivalThresholdMeters` are `static let` so tests can reference them for boundary
coverage without magic numbers.

### 3.2 `ContentView` — `.onChange(of: driveModeDistanceMeters)` handler

The existing `driveModeDistanceMeters: Double?` state var in `ContentView` (line 231) is
already recomputed on every location fix by `handleLocationUpdate()`. W8.5d adds a new
`.onChange(of: driveModeDistanceMeters)` modifier that drives approach-state transitions:

```
// Conceptual — not production code:
.onChange(of: driveModeDistanceMeters) { _, distanceOrNil in
    handleFinalApproachUpdate(distanceOrNil)
}
```

`handleFinalApproachUpdate(_:)`:
1. Guard: if `!driveModeActive || driveDestinationCoordinate == nil`, reset state to
   `.outside` and return.
2. Guard: if `distance == nil` (no destination set), reset to `.outside` and return.
3. Compute `let newState = FinalApproachService.finalApproachState(forDistanceMeters: distance)`.
4. If `newState != finalApproachState`:
   - Update `finalApproachState = newState`.
   - Call `drivingContextService?.setVoiceGap(FinalApproachService.voiceGap(for: newState))`.
     (See §3.3 for the `DrivingContextService` modification.)
5. If `newState == .arrived && !arrivalPromptFired`:
   - Set `arrivalPromptFired = true`.
   - Capture current location: `let arrivalCoord = locationService.userLocation?.coordinate`.
   - If `arrivalCoord != nil`: `activeSheet = .arrivalPrompt(arrivalCoord!)`.
   - If no location fix available, no-op (GPS edge case — user will see the approach strip
     still active, can tap End Drive manually).

**Reset on Drive Mode exit (in `handleDriveModeChange(_:)`, the existing handler):**
When `active == false`, add:
```
finalApproachState = .outside
arrivalPromptFired = false
```

### 3.3 `DrivingContextService` — voice gap becomes settable

The current hardcoded `private let voiceMinGapSeconds: TimeInterval = 12` becomes a settable
property:

```
// Conceptual — not production code:
private var voiceMinGapSeconds: TimeInterval = 12.0

func setVoiceGap(_ gap: TimeInterval) {
    voiceMinGapSeconds = gap
}
```

The `speakContext(_:)` guard becomes `guard now.timeIntervalSince(lastSpokenAt) >= voiceMinGapSeconds`.
When `voiceMinGapSeconds == .infinity` (arrived state), the guard always returns early —
voice is effectively suppressed without any new code path.

**Important:** `setVoiceGap` is called from `ContentView`'s `.onChange` handler, which is
on the main thread. `DrivingContextService` is `@Observable` — property mutations from the
main thread are safe.

### 3.4 Approaching strip — inside `DriveModeBottomCard`

The placeholder at `DriveModeBottomCard.swift:62` reads:
```swift

// showApproachStrip && context != nil → escalation UI (W8.5d).
```

Wire it:


This renders as a tinted accent-color strip at the top of the bottom card's VStack,
above `cardContent`. No new `.safeAreaInset` layer — the strip lives inside the existing

**Wire `showApproachStrip` in `ContentView`:** pass `finalApproachState == .approaching`

### 3.5 Arrival prompt → W5 pin-drop

In `sheetContent(_:)` for the new `.arrivalPrompt(let coord)` case:
- Present `ArrivalPromptSheet` (or adapted `ParkConfirmView`).
- On "Park Here" confirm:
  1. `activeSheet = nil`.
  2. Construct a `ParkedCar` at `coord` using the nearest detected segment from
     `drivingContext` (if available) — same logic as the existing `initiatePathBPinDrop`.
  3. Call `parkPinService.save(car)`.
  4. `driveModeActive = false` (ends Drive Mode, resets all approach state via the
     existing `handleDriveModeChange(false)` path).
  5. `pinDropped` fires → W7.5 Park Until follow-up fires naturally per the existing
     `.onReceive(parkPinService.pinDropped)` subscription already wired in `ContentView`.
- On "Not Yet" dismiss:
  1. `activeSheet = nil`.
  2. Drive Mode stays active. `arrivalPromptFired` remains `true` (no re-fire).
  3. `finalApproachState` remains `.arrived`.

**The arrival coordinate is the user's GPS position, NOT the destination coordinate.**
This is load-bearing: the user parked where they found a spot, not at the address they typed.

### 3.6 Existing architecture compatibility

- `driveModeDistanceMeters` is already maintained in `handleLocationUpdate()` via
  `CLLocation.distance(from:)` on `locationService.userLocation` and
  `driveDestinationCoordinate`. No new GPS plumbing.
- The approaching-strip is inside `DriveModeBottomCard`, which is already inside the
  `.safeAreaInset(edge: .bottom)` safe-area chain. No new overlay attachment.
- `ActiveSheet.arrivalPrompt` is a new case — the existing single `.sheet(item:)` modifier
  handles it. No second sheet modifier.
- OQ-5 resolved as (a): no `MapViewRepresentable` changes, no new `.onChange(of:
  driveModeActive)` camera handler, no new `CoordinatorActions` extensions.

## §6 — Risks

### R-1 (primary): Approaching strip disturbs the overlay chain (#31 regression class)

Adding any new view inside `DriveModeBottomCard` could shift the bottom card's intrinsic
height, which in turn changes how the `.safeAreaInset(edge: .bottom)` pushes content up.
If the height change is unexpected, overlay attachments above it (Park Until pill, bottom
card itself) could be displaced.

**Mitigation:** The strip is inside the existing `.safeAreaInset` bottom-card VStack —
not a new top-level overlay attachment. Height changes to the card are accommodated
naturally by `safeAreaInset` (the inset grows). The End Drive pill sits ABOVE the bottom
safe area inset and does not need adjustment. The live-UI smoke (AC-0a, AC-0b) is the
runtime gate. Kevin's manual smoke (AC-9) verifies the pill position with strip visible.

If OQ-1 resolves as option (a) instead (top banner), the engineer MUST extend
`paddingForBannerState(_:)` in `ContentView.swift` to add strip height to the End Drive
pill top padding when `finalApproachState == .approaching`. That is a non-trivial change
to the overlay chain and requires a separate live-UI smoke step.

### R-2: Voice gap stacking — setVoiceGap must REPLACE, not stack

`DrivingContextService.voiceMinGapSeconds` is currently a hardcoded constant. W8.5d
makes it settable. The risk: if `setVoiceGap` is called at the wrong time or from the
wrong thread, or if the `.onChange` fires before `drivingContextService` is non-nil,
the gap could be left in a stale state across Drive Mode sessions.

**Mitigation:**
- `setVoiceGap` is called from `ContentView`'s `.onChange(of: driveModeDistanceMeters)`
  — main thread, after `drivingContextService` is initialized (it's initialized in
  `handleDriveModeChange(true)` which fires before any location updates).
- `voiceMinGapSeconds` resets to 12.0 when `DrivingContextService` is re-instantiated
  on the next Drive Mode session (it is re-created on each `driveModeActive` flip-true,
  per HANDOFF.md W8.5c row N-3 note).
- Tests verify `voiceGap(for: .outside) == 12.0` — if the property default drifts, tests
  catch it.

### R-3: Arrival oscillation — GPS jitter at the 50m boundary

GPS accuracy in Manhattan (canyon effect) can jitter ±15–30m. A driver stationary near
the 50m boundary may see `driveModeDistanceMeters` oscillate 40m → 55m → 45m → 60m.
Without a hysteresis gate this fires the arrival prompt repeatedly.

**Mitigation:** The `arrivalPromptFired: Bool` flag is the gate. Once `.arrived` is first
reached and the prompt fires (or attempts to fire), the flag is set to `true` for the
rest of the Drive Mode session. The `.onChange` handler checks `&& !arrivalPromptFired`
before presenting the sheet. No re-fire regardless of subsequent oscillation.

### R-4: Arrival with no GPS fix

`locationService.userLocation` is `CLLocation?`. On the rare occasion `.arrived` fires
but `userLocation` is nil (GPS loss at arrival — unlikely but possible in a deep parking
garage approach), `arrivalCoord` is nil and the prompt does not fire. The user sees the
approach strip still active and can tap End Drive manually.

**Mitigation:** Explicit guard in `handleFinalApproachUpdate(_:)`: if `arrivalCoord ==
nil`, set `arrivalPromptFired = false` (don't mark it fired if we couldn't show it) and
return. If GPS recovers and distance is still <= 50m, the `.onChange` fires again and
the prompt fires then.

### R-5: `ActiveSheet` extensibility collision

`ActiveSheet.arrivalPrompt(CLLocationCoordinate2D)` is a new case. `CLLocationCoordinate2D`
is not `Codable` or `Hashable` — it requires custom `id` computation in the `Identifiable`
conformance. The existing `ActiveSheet.id` switch computes string IDs. Add:

```
case .arrivalPrompt(let coord): return "arrivalPrompt-\(coord.latitude)-\(coord.longitude)"
```

This is fine for the use case (there is only ever one arrivalPrompt at a time). Ensure
the case is handled in `sheetContent(_:)` — the Swift compiler will warn if it is missed.

### R-6: Pitch escalation (OQ-5 resolved as option (a) — not shipping)

Pitch escalation is explicitly OUT of scope for this PR. If the engineer is tempted to
add it (it is architecturally easy — the PR-3 hook exists), they must flag it as scope
creep and defer. The specced behavior is 45° constant pitch throughout Drive Mode.
