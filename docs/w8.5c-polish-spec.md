## §0 — Open Questions for Kevin

Four decisions before code starts. Recommendations are tech-lead opinions, not decisions. Surface these first; do not start implementation until Kevin confirms.

**OQ-1: Default zoom span on Drive Mode start.**
When `driveModeActive` flips true, what span should the camera animate to?
- Option A: ~0.005° lat (~500m radius, roughly "1–2 blocks visible end-to-end")
- Option B: ~0.01° lat (~1km radius, "3–4 blocks visible")
- Option C: Do not change zoom — only animate pitch + heading, leave prior span alone.

Recommendation: **Option A (0.005°).** Apple Maps drive mode zooms in aggressively so the user can read block names without squinting. 0.005° keeps a block or two on each side visible. Option C risks starting Drive Mode at whatever the user had previously zoomed to, which could be very wide. Option B is a reasonable fallback if A feels too zoomed in; the engineer should spec this as a named constant (`DriveModeCameraSpan`) so Kevin can tune it post-drive-test without a code change.

**OQ-2: Restore prior zoom on End Drive, or stay at drive-zoom?**
When Drive Mode exits, the camera zoom was programmatically tightened. Two options:
- Option A: Restore the pre-Drive-Mode zoom span (store it before overwriting).
- Option B: Leave the camera at drive-zoom. The user can pinch to zoom out.

Recommendation: **Option A (restore).** Apple Maps restores prior zoom on navigation end. Less jarring than leaving a hyperzoomed map after a 20-minute session. Store the prior region as a `let preDriveRegion: MKCoordinateRegion?` in `ContentView` at the moment `driveModeActive` flips true, then restore it when Drive Mode exits.

**OQ-3: Camera pitch angle during Drive Mode.**
Apple Maps uses ~60° pitch in drive mode. Options:
- Option A: 45° — moderate 3D angle. Preserves more of the parking-state overlay layer visible on the map ahead. Less extreme; safer for a first pass.
- Option B: 60° — matches Apple Maps. More dramatic; may occlude overlay data closer to the camera eye.

Recommendation: **Option A (45°).** The parking overlays are the primary data — a 60° pitch risks making nearby blocks hard to read. Ship 45°; name it `DriveModePitch` as a constant for post-drive-test tuning. This is explicitly a calibration item for W8.5c-follow.

**OQ-4: Distance indicator placement.**
A small element showing remaining distance to the destination (e.g., "0.8 mi"). Three candidate placements:
- Option A: Top-right of the bottom card, on the same row as the street name.
- Option B: A third chip row below the Left/Right chips.
- Option C: A floating pill above the bottom card (same zone as the Recenter button).

Recommendation: **Option A (top-right of street name row).** Keeps the card compact. One additional `Text` element on the existing row — no new row, no new floating element. Bold, large font. Localized units (`Locale.current.usesMetricSystem`). Hidden when no destination is set (no-destination Drive Mode per AC-DM.5).

## §1 — Scope

### 1.1 In scope

**A. Apple-Maps-isms (new product surface)**

1. **Auto-zoom on Drive Mode start.** When `driveModeActive` flips true, animate `MKMapView` camera to a tighter zoom (OQ-1 default: span ~0.005°). Preserve prior region for restoration on exit (OQ-2). Camera change is a one-shot event on Drive Mode entry, not a continuous update. Must not trigger the `syncDriveHeading` dead-band feedback loop (see §6, R-1).

2. **3D camera tilt during Drive Mode.** Set `camera.pitch` to ~45° (OQ-3) when Drive Mode activates. Reset to 0° when Drive Mode exits. `makeUIView` currently sets `mapView.isPitchEnabled = false` (line 247 of `MapViewRepresentable.swift`) — this disables user-gesture pitch control, not programmatic pitch. Programmatic pitch via `MKMapCamera` works regardless of `isPitchEnabled`. Engineer must verify this on device; no `Info.plist` change needed.

3. **Distance-to-destination indicator.** A `Text` element in the bottom card showing remaining distance to `destinationCoordinate`. Placement per OQ-4 (recommendation: top-right of street name row). Calculation: `CLLocation(latitude:longitude:).distance(from: CLLocation(destinationCoordinate))` on every location fix. Convert meters to miles (imperial) or kilometers (metric) per `Locale.current.usesMetricSystem`. Format: "0.8 mi" or "1.2 km" (one decimal place). Hidden when `destinationCoordinate == nil`. Does NOT include ETA or speed — those are explicitly out of scope per master spec §9 ("Speed readout, ETA, distance remaining meta row — navigation scaffolding, not parking").

**B. Bottom card chip-layout verification (diagnosed below — see note)**

4. **Bottom card chip rendering is correct — no bug.** Reading `DriveModeBottomCard.swift` lines 61–99: the view branches on `context: DrivingContext?`. When `context != nil` it renders the street name row + left/right chips (`chipView`). When `context == nil` it renders "Looking for street..." placeholder. Kevin's smoke screenshot showing the placeholder was taken at a moment when `DrivingContextService.currentContext` was nil — the GPS position was not matched to a known block. The chip layout is implemented correctly and will render when a block is matched.

   Engineer's task: add a doc-comment block to `DriveModeBottomCard.swift` above `cardContent` explaining the two-state machine — "nil context = placeholder shown when GPS is not matched to a tile segment; non-nil context = chip layout with street name and left/right severity chips." No rendering fix required. If the engineer's live testing reveals the chips never render even in good tile coverage, escalate and diagnose `DrivingContextService.update(coordinate:heading:segments:engine:date:)` as the failure point, not the card itself.

**C. Cosmetic fix**

5. **End Drive pill / ASP banner z-order.** Kevin's smoke showed the "End Drive" pill overlapping the W7 ASP banner (`Views/ASPBanner.swift`, attached via `.safeAreaInset(edge: .top)`). The pill is rendered in `ContentView`. Fix: position the End Drive pill so it does not overlap the top safe area. Two approaches — engineer's call, flag which was chosen in the commit message:
   - Approach A: Give the End Drive pill a top offset equal to the ASP banner height when the banner is active. `ASPBanner` returns a non-nil suspension when `ASPSuspensionService.suspensionState(at: .nowET) != .normal`. ContentView can guard: `if aspSuspensionService.suspensionState(at: .nowET) != .normal { topPadding += bannerHeight }`.
   - Approach B: Move the End Drive pill to the bottom of the screen (near the bottom card). Avoids the top-area collision entirely. May conflict with bottom card real estate.
   - Approach C: Wrap the End Drive pill in a `.padding(.top, geometry.safeAreaInsets.top)` or similar, computed to always clear the safe area inset including the banner. Simpler than Approach A if the banner height is just the top safe-area inset.

## §3 — Implementation Plan

Steps are ordered by dependency. Steps 1–2 are camera-layer changes. Step 3 is card UI. Step 4 is the cosmetic fix. Step 5 is tests. Each step should be a discrete commit.

**Step 1 — Auto-zoom on Drive Mode entry/exit.**

In `MapViewRepresentable.swift`, add:

```swift
// New input from ContentView (Drive Mode camera control)
var driveModeActive: Bool = false
var preDriveSpan: MKCoordinateSpan? = nil  // restored on exit
```

Add `syncDriveCamera(active:preDriveSpan:)` to the Coordinator. Called from `updateUIView` alongside `syncDriveHeading`. When `active` flips true and `lastDriveModeActive == false`:
- Store nothing (the caller — ContentView — already captured `preDriveRegion`).
- Build a new `MKMapCamera` from `mapView.camera.copy()`. Set `coordinateSpan` (or altitude derived from span) to `DriveModeCameraSpan = MKCoordinateSpan(latitudeDelta: 0.005, longitudeDelta: 0.005)`. Call `mapView.setCamera(_:animated: true)` (smooth zoom-in).

When `active` flips false and `lastDriveModeActive == true`:
- Restore to `preDriveSpan` if non-nil. Use `mapView.setRegion(preDriveRegion, animated: true)`.

Track `lastDriveModeActive: Bool` in the Coordinator (same pattern as `lastAppliedHeading`).

In `ContentView`, capture `preDriveRegion` in `.onChange(of: driveModeActive)` before calling `locationService.startDriveMode()`:

```swift
.onChange(of: driveModeActive) { _, newValue in
    if newValue {
        preDriveRegion = currentRegion  // capture before Drive Mode overrides it
        locationService.startDriveMode()
    } else {
        locationService.endDriveMode()
        drivingContext = nil
    }
}
```

**Step 2 — 3D camera tilt.**

Extend `syncDriveCamera` from Step 1 to also set `camera.pitch`:
- On Drive Mode entry: `camera.pitch = DriveModePitch` where `DriveModePitch: CGFloat = 45`.
- On Drive Mode exit: `camera.pitch = 0`.

Both pitch and zoom are applied in a single `setCamera` call — one UIKit operation, not two. This avoids a double-frame intermediate state.

Verify the dead-band does NOT interfere: `syncDriveHeading` reads `lastAppliedHeading` and fires only when heading changes > 5°. The pitch/zoom change in `syncDriveCamera` sets the camera independently (it does not go through `syncDriveHeading`). The two methods share the same `MKMapView` camera but do not share any guard state. The only risk is that `setCamera` inside `syncDriveCamera` fires `mapView(_:regionDidChangeAnimated:)`, which writes the region binding, which calls `updateUIView`. In `updateUIView`, the camera sync guard (line 314–322 of `MapViewRepresentable.swift`) already skips region sync when `driveHeading != nil`. Verify the same guard applies when pitch/zoom change fires the region callback. If needed, add a `lastAppliedDriveModeActive: Bool` guard so `syncDriveCamera` is idempotent (only runs on the first frame where `active` changed, not on every subsequent `updateUIView` call).

**Step 3 — Distance-to-destination indicator.**

In `DriveModeBottomCard.swift`:
- Add `let destinationDistance: Double?` to the struct inputs (distance in meters, pre-computed by ContentView).
- Add `let usesMetric: Bool` (pass `Locale.current.usesMetricSystem` from ContentView, or compute inside the card — engineer's call).
- In the street name row `HStack`, when `destinationDistance != nil`, add a `Text` trailing the street name and preceding the mute button. Example: `"0.8 mi"` or `"1.2 km"`. Format: `String(format: "%.1f", value)` + unit string. When nil, the text element is hidden (`.hidden()` or conditional).

In `ContentView`, compute the distance on each `locationService.locationUpdateCount` change while `driveModeActive`:
```swift
if let dest = destinationCoordinate, let loc = locationService.userLocation {
    driveModeDistanceMeters = loc.distance(from: CLLocation(
        latitude: dest.latitude, longitude: dest.longitude
    ))
} else {
    driveModeDistanceMeters = nil
}
```

Pass `driveModeDistanceMeters` to `DriveModeBottomCard`.

Also add the doc-comment state machine explanation to `DriveModeBottomCard.swift` above `cardContent`:
```
/// Two-state layout:
///   - context == nil: GPS not matched to a tile segment → "Looking for street..." placeholder.
///     Shown at Drive Mode start before DrivingContextService has a fix, or when driving
///     in a gap between tile coverage areas.
///   - context != nil: GPS matched to a block → street name + left/right severity chips.
///     Chips color-code parking severity per the W4.5 palette.
```

**Step 4 — End Drive pill / ASP banner z-order.**

Read the current End Drive pill placement in `ContentView`. Identify which overlay modifier positions it. Apply the chosen fix (engineer selects Approach A, B, or C from §1.1 item C; documents in commit message). Verify in simulator: launch with an ASP suspension date active (or mock one via `ASPSuspensionService`), enter Drive Mode, confirm the End Drive pill and ASP banner do not overlap.

## §6 — Risks / Known Gotchas

**R-1: Camera pitch + zoom vs. heading-up dead-band (load-bearing).**
`syncDriveHeading` tracks `lastAppliedHeading` to prevent a feedback loop: camera set → `regionDidChangeAnimated` fires → `updateUIView` runs → camera set again → loop. The new `syncDriveCamera` adds a second camera mutation path. Risk: `syncDriveCamera`'s `setCamera` call fires `regionDidChangeAnimated`, which triggers `updateUIView`, which calls `syncDriveCamera` again. Without a guard, this creates a second tight loop. Mitigation: track `lastDriveModeActive: Bool` in the Coordinator (parallel to `lastAppliedHeading`). `syncDriveCamera` is a no-op when `driveModeActive == lastDriveModeActive`. This ensures the zoom+tilt fires exactly once on entry and once on exit — not on every subsequent `updateUIView`. The engineer must confirm this guard is in place and working in the first commit.

**R-2: `isPitchEnabled = false` and programmatic pitch.**
`makeUIView` sets `mapView.isPitchEnabled = false` (line 247 of `MapViewRepresentable.swift`). This disables the two-finger-drag gesture for pitch — it does not block programmatic `MKMapCamera.pitch` assignment. Apple's documentation confirms: `isPitchEnabled` controls user gesture only. However, behavior may differ on iOS 26.x. Engineer should verify in simulator that `setCamera` with a non-zero pitch actually tilts the view when `isPitchEnabled = false`. If it does not, `isPitchEnabled` must be set to `true` during Drive Mode and `false` when Drive Mode exits (add to `syncDriveCamera`).

**R-3: Camera animation and follow-mode.**
The auto-zoom fires a `setCamera(_:animated: true)` call. If follow-mode is active at the same moment (ContentView is also calling `mapView.setRegion` to recenter on the user), two simultaneous camera animations may conflict. The engineer should ensure the zoom animation fires before or instead of the follow-mode recenter on the same tick. Simplest fix: skip the follow-mode recenter for the one frame where `syncDriveCamera` fired the entry animation (use the `lastDriveModeActive` flag — if it just flipped, the recenter is redundant).

**R-4: Distance calculation on each location fix — performance.**
`CLLocation.distance(from:)` is O(1) (Haversine calculation). No performance concern. However, `driveModeDistanceMeters` must only be computed when `driveModeActive == true && destinationCoordinate != nil`. Do not run the calculation when Drive Mode is inactive.

**R-5: ASP banner height for z-order fix.**
The ASP banner height is not a fixed constant — it depends on Dynamic Type and the number of lines of suspension text. Approach A (adding a fixed offset) may not work at all text sizes. Approach C (respecting the safe area inset, which already includes the banner via `.safeAreaInset(edge: .top)`) is more robust. Engineer should verify which approach actually works at multiple Dynamic Type sizes.
