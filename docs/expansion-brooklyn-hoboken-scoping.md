# Scoping memo: does WePark extend to Brooklyn and Hoboken?

**Status:** scoping only. Nothing built, no data pulled beyond count queries to verify claims. Written because Kevin has inbound users with cars in Brooklyn and Hoboken and wants a real answer, not a guess.

## Bottom line

- **Brooklyn: feasible-with-work.** Every data source the pipeline already ingests — NYC DOT signs, DOT centerlines (CSCL), the ASP suspension calendar — is citywide, not Manhattan-only. The pipeline just throws Brooklyn's rows away with a `borough=Manhattan` filter today. This is a scale-and-validation project, not a new-data-source project. Rough sizing below suggests a bigger job than "flip a filter" because Brooklyn has more signs and more street miles than Manhattan, and the street-name/geometry-join logic that took multiple rounds of debugging for Manhattan will need to survive Brooklyn's grid quirks (angled streets, more one-way pairs, diagonal avenues) on its own.
- **Hoboken: not currently feasible, in the "get a real regulation feed" sense.** It's a different state with no equivalent to NYC's DOT sign inventory. Street geometry is fine (OpenStreetMap covers it well, NJDOT has a centerline layer). But there is no machine-readable dataset of individual curb regulations, no NYC-style ASP program, and Hoboken's core parking model — heavy resident-permit zoning, roughly 2x as many permits issued as spaces — doesn't map cleanly onto the app's existing legality categories at all. This would need real field/manual curation to bootstrap, not a pipeline change.

Everything below is the evidence for those two verdicts.

## What "the Manhattan implementation" actually is (read from the pipeline itself)

The tile pipeline has three build scripts and one core preprocessor:

| Script | What it does | Manhattan hardcode |
|---|---|---|
| `build/preprocess.js` | Pulls parking-sign records from two NYC Socrata datasets, classifies them into rule categories, joins them to OSM street geometry, computes curb offsets, and writes the tile grid. | `SP_BOUNDS` (State Plane coordinate box) filters signs to Manhattan; `GRID` (`latMin/latMax/lngMin/lngMax`, 80×50 rows/cols) is a Manhattan-only bounding box baked into every tile filename and the `tiles/index.json` header; both Socrata fetch URLs append `&borough=Manhattan` directly in the query string (`build/preprocess.js:1405`, `:1456`) |
| `scripts/build-oneway-data.js` | Pulls one-way/two-way direction from NYC DOT's CSCL centerline dataset (`inkn-q76z`), writes `osm_oneway.json`. | `WHERE = "boroughcode='1' AND ..."` — hardcoded to Manhattan's borough code |
| `scripts/build-street-widths.js` | Pulls paved street width from the same CSCL dataset, writes `street_widths.json`, used for curb-offset accuracy. | Same `boroughcode='1'` filter, copy-pasted from the oneway script |
| `scripts/coverage-report.js` | QA tool: reports what % of street-miles have sign coverage, broken out by neighborhood. | `HOODS` is a hand-drawn list of ~20 Manhattan neighborhood bounding boxes (Tribeca, SoHo, Harlem, etc.) — this tool would need a fresh neighborhood list for any new borough/city, it's not load-bearing for the actual data pipeline |

Beyond the scripts, two more Manhattan-only assumptions live in committed data/config, not code:

- **`NYC_TO_OSM` alias table** inside `preprocess.js` (~50 hand-verified street-name aliases like `LENOX AVENUE` → `Malcolm X Boulevard`) exists because NYC's sign dataset and OSM's street names disagree in Manhattan-specific ways. Brooklyn will have its own set of these (different street renamings, different co-name conventions) that nobody has audited yet.
- **iOS `AppConstants.manhattanCoverageBounds`** (`ios/WePark/WePark/Services/Constants.swift`) is the *same* lat/lng box as the tile grid, used to decide whether to auto-center the map on launch and how far the user can zoom out. Its own doc comment explicitly says: *"Excludes: Hoboken (lon -74.032 < lngMin) ... Northwest Brooklyn (DUMBO/Brooklyn Heights) falls inside — auto-centering there is acceptable (honest basemap; no overlays at that location)."* In other words: the code already knows Hoboken is outside its box and Brooklyn is partially, coincidentally, inside it with zero real data.

**What is NOT hardcoded:** the `zones` table (Community 2.0 / Regulars) is a plain Postgres table — `id, name, description, lat_min, lat_max, lng_min, lng_max` — with an RLS policy of `select using (true)`. Zones are fetched at app launch (S14, migration `06-manhattan-zones.sql`), not compiled in. Adding a Brooklyn or Hoboken zone is a data insert, not a code change. See the Community 2.0 note below.

**Effort to generalize, rough take:** the grid bounds, State Plane filter, and `borough=Manhattan` / `boroughcode='1'` strings are mechanical — swap constants, add a borough parameter, done in an afternoon each. The real cost is everything downstream of that swap: the street-name alias table, the wide-street/curb-offset heuristics (`WIDE_AVENUE_RE`, `WIDE_NS_NAMES`, `WIDE_CROSSTOWN_NAMES` — all hand-curated Manhattan street lists), and the multi-round intersection/geometry bugs the QA docs in `docs/qa/` show this pipeline has already been through once for Manhattan alone (FT-14 join-drop, FT-19 setback tapering, TF2-19 Houston/Bowery investigation). Those bugs weren't Manhattan-specific in cause — they were "real-world street geometry is messy" bugs — which means Brooklyn's grid (diagonal streets, more divided/median avenues, different intersection density) should be expected to surface its own version of the same bug class, not a clean rerun.

## Semantic gaps and what they mean for the 5-color legality palette

The app's curb-color model — `Services/ParkingColors.swift`, described in the reconciliation spec as "sacred, untouched" — maps a fixed `Category` enum (ASP variants, `METERED`, `TRUCK_LOADING`, `NO_PARKING`/`NO_STANDING`, `SPECIAL`, `FREE`/`UNKNOWN`) onto five colors. That model was built entirely around NYC's regulatory vocabulary: alternate-side sweeping, metered paid parking, standing/loading restrictions.

- **Brooklyn:** same regulatory vocabulary, same sign taxonomy, same `SOCRATA_MAIN` / `SOCRATA_ASP` datasets. The classification logic in `preprocess.js` (`classifySign`, `parseSchedule`) should port with zero changes to the category model itself. The risk is entirely in geometry/name-join accuracy, not semantics.
- **Hoboken:** the semantics don't fit. Hoboken's defining parking fact is that most legal curb space is **resident-permit-only**, and the city issues roughly twice as many permits as it has spaces — meaning "legal to park here" is conditional on an attribute the app has no concept of (does this specific car hold a Hoboken RPP sticker for this specific zone?), not on time-of-day/day-of-week the way every existing category is. There's also no ASP-equivalent program, and the "street cleaning" restriction there is a simpler once-a-week-per-side model, not NYC's twice-a-week broom pattern. Representing "permit zone, non-permit-holders limited to 4 hours" honestly would require either a genuinely new category (which the reconciliation spec's "sacred, untouched" language suggests is a real design conversation, not a data change) or overloading an existing color in a way that would mislead a non-permit-holding driver. That's a product decision, not an engineering one — flagged below.

## Community 2.0 / Regulars implication (one paragraph)

Zones are Manhattan-only today because the 41 rows in `06-manhattan-zones.sql` are Manhattan rows, not because the schema or the fetch-at-launch architecture (S14) restricts them to Manhattan. The `zones` table has no borough column, no bounding-box constraint tying it to any city, and RLS already allows public read of every row. A Brooklyn or Hoboken zone is a straightforward data insert once someone decides on names/boundaries — the same migration pattern as `06-manhattan-zones.sql`. This is genuinely low-risk and low-effort *relative to the tile-data problem*; it should not be read as evidence that the harder problem (getting real curb-regulation data for a new area) is also easy.

## Rough session estimates — IF Kevin greenlights either

**These are estimates for scoping purposes, not a plan, not a commitment, and not sequenced.** They assume the same session-based cadence visible in `HANDOFF.md`'s history for Manhattan's own build-out (which took many iterative sessions to reach today's tile quality).

- **Brooklyn:** roughly 4-8 sessions. Rough breakdown: parameterize the borough filter and grid bounds (~1 session) → pull and inspect real Brooklyn OSM/CSCL/sign data side by side to find the name-join failures Manhattan already hit once (~2-3 sessions, this is where the real cost lives) → build and QA-pass the tile regen, likely 2+ rounds given Manhattan's own regen history → decide app bundle size posture (see sizing note below) → ship a Brooklyn coverage report and let Kevin field-test it the way he field-tested Manhattan before any flag flip.
- **Hoboken:** not sessionable yet in the same sense, because there's no data-source problem to solve with code — there's a data-*existence* problem. Before any engineering session makes sense, someone (Kevin, or a research pass) needs to determine whether a real regulation feed exists that this scoping pass didn't find (city may have non-public GIS layers, or a vendor feed), or whether the honest plan is manual curation of a small number of blocks as a proof of concept. If manual curation is the path, that's a content/ops effort, not a backend session — rough guess 1-2 sessions of engineering to build a manual-entry schema/tile format for a handful of hand-curated blocks, but the bulk of the work would be someone walking blocks and reading signs, which isn't a Claude-agent task.

## Rough sizing note (Brooklyn)

Current Manhattan tile set, measured directly from this worktree: **1,071 tiles, 31 MB, 44,280 segments** (`tiles/index.json`, generated 2026-08-18). Brooklyn's CSCL centerline-segment count is ~2x Manhattan's (27,678 vs 14,106) and its sign volume is 2x-4.6x Manhattan's depending on dataset. A same-density Brooklyn tile set would plausibly land somewhere in the 2-3x range of Manhattan's current footprint — call it a rough 60-90 MB addition to whatever bundles tiles (the iOS Resources folder currently mirrors `tiles/` 1:1). That's a real app-bundle-size conversation, not a blocker, but worth sizing precisely (not estimating) before committing, and it's exactly the kind of number a real pull would nail down in the first session rather than guessing further here.

## Open product questions only Kevin can answer

1. **Does Hoboken's permit model even fit what WePark promises?** The app's core promise is "here's where you can legally park right now." If most of Hoboken's curb space is permit-conditional in a way the app can't verify (does this user's car have a sticker?), does showing a color at all risk being actively misleading rather than just incomplete?
2. If Hoboken is worth pursuing, is manual curation of a small number of blocks (Kevin's own neighborhood, say) an acceptable first step, or is "no real feed exists" a hard stop until a better source turns up?
3. For Brooklyn: is this driven by actual demand (how many of the inbound users are Brooklyn vs. Hoboken), or worth doing preemptively? The effort estimate above assumes a real build; if it's a handful of users, a much smaller pilot (e.g., one Brooklyn neighborhood, tile-count capped) might be the more honest first move.
4. Should Staten Island's near-absence of ASP signage (5 rows citywide) change how "Brooklyn" is scoped — i.e., is this really "the other four boroughs" as a long-term intent, or specifically Brooklyn because that's where the demand is?
5. If a new legality category is needed for permit-only curbs, who owns that design call — is that a `@designer` conversation before any Hoboken engineering starts, given the "sacred, untouched" language already on the palette?
