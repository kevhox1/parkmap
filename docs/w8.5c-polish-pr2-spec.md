### In (four features — or three if OQ-1 resolves as split)

1. **Auto-zoom on Drive Mode entry.** Animate camera to a tighter span on Drive Mode entry; restore the prior `centerCoordinateDistance` on exit. Target span: `~0.005°` latitude (approximately 1–2 Manhattan blocks visible). The `altitudeForSpan(_:)` helper is already stubbed in `MapViewRepresentable.swift` line ~710 with a `// [used by PR-2]` comment per the PR-3 spec — engineer uses that as the implementation entry point.

2. **Pitch re-evaluation at the tighter zoom.** At the W8.5c-polish zoom level (wider, span ~0.04°), MapKit clamped pitch at ~35°, so PR-3 shipped 30°. At the PR-2 tighter span (~0.005°), MapKit may allow steeper pitch without clamping. Engineer measures empirically (OQ-2 lean: Option B instrument-first) and ships the highest pitch that renders faithfully — likely 45° or 60°. The constant `driveModePitch` in `MapViewRepresentable.swift:193` is updated from 30 to the measured value. If 30° is still the ceiling at the tighter zoom, document that finding and keep 30°.

Capture the prior configuration at entry (`preDriveMapConfiguration`) and restore on exit. Rationale: a quieter base map makes the red/green/yellow parking polylines stand out more for at-a-glance driver legibility. `MKMultiPolyline` overlays draw above the base map regardless of `preferredConfiguration` — no overlay rendering regression expected.

## §3 — Implementation Plan

This section is the architectural core. Read before writing any code.

### 3.1 The pattern (from PR-3) — reuse, do not parallel

PR-3 introduced:
- `CoordinatorActions` reference-type box in `MapViewRepresentable` (line ~223).
- `@State private var coordinatorActions = MapViewRepresentable.CoordinatorActions()` in `ContentView`.
- `.onChange(of: driveModeActive)` → `handleDriveCameraChange(_:)` in `ContentView` that calls `coordinatorActions.applyDrivePitch?`.
- `shouldSyncRegionToBinding(driveModeActive:)` pure func gating `setRegion` in `updateUIView`.

PR-2 extends this pattern. The engineer does NOT add a new `.onChange(of: driveModeActive)` block. Everything fires from the existing `handleDriveCameraChange(_:)` function.

### 3.2 Extending `CoordinatorActions`

Add four new optional closures to the `CoordinatorActions` class alongside the existing `applyDrivePitch` / `captureCurrentPitch`:

```
// In CoordinatorActions:
var captureCurrentDistance: (() -> CLLocationDistance)?
var applyDriveZoom: ((Bool, CLLocationDistance) -> Void)?
var captureCurrentMapConfiguration: (() -> MKMapConfiguration?)?
var applyDriveMapStyle: ((Bool, MKMapConfiguration?) -> Void)?
```

Wire them in `makeUIView` using the same `[weak coordinator]` capture pattern as `applyDrivePitch`.

### 3.3 Extending `handleDriveCameraChange(_:)` in `ContentView`

The current implementation captures `preDrivePitch` and calls `applyDrivePitch`. Extend it to also capture and apply zoom and map style:

```
// Conceptual extension — not production code:
private func handleDriveCameraChange(_ active: Bool) {
    if active {
        preDrivePitch = coordinatorActions.captureCurrentPitch?() ?? 0
        preDriveDistance = coordinatorActions.captureCurrentDistance?() ?? 0
        preDriveMapConfiguration = coordinatorActions.captureCurrentMapConfiguration?()
    }
    coordinatorActions.applyDrivePitch?(active, preDrivePitch)
    coordinatorActions.applyDriveZoom?(active, preDriveDistance)
    coordinatorActions.applyDriveMapStyle?(active, preDriveMapConfiguration)
}
```

All three camera/style mutations fire from the same `.onChange`-driven call. They must be ordered: zoom fires after pitch (same `setCamera` call is preferred — see §3.4). Style fires independently via `preferredConfiguration` (not a `setCamera` call).

### 3.4 Single `setCamera` for pitch + zoom together

PR-3's `applyDriveCameraPitch` currently sets only pitch and leaves a `// [deferred to PR-2]` comment at the altitude line (line ~710 in `MapViewRepresentable.swift`). PR-2 fills that stub.

The coordinator method signature expands to:

```
// Conceptual — not production code:
func applyDriveCameraState(
    active: Bool,
    priorPitch: CGFloat,
    priorDistance: CLLocationDistance,
    on mapView: MKMapView
)
```

On entry: `mapView.camera.copy()` → set `pitch` to `targetPitch(...)` AND `centerCoordinateDistance` to `targetDistance(...)` → `setCamera(camera, animated: true)`. Single animated transition, ~0.3s. On exit: restore both `priorPitch` and `priorDistance` in a single `setCamera` call.

The engineer may keep `applyDriveCameraPitch` as-is and add `applyDriveZoom` as a second coordinator method if the seam is cleaner, but the single-call approach is preferred to avoid two sequential `setCamera` calls (each fires `regionDidChangeAnimated`).

### 3.5 `altitudeForSpan(_:)` static helper

PR-3 left a `// [used by PR-2]` stub for this function. Implement it:

```
// Conceptual — not production code:
static func altitudeForSpan(_ latitudeDelta: CLLocationDegrees) -> CLLocationDistance {
    // Half the N-S visible distance in meters, divided by tan(camera half-angle).
    // For a standard iPhone viewport at MapKit's default ~60° vertical FOV:
    let metersPerDegree: CLLocationDistance = 111_000
    let halfHeightMeters = (latitudeDelta / 2) * metersPerDegree
    return halfHeightMeters / tan(15 * .pi / 180)
}
```

This approximation matches the formula from the reverted PR. Mark it `static` so pure-function tests can call it without a coordinator instance.

Corresponding pure-function decision:

```
static func targetSpan(forDriveModeActive active: Bool, priorSpan: CLLocationDegrees) -> CLLocationDegrees {
    active ? driveModeCameraSpan : priorSpan
}

static let driveModeCameraSpan: CLLocationDegrees = 0.005
```

`targetDistance` derives from `altitudeForSpan(targetSpan(...))`. The two-step indirection keeps each function unit-testable independently.

### 3.6 Map style swap

The coordinator closure for `applyDriveMapStyle`:

```
// Conceptual — not production code:
coordinatorActions.applyDriveMapStyle = { [weak coordinator] active, priorConfig in
    guard let c = coordinator, let mapView = c.mapView else { return }
    if active {
        mapView.preferredConfiguration = MKStandardMapConfiguration(emphasisStyle: .muted)
    } else {
        mapView.preferredConfiguration = priorConfig ?? MKStandardMapConfiguration()
    }
}
```

`captureCurrentMapConfiguration` simply reads `mapView.preferredConfiguration` at entry.

The fallback on exit (`?? MKStandardMapConfiguration()`) handles the edge case where `preDriveMapConfiguration` is nil (e.g., first Drive Mode entry ever on a fresh app install before any configuration is explicitly set — MapKit returns the system default `MKStandardMapConfiguration()` without `.muted`).

Note: `preferredConfiguration` is not a `setCamera` call, does not fire `regionDidChangeAnimated`, and cannot cause the feedback loop. It fires independently from the camera mutations in §3.4.

### 3.7 Directional user puck (OQ-1 bundle path only)

If OQ-1 resolves as bundle with mechanism (b), add to the `mapView(_:viewFor:)` delegate at `MapViewRepresentable.swift:746`, above the existing `guard annotation is CarPinAnnotation` line:

```
// Conceptual — not production code:
if annotation is MKUserLocation && parent.driveModeActive {
    let view = MKAnnotationView(annotation: annotation, reuseIdentifier: "driveUserPuck")
    view.image = UIImage(systemName: "location.north.fill")?
        .withTintColor(.systemBlue, renderingMode: .alwaysOriginal)
    // Rotate image by driveHeading in degrees. MKAnnotationView does not auto-rotate.
    // Apply rotation in regionDidChangeAnimated or via a separate heading observer.
    view.transform = CGAffineTransform(rotationAngle: (parent.driveHeading ?? 0) * .pi / 180)
    return view
}
```

Key constraints:
- **Rotation update mechanism:** `mapView(_:viewFor:)` is called once when the annotation is added. To rotate the puck as heading changes, the coordinator must also update the transform in a heading-change path. The least-invasive approach: in `syncDriveHeading`, after the camera `setCamera` call, also update the user location annotation view's transform by calling `mapView.view(for: mapView.userLocation)?.transform = ...`. This keeps puck rotation in sync with camera rotation.
- **No conflict with `syncDriveHeading`:** mechanism (b) only rotates the annotation view image; it does NOT set `userTrackingMode`. `syncDriveHeading` continues to own camera rotation. The two are orthogonal.
- **Exit:** When `driveModeActive` becomes false, `mapView(_:viewFor:)` returning `nil` for `MKUserLocation` restores the default blue dot. Trigger a view refresh by briefly removing and re-adding the user location annotation — or by calling `mapView.showsUserLocation = false` then `= true` — so MapKit re-queries the delegate for a fresh view. Document the chosen mechanism in the PR.

### 3.8 Transition guard — `shouldSyncRegionToBinding` preservation

PR-3's `shouldSyncRegionToBinding(driveModeActive:) -> Bool` guard (returns `!driveModeActive`) gates `setRegion` in `updateUIView`. The auto-zoom `setCamera` in PR-2 will fire `regionDidChangeAnimated`, which triggers `updateUIView`, which checks this guard. The guard returns `false` (Drive Mode active → skip `setRegion`) → no feedback loop. This is the same coexistence behavior verified for the pitch `setCamera` in PR-3.

The engineer must verify that the zoom `setCamera` + style `preferredConfiguration` change does NOT cause a `setRegion` call on any code path in `updateUIView`. If the `syncDriveRegion` path is reached after the zoom `setCamera`, it must use `setCamera` (not `setRegion`) and must preserve pitch — no change to the existing `syncDriveRegion` implementation expected.

### 3.9 What is NOT acceptable

- Calling `mapView.setCamera(...)` or `mapView.setRegion(...)` synchronously inside `updateUIView` on any code path introduced by this PR. (Exception: the existing `syncDriveRegion` call inside `updateUIView` is acceptable because it already uses `setCamera` and is gated on `driveModeActive`.)
- Any use of `mapView.mapType` (deprecated API).
- Any `userTrackingMode` change (conflict with `syncDriveHeading`).
- Any headless-window guard, `UIWindowScene` synthesis, or `RunLoop.main.run(until:)` in production code.
- A second `.onChange(of: driveModeActive)` block in `ContentView` for these features. Extend `handleDriveCameraChange`.

## §6 — Risks

### R-1 (primary): Re-breaking the overlay chain (the #31 regression class)

Any synchronous UIKit mutation inside `updateUIView` is a live regression risk. PR-2 adds two new mutation paths — zoom (`setCamera`) and style (`preferredConfiguration`). Both must fire from `handleDriveCameraChange` in `ContentView`, not from `updateUIView`. The live-UI smoke (AC-9) is the runtime gate. Screenshots before and after Drive Mode entry confirm the toolbar / ASP banner / pill layer is intact.

### R-2: Double `setCamera` → double `regionDidChangeAnimated`

If zoom and pitch fire as two separate `setCamera` calls (rather than one combined call per §3.4), two `regionDidChangeAnimated` events fire in sequence. Each triggers `updateUIView` → `syncDriveHeading`. With the `lastAppliedHeading` dead-band in place, the second heading-check fires with the same heading → guard returns early → no loop. Risk is low but the engineer should confirm this explicitly. Prefer the single-call approach to eliminate the risk entirely.

### R-3: Feedback loop via `preferredConfiguration`

Setting `mapView.preferredConfiguration` does NOT fire `regionDidChangeAnimated`. This is a separate MapKit path. No feedback loop risk from the style swap.

### R-4: `userTrackingMode` conflict (puck mechanism)

If OQ-1 resolves as bundle and the engineer is tempted to use mechanism (a) because it is simpler, the heading-conflict is load-bearing. `syncDriveHeading` (`MapViewRepresentable.swift:648`) sets camera heading manually via `setCamera`. `.followWithHeading` / `.followWithCourse` also sets camera heading via the system's tracking mode. The two will fight: each `setCamera` from `syncDriveHeading` will reset the tracking mode to `.none`, and the system's subsequent heading update will fire `regionDidChangeAnimated` again. This is an undiagnosed feedback loop risk. The spec prescribes mechanism (b) exclusively for PR-2. Any investigation of mechanism (a) is PR-2.5 scope.

### R-5: Map style restore edge case

On Drive Mode exit, the app restores `preDriveMapConfiguration` captured at entry. If a future version of WePark allows the user to toggle the map type (satellite, hybrid, etc.) via a settings UI, a user who changed the map type during Drive Mode would lose their change on exit. Today (as of PR-3), map type is not user-configurable in WePark's UI — there is no map type picker in `SettingsView`. The capture-at-entry / restore-on-exit pattern is correct for the current product and matches the PR-3 pitch restore pattern. If map type becomes user-configurable in a future release, this restore will need revisiting.

### R-6: `altitudeForSpan` approximation divergence

The `halfHeightMeters / tan(15°)` formula assumes a ~60° vertical FOV and a flat-Earth approximation. At Manhattan latitudes and small spans (~0.005°), this is accurate to within ~5% — acceptable for a Drive Mode zoom that is a UX heuristic, not a navigation-critical value. If the sim renders at a span materially different from ~0.005°, the engineer measures the actual rendered span and adjusts `driveModeCameraSpan` accordingly. Document the measured value in the PR.

### R-7: Polyline visibility at `.mutedStandard`

Parking polylines (`MKMultiPolyline` overlays added via `addOverlay(_:level: .aboveRoads)`) draw above the MapKit base layer regardless of `preferredConfiguration`. The muted style affects street colors and building colors on the base map — it does not affect overlay rendering. The `polylineHideSpanThreshold = 0.04` guard in `ContentView.swift:297` will still show polylines at the PR-2 drive-mode span (~0.005° << 0.04°), so parking overlays are visible throughout Drive Mode. Confirm in Kevin's smoke that the contrast is improved, not degraded.

### R-8: puck view refresh on exit

Restoring the default blue dot after Drive Mode exit requires MapKit to re-query the delegate for `MKUserLocation`. If `showsUserLocation` is already `true`, MapKit may not call `mapView(_:viewFor:)` again. The engineer must trigger a refresh — likely by toggling `showsUserLocation = false` then `= true` in the exit path, or by calling `mapView.removeAnnotation(mapView.userLocation)` and re-adding it. Either must be done from `ContentView`'s `.onChange(of: driveModeActive)` handler (via a new `CoordinatorActions` closure), not from `updateUIView`. Document the chosen mechanism.
