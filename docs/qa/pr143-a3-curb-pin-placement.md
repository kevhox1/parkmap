### 🟡 Significant

- **#1: Pin coordinate is estimated from `region`; wrong on a rotated or pitched map (orchestrator ruling: fix via an A2 `placementPinCoordinate()` seam in the fix round).**
  - Where: `ContentView.estimatedCurbPlacementPin()` / `CurbPlacementPolicy.estimatedPinCoordinate`; consumers: `updateCurbPlacementNearestCurb()` (chip probe), `commitCurbPlacementPark` (no-curb save), `openCurbPlacementReport` (no-curb Next). Those three are the ONLY places that compute a pin from `region`; the snapped paths use `result.snappedCoordinate` and are unaffected. Entry seeds use `userLocation ?? region.center` as a seed only (fine).
  - What: the estimate is `region.center` plus `0.1 x latitudeDelta` due north. The tip is 0.1 x visible-height up the SCREEN axis. `mapView.isRotateEnabled` and `isPitchEnabled` are both `true` (`MapViewRepresentable.swift:1247-1248`) and A2 does not lock either (pr140 pass-1 #9), so the user can twist the map at will. My arithmetic at entry zoom (110 m wide, ~238 m visible height, tip offset 23.8 m, assuming `mapView.region` returns the enclosing box of the rotated rect): error ~18 m at 45 deg, ~26 m at 90 deg, ~48 m at 180 deg; roughly half that at the zoom floor. Pitch: `region` of a tilted camera is not the camera centre at all, so the error can be larger; I did not quantify it. It may also be skewed if MapKit folds `layoutMargins` into `region` (unverified).
  - Damage: (i) "Save car here (no parking info)" persists the car up to ~50 m from the reticle the user was looking at. This is the exact state outside-coverage users (Brooklyn/NJ) depend on, and there is no curb data to cross-check it. (ii) Pill "Next" in the no-curb state writes a community report at the wrong coordinate (`segment: nil`, so nothing corrects it). (iii) The nearest-curb chip's distance/bearing text is computed from the wrong origin; tapping it still lands the curb under the tip (absolute coordinate), so the chip is mislabelled rather than broken.
  - Expected: the coordinate the user sees under the needle is the coordinate that is saved/reported.
  - Fix: add `placementPinCoordinate()` to A2's marked `CoordinatorActions` block (the controller already computes `mapView.convert(tipPoint, toCoordinateFrom:)`), swap the three call sites, delete `estimatedPinCoordinate` and its test. Also resolve it at commit time, not from a settled value (see #5 on staleness).
  - Owner: `@ios-engineer` (A2 seam + A3 call sites).

- **#2: "Loading curbs…" never resolves when the viewport has no tiles (Brooklyn/NJ/Cupertino): Park/Next stay disabled forever.**
  - Where: `CurbPlacementCardModel.make` (`tilesLoaded: !tileLoader.segments.isEmpty` -> `isLoading = outcome == nil || (noCurb && (!tilesLoaded || indexRefreshing))`); `ContentView.curbPlacementOverlay`.
  - What: `tileLoader.segments` is only the tiles for the current viewport. Tiles are bundled and decode locally, so "empty" means "no data here", not "still loading". With empty segments the index resolves `.noCurbInRange`, the model reads it as loading, the primary is disabled with a spinner, and the only exit is Cancel. The spec's own A.3 text ("if `tileLoader.segments` is empty ... show Loading") conflicts with the same paragraph's "only way Brooklyn/outside-coverage users can mark a car" and with A11 ("never dead-end"); the builder followed the first and broke the second. Legacy long-press and the legacy report pill both worked here (`segment: nil` / "Save car"). The pill additionally seeds the camera at a GPS fix with no `isInManhattanCoverage` guard (the Recenter button has one precisely so "no data AND can't get back" is unreachable), so a pill tap from Brooklyn flies the camera there, then sticks on Loading. Flag-on only; ships dark, but it is a flip blocker and an App-Review-in-Cupertino hazard.
  - Expected: Loading is bounded: only while an index build is in flight or until the first outcome after the first build completes (plus, at most, a short settle window after new tiles). Empty-segments after a completed build is "No curb here" with Save/Next enabled.
  - Repro: Mac sim, set location to Brooklyn or Cupertino (or pan out of the tile footprint), flag on, tap Report pill or long-press: spinner, primary disabled indefinitely.
  - Owner: `@ios-engineer`.

- **#3: Card height is not constant: the nearest-curb row is additive, and the subtitle is not reserved (design Finding 8; pr140 P2-2 mechanism).**
  - Where: `CurbPlacementOverlay.card(...)`: `nearestCurbRow` is a separate row AFTER the text block, while `statusSlot` already reserves a 44 pt clear slot in the no-curb state; the design puts the chip IN that slot ("same outer height, rows swapped", design 3.3). `Text(model.subtitle ?? " ").lineLimit(2)` has no `reservesSpace`.
  - What: (a) in the no-curb state the card grows by ~52 pt (44 + 4 + gaps) when a nearest curb is found and shrinks when none; (b) a cross-street line that wraps to two lines (long names) adds ~17 pt; (c) `pinned` in the cap math does not include the chip row, so on an SE-class phone (cap 270 pt) a no-curb + chip card is ~320 pt and its top (~y 345) sits ~78 pt below the tip, inside the ghost's reach (~149 pt at the floor zoom), defeating the "card never covers the ghost" cap. Each height change drives `onCardHeightChange` -> `setPlacementBottomInset` (margin write) while the user may still be panning, which is the exact interaction pr140 flagged as an unverified re-centring hazard.
  - Expected: one stable height per intent; chip replaces the clear status slot; subtitle `lineLimit(2, reservesSpace: true)` or the card cap absorbs it.
  - Owner: `@ios-engineer`.

- **#4: Index-swap refresh is a single unverified main-queue hop on the COMMON entry path, with no retry; failure leaves the primary disabled until the first pan.**
  - Where: `startCurbPlacementIndexBuild` / `scheduleCurbPlacementRefresh`; A2 `refresh()` and `Coordinator.beginPlacement` hook `index: { parent.placementIndex }`.
  - What: the index is nil at `beginPlacement` on EVERY entry (it is built lazily in the same `.onChange`), so A2's seed resolve returns nil, no outcome fires, and the card shows Loading (`outcome == nil`, primary disabled, pill "Next" disabled) until the swap is rendered and `refreshPlacement()` re-resolves. That is the normal path, not a race corner. `refresh()` also early-returns while `entryInProgress` (the animated entry), relying on `finishEntry` to resolve afterwards, and it reads the index through the representable's `parent`, which only updates in `updateUIView`. The `DispatchQueue.main.async` hop out of `.onChange(of: curbPlacementIndexVersion)` is a reasonable guess that `updateUIView` has run, but it is not guaranteed; if it hasn't, the refresh resolves against nil, emits nothing, and nothing retries (no further outcome until the user moves the map, which the Loading card gives them no reason to do).
  - Mitigations worth taking in the fix round (cheap): cache the built index across sessions and invalidate on `segments.count` change so it is non-nil at `beginPlacement` (also removes a Loading flash and a per-entry rebuild); and/or retry `refreshPlacement()` once more ~0.25 s later, or give the controller's `index` hook a direct read of ContentView state instead of going through `updateUIView`. Keep the Mac "index race" smoke.
  - Owner: `@ios-engineer`.
