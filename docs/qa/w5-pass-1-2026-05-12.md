## Summary

The W5 implementation is structurally sound: all major user flows (long-press, "Park here" button, ParkConfirmView, pin annotation, ParkedCarDetailView, "I left" clear, persistence, silent replace, W6/W7.5 hooks) are implemented and the 45-test baseline passes with zero failures. Two issues prevent a clean-ship verdict. First, `ParkPinService.save()` calls `pinDropped.send(car)` unconditionally outside the encode/write do-catch block — if encoding fails, W7.5 gets a "pin dropped" event for a car that was never actually saved (logic inversion). Second, after a user taps a "Wrong street?" alternative in `ParkConfirmView`, the alternatives list is not updated to exclude the newly-selected block, so the same block appears in both the "detected" header and the alternatives list simultaneously. Neither issue is a crash or data-loss path in practice, but both are observable by W7.5 subscribers and by users at corners. No W5-specific unit tests were added to the suite.

## Findings

### Blocking

None.

### Significant

**#1: `pinDropped` hook fires unconditionally on encode failure**

- Where: `ParkPinService.swift`, `save()` function, line 82 (`pinDropped.send(car)`)
- What: `pinDropped.send(car)` is placed outside the `do { ... } catch { ... }` block that encodes and writes `ParkedCar`. If `JSONEncoder().encode(car)` throws (for any reason), `parkedCar` is NOT updated and nothing is written to `UserDefaults`, but `pinDropped.send(car)` fires regardless. W7.5 receives a "pin dropped" event for a car that was never persisted.
- Expected (per spec §6.2): "Emits on every pin drop" — "pin drop" here means a successful save. The hook should only fire when the write succeeds.
- Repro: In a test harness, inject a `MockEncoder` that throws. Observe `pinDropped` fires while `parkedCar` remains nil and `UserDefaults` is unchanged.
- Note: `assertionFailure` in the catch block is a NOP in release builds, making the error path silent in production.
- Severity: Significant (not blocking) because `JSONEncoder` cannot fail on a struct containing only `UUID`, `Double`, `String?`, and `Date` — all primitive `Codable` types. The failure path is unreachable in practice. But the ordering invariant in the spec is violated, and W7.5 will be written to trust the contract.
- Owner: `@ios-engineer`
- Fix: move `pinDropped.send(car)` inside the `do` block, after `parkedCar = car`.

### Minor / Nit

**#2: "Wrong street?" alternatives list not updated after selection**

- Where: `ParkConfirmView.swift`, `alternativesSection`, `ForEach` over `intent.alternativeCandidates`
- What: After the user taps an alternative block (e.g., "1st Avenue"), `intent.detectedSegment` is updated to that block, but `intent.alternativeCandidates` still contains "1st Avenue" as an entry. The sheet now shows "1st Avenue — North side" as the detected block AND "1st Avenue (8m)" in the "Wrong street?" list simultaneously.
- Expected: After re-selection, the selected alternative should be removed from (or replaced in) the alternatives list to avoid showing the currently-detected block as an alternative.
- Repro: Long-press at a corner with 2+ alternatives. Tap an alternative. Observe the alternatives list still contains the newly-selected block.
- Severity: Minor UX — the user can still interact correctly; it is just confusing to see the selected block in both positions.
- Owner: `@ios-engineer`
- Fix: When tapping an alternative, swap the selected candidate back into the list in place of the previous `detectedSegment`, or rebuild the alternatives list to exclude the new detected segment.

**#3: No W5-specific unit tests**

- Where: `ios/WePark/WeParkTests/ParkingRulesEngineParityTests.swift` (only test file)
- What: No unit tests were added for `ParkPinService` (Codable round-trip, `hasEverParkedKey` persistence semantics, hook emission order) or `findCandidateSegments` (haversine radius boundary, deduplication by block key, max-4 cap). The spec §9 QA checklist does not mandate specific tests from the engineer, but these are the two non-trivial new pure-logic functions and both are unit-testable without a simulator.
- Severity: Minor — the 45-test baseline is met; no regression.
- Owner: `@ios-engineer`

## What's Working

- The full pin-drop UX pipeline is correctly wired end-to-end across 8 files with tight separation of concerns: `ParkedCar` is a pure data struct, `ParkPinService` is a pure service, views are pure UI.
- `findCandidateSegments` correctly ports the PWA haversine search with block-key deduplication (`street|from|to`), 35m radius, and max-4 results. The algorithm matches the spec's PWA reference at `index.html:5096-5111`.
- The W6 hook (`firstPinDropped`) emission-before-write ordering is correct — W6 will receive the event before the car appears in storage, which is intentional (W6 presents a rationale sheet, not a parked-car view).
- Silent replace is clean: `syncCarPin` compares `renderedCarPinID` to avoid redundant annotation swaps on every SwiftUI re-render. Only re-renders the annotation when the pin actually changes.
- `ParkedCarDetailView` has a solid LRU-eviction fallback: it uses cached `ParkedCar.street`/`side`/`fromStreet`/`toStreet` fields when the segment is not in `loadedSegments`. Both the re-lookup path and the cached-metadata path are tested by the code structure.
- `ParkConfirmView.interactiveDismissDisabled(true)` prevents accidental swipe-dismiss — correct for a confirmation gate.
- The "Park here" button in `BlockDetailView` retains the preview-safe nil pattern: passing `onParkHere: nil` in `#Preview` keeps the disabled state correct without any code changes to the preview.
- `ParkedCar.id` is a fresh `UUID()` per `confirmPinDrop` call (not reused from `PinDropIntent.id`), ensuring SwiftUI `.sheet(item:)` on `parkedCarDetailItem` always sees a distinct identity on re-park.
- No `Modifying state during view update` risk paths found. `syncCarPin` in `updateUIView` only mutates UIKit state (`MKMapView` annotations) and Coordinator-private vars — no `@Binding` or `@State` writes from inside `updateUIView`.

### One minor observation (not a finding)

In `locationManagerDidChangeAuthorization`, the `manager` parameter is captured strongly inside the `DispatchQueue.main.async` block alongside `[weak self]`. This is technically a strong reference to a system `CLLocationManager` that executes within one run loop cycle — there is no practical leak. However, a strictly idiomatic pattern would use `[weak self, weak manager]` (or access `self?.manager` inside the block) to make the weak-capture intent explicit. This is not a bug — `CLLocationManager` delegate methods deliver `manager` as the same object the service already owns strongly via `self.manager`, and the closure executes before the next render — but it reads slightly inconsistently with the `[weak self]` pattern. Logging as an observation, not a finding, because the actual behavior is correct.
