## Findings

### Blocker (smoke-test finding — fixed in 53bb7c6)

**B-1: `INFOPLIST_KEY_MAPBOX_ACCESS_TOKEN` was a no-op; Bundle.main would have returned nil in production**

- Where: `project.pbxproj` lines 329 / 365 in commit 5764182 (now removed in 53bb7c6).
- What: The initial wiring set `INFOPLIST_KEY_MAPBOX_ACCESS_TOKEN = "$(MAPBOX_ACCESS_TOKEN)"` as a build setting, on the assumption that Xcode's auto-Info.plist machinery would translate any `INFOPLIST_KEY_<name>` setting into a corresponding key in the generated plist. **That assumption is false.** The `INFOPLIST_KEY_*` mechanism is restricted to an Apple-defined allowlist (`NSLocationWhenInUseUsageDescription`, `UISupportedInterfaceOrientations`, scene-manifest keys, etc.). Custom keys are silently dropped.
- Detection path: smoke-test by Kevin (post-QA) ran `PlistBuddy -c "Print :MAPBOX_ACCESS_TOKEN"` against both `Debug-iphonesimulator/WePark.app/Info.plist` and `Release-iphonesimulator/WePark.app/Info.plist`. Both returned `Entry, ":MAPBOX_ACCESS_TOKEN", Does Not Exist`. Unit tests did not catch this because every test injects `tokenProvider: { ... }` directly into `RouteService(...)`, bypassing `Bundle.main` entirely.
- Production impact (if shipped): every `RouteService.fetchRoute(...)` call would throw `MapboxRouteError.missingToken` — no routes would ever be fetched. W8.5b destination UI would render the empty/error state for every search.
- Fix in commit 53bb7c6:
  - Added `ios/WePark/Info.plist` as a minimal stub containing just `<key>MAPBOX_ACCESS_TOKEN</key><string>$(MAPBOX_ACCESS_TOKEN)</string>`.
  - Set `INFOPLIST_FILE = Info.plist` on both Debug + Release configs. `GENERATE_INFOPLIST_FILE` stays `YES`; Xcode merges the file's keys with the auto-generated `INFOPLIST_KEY_*` values, so the Apple-defined keys (location usage description, orientations, scene manifest) continue to be auto-injected.
  - Removed the now-useless `INFOPLIST_KEY_MAPBOX_ACCESS_TOKEN = "$(MAPBOX_ACCESS_TOKEN)";` lines.
- Re-verification:
  - PlistBuddy now returns the token value (redacted) in both Debug and Release Info.plists.
  - PlistBuddy confirms `NSLocationWhenInUseUsageDescription` and other Apple keys are still present (the merge preserves them).
  - Tests: 126/0 (no regression).
  - Live Mapbox HTTP smoke (using the value in `Config.xcconfig`): HTTP 200, valid driving route (5.3km / 23min NYC route, 283 geometry points).
- QA process lesson: future PRs that wire build-setting → runtime values via Info.plist should add a smoke check that loads the built `.app`'s Info.plist with PlistBuddy and asserts the key is present. The QA agent's Pass 1 read-only diff review cannot catch this class of bug — only a `Bundle.main`-bound integration test or a built-bundle inspection can.

### Major

**M-1: `@MainActor` annotation on `RouteService` may force W8.5b callers onto the main thread**

- Where: `RouteService.swift:48` — `@MainActor final class RouteService`
- What: The entire class is pinned to the main actor. `fetchRoute` performs a `session.data(from:)` network hop that itself suspends off-main, but because the caller must hop to the main actor to call `fetchRoute` in the first place, any location-update callback in W8.5b that calls `fetchRoute` from a background isolation context will incur a main-actor hop. This is a plausible source of "main thread blocked" warnings if the call site is careless, though `async/await` should prevent actual blocking.
- Expected (per spec §4): no explicit isolation requirement stated; `@MainActor` is the project-wide pattern for services (`TileLoader`, `ToastService`). This is consistent with the codebase convention.
- Impact: Likely harmless given the `async` boundary, but W8.5b should be aware that `RouteService.shared.fetchRoute` must be called with `await` from any isolation context and will schedule work on the main actor. Flag for `@ios-engineer` to consider `nonisolated` on `fetchRoute` if call-site latency becomes observable.
- Owner: `@ios-engineer` — revisit at W8.5b if location-update → fetchRoute path shows main-thread saturation.

### Nit

**N-1: Redundant double-trim of token in `fetchRoute`**

- Where: `RouteService.swift:105` — `let token = raw.trimmingCharacters(in: .whitespacesAndNewlines)`
- What: `bundleTokenProvider` (the default `tokenProvider`) already trims and returns `nil` for empty strings (lines 79-80). The second trim at line 105 is therefore a no-op for the production path. It does serve a purpose in tests that inject `tokenProvider: { "   " }` directly, bypassing `bundleTokenProvider`. The net behavior is correct; the redundancy is cosmetic.
- Expected: Single trim point.
- Impact: Zero runtime impact. Cosmetic only.

- `MapboxRouteError` conforms to `Equatable` — test assertions like `catch MapboxRouteError.missingToken` use pattern matching correctly; the cases with associated values (`network`, `http`, `decoding`) are still usable in catch patterns with binding.
- `alternatives` flag defaults to `false` in `fetchRoute` — callers that don't need scoring don't need to pass it; W8.5b scoring path passes `true` explicitly.

## Follow-ups for W8.5b

1. **`@MainActor` on `RouteService`** — before wiring location-update callbacks to `fetchRoute`, confirm whether call sites naturally satisfy the main-actor constraint or if `nonisolated` on the method is cleaner. See M-1 above.
2. **Token restriction scope** — the `Config.xcconfig` on disk uses a `pk.*` Mapbox public token (redacted; see local file). Per spec §4, this token should be scoped to the iOS bundle ID (`com.wepark.app`) on the Mapbox dashboard, not left unrestricted. Verify the token restriction is configured before any TestFlight distribution.
3. **`alternatives` flag wiring** — `fetchRoute(from:to:alternatives:)` defaults to `false`. W8.5b's parking-aware scoring requires `alternatives: true`. The `testFetchRoute_alternatives_decodesAllThree` test confirms parsing works; W8.5b must pass the flag at the call site.
4. **Multi-leg routes** — current `toDomain()` on `MapboxRoute` flattens steps across all legs (`legs.flatMap { $0.steps }`). For A→B with no waypoints (the Drive Mode case), this is always a single leg. W8.5 patrol mode will need waypoints, which can produce multi-leg responses; confirm step flattening is the right behavior when that lands.
