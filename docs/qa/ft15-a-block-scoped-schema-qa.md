**Verdict: 🔴 DO NOT APPLY as-is.** One blocking finding: the two new abuse-control mechanisms (hard-ceiling CHECK and rate-limit trigger) are both scoped to `report_group_id is not null`, but `report_group_id` is a client-supplied, RLS-unenforced column — any authenticated user (including anonymous-auth users, which are enabled in this project per HANDOFF.md) can insert an unlimited-duration `filming`/`construction` "closure" pin that both the ceiling and the rate limiter completely ignore, simply by omitting `report_group_id` on the insert. This defeats the entire purpose of §6 for the two pin types the feature exists to protect. Everything else in the file is well-reasoned, and the three explicitly-flagged divergences from the spec sketch are each sound on independent re-derivation. This is a small, mechanical fix — recommend a fast follow-up commit, then a fast re-review, not a redesign.

## Findings

### 🔴 Blocking

- **#1: Both new abuse controls (hard-ceiling CHECK + rate-limit trigger) are scoped to a client-controlled column and are trivially bypassable by any authenticated (including anonymous-auth) user, on the two pin types this feature exists to bound.**
  - Where: `supabase/02f-block-scoped-restrictions.sql`, `pins_block_scoped_ceiling_chk` (§2) and `enforce_block_scoped_rate_limit()` (§6).
  - What: Both mechanisms short-circuit to "not applicable" when `report_group_id is null`:
    - Ceiling: `check (not (source = 'crowd' and report_group_id is not null) or expires_at <= ...)` — if `report_group_id is null`, `not(false) = true`, and the whole constraint is trivially satisfied regardless of `expires_at`.
    - Rate limit: `if new.report_group_id is null or new.source != 'crowd' then return new; end if;` — an insert with `report_group_id` omitted returns immediately, before any count check.
    - `report_group_id` is a plain nullable `uuid` column with no NOT NULL constraint tying it to `pin_type`. Nothing in `pins_insert_crowd` (unmodified RLS, `02-pins-schema.sql:142-148`) requires it to be set — that policy only checks `auth.uid() is not null and author_id = auth.uid() and source = 'crowd'`, exactly as the spec itself documents ("No RLS changes needed for the `pins` insert path... Crowd `filming`/`construction` rows satisfy this today, unmodified" — §3.2).
    - Consequence: `POST /pins {pin_type: 'construction', source: 'crowd', segment_id: '<any blockface>', expires_at: '<10 years out>', author_id: <self>}` with `report_group_id` simply absent from the payload succeeds, is exempt from both the 7-day/90-day ceiling and the 3-per-24h rate limit, and — per the spec's own §3.4 Channel 3 fetch definition (`source=crowd, pin_type in (filming, construction), resolved_at is null, (expires_at is null OR expires_at > now)`, no `report_group_id` filter) — is still fetched, rendered, and consumed by the iOS app as a legitimate active closure. This is not a hypothetical "what if the app has a bug" path: it requires zero iOS changes and works today against the existing, unmodified `pins_insert_crowd` policy the moment this migration is applied — a raw `curl` with a valid session JWT is sufficient. HANDOFF.md records that Anonymous Sign-ins are enabled in production, so the barrier to obtaining a valid session is a single unauthenticated `/auth/v1/signup?anonymous`, not even an email.
  - Expected: per spec §6 and §11 ("Trust/abuse: RLS reuse, extended auto-resolve, rate limit (§6) — required"), a malicious/griefing crowd report should be bounded by both the duration ceiling and the per-author rate limit for exactly this scenario (false "block closed" reports).
  - Repro: (against a test project, not prod) sign in anonymously → `POST /rest/v1/pins` with `pin_type=construction, source=crowd, author_id=<own uid>, expires_at=now()+interval '10 years', report_group_id` omitted from the body → row inserts successfully, ceiling and rate-limit are both silently skipped, row is indistinguishable from a legitimate report to any client reading Channel 3.
  - Why the current scoping doesn't achieve its own stated goal: divergence note #2's rationale is "avoid rejecting legitimate long NYC film permits arriving via `upsert_filming_pin`" — but `upsert_filming_pin` always writes `source = 'open_data'`, so scoping on `source = 'crowd'` alone already achieves that goal without needing the `report_group_id is not null` clause at all. The extra clause doesn't protect anything the `source` check didn't already protect, and it's the specific thing that opens this hole.
  - Recommended fix (either is sufficient, first is more robust): (a) add a complementary CHECK forcing the correlation the file currently disclaims: `check (not (source = 'crowd' and pin_type in ('filming','construction')) or report_group_id is not null)` — i.e., any crowd filming/construction row *must* carry a group id, closing the gap at its root while preserving the stated forward-compat goal that a future pin_type can still reuse `report_group_id` without a schema change; verify no existing crowd `filming`/`construction` rows exist in prod before adding this as a validating (not `NOT VALID`) constraint — the existing `ReportSheet` UI has never offered these types as crowd-submittable, so this should be zero rows, but confirm before applying. Or (b) re-scope both the ceiling and the rate-limit trigger's guard to `source = 'crowd' and pin_type in ('filming', 'construction')` directly (matching the original spec sketch's simpler, non-bypassable framing) — cheaper, but loses automatic coverage for a hypothetical future pin_type reusing this primitive without a matching schema update, per the file's own §9.3 forward-compat concern the file already articulated for the "not constrained" comment.
  - Owner: `@backend-data`

### 🟡 Significant

- **#2: The migration's own partial-apply story for a persistent (not transient) storage-ownership failure is incomplete, and could leave the two "required" trust/abuse mechanisms (§5 items 5/6: extended auto-resolve, rate limit) permanently unapplied without Kevin knowing it.**
  - Where: `supabase/02f-block-scoped-restrictions.sql`, the §4 "OPERATOR NOTE" (added in the `40f04315` hardening commit) versus section ordering (§4 Storage precedes §5 auto-resolve and §6 rate-limit in file order).
  - What: The operator note says "if section 4 fails partway through, you can re-run the ENTIRE file safely... section 5 and 6 do NOT depend on section 4 succeeding." That's true in isolation (nothing later reads state section 4 would have created), but it doesn't follow that re-running the file gets sections 5/6 applied. Whether Kevin's SQL Editor paste executes as one implicit multi-statement transaction (standard Postgres simple-query-protocol behavior for a semicolon-separated batch) or as autocommit-per-statement is unverified here (Supabase doesn't document this, and I don't have access to test it), but under **either** interpretation the practical risk is real:
    - If it's one implicit transaction (the Postgres default for a multi-statement batch sent as a single query): a section-4 failure rolls back the *entire* script, including sections 1-3 that "succeeded" — sections 5 and 6 never execute, and re-running the file makes zero forward progress on every attempt for as long as the ownership issue persists. Kevin would see an error every time and might reasonably assume "close enough, most of it applied" when in fact nothing did.
    - If it's autocommit-per-statement: sections 1-3 do persist, but execution still halts at the first error in section 4 — sections 5 and 6 (the rate limiter and the extended dispute-resolution trigger, both marked "required" in spec §11) simply never run in that pass, and the file gives no explicit instruction to copy-paste just sections 5+6 separately if section 4 keeps failing.
  - Expected: since the whole point of the note is "tell Kevin what to do when this fails," it should also say explicitly: "if section 4's `create policy ... on storage.objects` statements keep failing after a retry, manually select-and-run sections 1, 2, 3, 5, 6 only (skip section 4), then fix the Storage policies separately via the Supabase Dashboard → Storage → Policies UI once ownership is sorted — do not assume re-running the whole file will ever get you past a persistent (not transient) ownership error."
  - Repro: not applicable to prod (would require actually breaking storage ownership to observe) — this is a code-review finding about the runbook text, not an executable bug. Low cost to fix, high value given Kevin is running this by hand with no agent watching.
  - Recommended fix: reorder the file so §5 (auto-resolve) and §6 (rate limit) — which are independent of §4 and are the two "required" abuse-control pieces — come *before* §4 (storage), so a storage-ownership failure can't gate them out of a single-pass apply at all. This is a pure reordering, zero semantic change, and removes the entire class of risk described above.
  - Owner: `@backend-data`

### 🟢 Minor / nit

- **#3: Comment/code mismatch on the sanity CHECK.** The top-of-file summary calls this "a general `starts_at <= expires_at` sanity constraint," but the actual code is `check (starts_at is null or expires_at is null or expires_at > starts_at)` — strictly greater-than, disallowing a zero-length window (`starts_at == expires_at`), not `<=`. Almost certainly the intended behavior (a zero-duration restriction is meaningless), but the comment should say `<` to match the code, or the code should use `>=` if a zero-length window is meant to be legal.
- **#4: Rate-limit trigger has a benign TOCTOU race under concurrent inserts.** `enforce_block_scoped_rate_limit()` reads `count(distinct report_group_id)` under default READ COMMITTED isolation with no row lock (no `SELECT ... FOR UPDATE`, no advisory lock). Two near-simultaneous report submissions from the same author (e.g. two tabs/devices) could both read "2 groups in the last 24h" and both proceed, landing the author at 4 groups instead of being capped at 3. Given the feature's realistic volume (a handful of reports per author) and that this is an abuse *deterrent*, not a security boundary, this is low-severity — flagging as a known limitation, not a blocker.
- **#5: `pins_author_report_group_created_idx` doesn't cover `report_group_id`, so the rate-limit trigger's `count(distinct report_group_id)` still needs a heap visit per candidate row rather than an index-only scan.** At the feature's expected volume this is immaterial, but if it's ever revisited, `(author_id, created_at, report_group_id)` would let the planner do more of the work index-only.
- **#6: `pin_evidence.pin_id` is, in practice, always null at insert time** given the documented write order (evidence row created before any `pins` rows exist), and there's no described follow-up step that ever back-fills it. Not a defect — it's an intentionally optional convenience column per the file's own comment — but worth noting for whoever writes B3 that "convenience pointer" currently has no code path that ever sets it.
- **#7: `pin_evidence.report_group_id` has no FK to anything** (documented as intentional, since the row is written before any `pins` row with that group id exists). This means a user could insert a `pin_evidence` row referencing a `report_group_id` that belongs to a *different* user's report, or one that never gets a matching `pins` row at all. Neither creates a security issue (read access is still gated on `uploaded_by`, not `report_group_id`), just a data-integrity looseness already implicitly accepted by the "no automatic deletion" retention posture. No action needed, noting for completeness.

### 💡 Out of scope (logged, not fixed)

- Both new `SECURITY DEFINER` functions (`auto_resolve_on_dispute`, `enforce_block_scoped_rate_limit`) don't pin `search_path`, which is general Postgres SECURITY DEFINER hardening best practice against search_path-shadowing attacks. Not a live risk here since every object reference inside both function bodies is already schema-qualified (`public.pins`, `public.rate_limit_config`), and this matches the pre-existing pattern in `02-pins-schema.sql`/`02e-auto-resolve-trigger.sql` (also unpinned) — not a regression introduced by this PR, not worth a one-off fix here.
- If `02e-auto-resolve-trigger.sql` is ever re-run *after* `02f` (e.g. someone re-pastes it by mistake during a future full-reapply), it would silently revert the auto-resolve guard back to ephemeral-only, undoing this migration's §3.3 fix. This is an inherent risk of the "replace function body, no version tracking" pattern already used elsewhere in this repo, not something unique to this PR — flagging for awareness, not a blocker.

- Idempotency discipline is excellent — every single DDL statement in the file is independently guarded, and I could not find one exception. This is materially better than "safe to re-run" as an unverified claim; it's true statement-by-statement on inspection.
- The PII containment boundary (§7's whole reason for existing) holds up under active adversarial testing — no anon read path, no cross-user leak via path-prefix tricks, `pins_with_author` genuinely untouched.
- All three explicitly-flagged divergences from the spec sketch are sound: the `pin_evidence.pin_id` nullable+SET NULL / `report_group_id`-as-durable-key shape correctly avoids the sketch's orphaning bug with no worse failure mode I could find; the `storage.objects` RLS-enable removal is a real, well-justified risk reduction for a hand-run migration; the `starts_at <= expires_at` addition is free correctness with zero backward-compat risk.
- The `auto_resolve_on_dispute` replacement is a textbook-careful extension — same recursion-safety property, same threshold, guard widened by exactly the amount the spec asked for and no more.
- The rate-limiter's "exclude the group currently being inserted" logic correctly avoids self-limiting a legitimate N-row batch submission, and the `coalesce` fallback for a missing `rate_limit_config` row is a real, working safety net (confirmed via the owner-bypass reasoning that a `SECURITY DEFINER` function owned by the table-creating role bypasses RLS regardless of policies present).
- The file's own inline documentation is unusually good — the divergence callouts, the "known accepted gap" note on evidence orphaning, and the operator note on storage ownership all show real engineering judgment about what a hand-run production migration needs to communicate. Finding #1 is a scoping bug, not a carelessness problem — the author clearly thought hard about this file; the fix is small and mechanical, not a sign the rest of the file needs re-review.
