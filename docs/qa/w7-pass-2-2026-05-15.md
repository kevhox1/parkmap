### Minor / Nit

**#7 (Nit): GeometryReader used instead of spec-preferred `.safeAreaInset` proxy pattern**

- Where: `ContentView.swift` lines 270–277.
- What: The spec (§3.E "Placement in ContentView") explicitly says: "The exact inset can be
  read from `GeometryReader` or via the `.safeAreaInset(edge: .top)` modifier applied to a
  transparent proxy view — prefer the proxy approach to avoid an extra `GeometryReader` wrapper."
  The implementation uses `GeometryReader`, which the spec deprioritizes.
- Expected per spec: `.safeAreaInset(edge: .top)` transparent-proxy approach preferred.
- Impact: None visible to the user. `GeometryReader` is a valid implementation of the spec's
  requirement — the spec permits it but de-prefers it. The commit message for `43b3994` correctly
  describes what it does. This is purely a code-style deviation from the spec's stated preference.
- Owner: `@ios-engineer` (awareness only; fix not required for ship)

**#8 (Nit): `proxy.safeAreaInsets.top` value in safe-area-constrained ZStack**

- Where: `ContentView.swift` line 273: `.padding(.top, proxy.safeAreaInsets.top)`.
- What: The outer `ZStack(alignment: .top)` has no `.ignoresSafeArea()` modifier. SwiftUI
  positions a safe-area-respecting `ZStack` with its top edge at the bottom of the status bar
  by default. In this layout, `GeometryReader`'s `proxy.safeAreaInsets.top` inside a
  safe-area-constrained `ZStack` may report `0` (because the safe area was already consumed
  by the ZStack's positioning). If so, `.padding(.top, 0)` means the toast capsule's top edge
  aligns with the very top of the `ZStack`'s content area — which is already below the status
  bar. The toast would still clear the status bar; the spec's goal is satisfied. However, the
  exact pixel behavior depends on SwiftUI's layout resolution and cannot be verified without
  a simulator run. If `proxy.safeAreaInsets.top` returns `0`, the fix is functionally correct
  but redundant (same as no padding). If the outer `ZStack` were ever given `.ignoresSafeArea()`
  in the future, the `GeometryReader` approach would then correctly inset the toast.
- Expected: Verify on a notched device (Dynamic Island or notch) that the toast capsule appears
  entirely below the status bar / island with a small visual margin.
- Impact: Risk is low — worst case the toast aligns flush to the top of the safe-area content
  zone, which is still below the status bar. Not a regression from pass-1's flat-8pt behavior.
  Recommend live smoke to confirm position on iPhone 17 Pro or equivalent.
- Owner: `@ios-engineer` (verify only; no fix needed unless toast overlaps the island)

## What's Working

- **Private init enforcement is clean.** `private init() {}` plus `#if DEBUG resetForTesting()`
  is the standard Swift singleton-with-testability pattern. It is correct, minimal, and does not
  compromise test coverage. The `@MainActor` annotation on both the service and the test class
  ensures all state mutations are on the main thread without any `await MainActor.run` ceremony
  in tests.

- **Commit discipline is good.** Both pass-2 commits are tightly scoped. `de16b0b` touches
  exactly the two files named in its commit message; `43b3994` touches exactly one. No unrelated
  changes snuck into either commit.

- **The GeometryReader approach is safe for this layout.** Even if `proxy.safeAreaInsets.top`
  returns `0` (because the ZStack is already safe-area-constrained), the result is that the toast
  aligns with the top of the content area, which is below the status bar. The Dynamic Island /
  notch is handled by the system safe-area layout; zero additional inset is still correct
  behavior. The worst-case outcome is a toast at the very top of the content area with no extra
  breathing room — acceptable and better than the pass-1 8pt constant on a 59pt island device.

- **Test isolation pattern is solid.** Calling `resetForTesting()` in both `setUp` AND `tearDown`
  guarantees clean state entering and exiting each test, even if the test itself triggers an
  async auto-dismiss task that could bleed into the next test. The `dismissTask?.cancel()` +
  `currentMessage = nil` reset is synchronous and complete.
