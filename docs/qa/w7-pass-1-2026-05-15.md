## Summary

The W7 implementation is largely correct and well-structured across all five sub-features. The per-pin `notifyOnRestriction` toggle, `ParkedCar` Codable migration, `NotificationScheduler` guard ordering, `RuleRow` tap-to-expand, `ASPBanner`, `SettingsView`, `ToastService`, and `ToastHostView` all follow the spec closely. Three issues were found requiring resolution before a clean ship: (1) `ToastService.init()` is not `private` — the spec prescribes `private init()` and the tests circumvent this by using a fresh non-singleton instance, making the singleton guarantee unenforced; (2) the `ToastHostView` toast top-inset is a flat 8pt padding rather than a geometry-aware safe-area inset, meaning on notch devices the toast may render under the status bar rather than below it; (3) `SettingsView` does not write `notificationsMuted` to `UserDefaults` directly on toggle-off — it relies entirely on `ContentView`'s `.onChange(of: notificationsMuted)` handler, which is indirect and creates a latency window where the mute flag isn't persisted until SwiftUI propagates the binding change. Additionally, `xcodebuild test` could not be run in this session (Bash tool denied), so the 72/0 test count claim is unverified. The engineer must confirm that claim via a live build before merge.

## Findings

### Blocker

None.

### Major

**#1: `ToastService.init()` is not `private` — singleton not enforced**

- Where: `Services/ToastService.swift`, line 43: `init() {}`
- What: The spec (`docs/w7-asp-banner-settings-spec.md` §3.E) explicitly prescribes `private init() {}` to enforce singleton discipline. The implementation uses a bare `init() {}` (internal access, the Swift default), which allows any code to instantiate a second `ToastService` outside the singleton path. The W7 tests (`W7ToastServiceTests`) do exactly this: they construct `toast = ToastService()` in `setUp()` to avoid singleton state bleed across tests — a reasonable test pattern, but it works only because the initializer is not private.
- Expected: `private init() {}` as specified.
- Impact: Any call site that does `let t = ToastService()` rather than `ToastService.shared` gets an independent instance. `ToastHostView` observes `ToastService.shared`; a call site using a local instance will not render in the UI. This is a semantic violation of the singleton contract and a future trap for W7.5/W8 callers. The test isolation workaround inadvertently hides the enforcement gap.
- Owner: `@ios-engineer`

**#2: `ToastHostView` top padding uses a flat 8pt constant — may render under status bar on notched devices**

- Where: `ContentView.swift`, lines 267-271: `VStack { ToastHostView().padding(.top, 8); Spacer() }`
- What: The toast is positioned with `.padding(.top, 8)` relative to the root `ZStack`'s top edge. The spec (§3.E "Placement in ContentView") explicitly says: "It should be pinned to the top via a `VStack { ToastHostView(); Spacer() }` with `.padding(.top, safeAreaTopInset)` so it clears the status bar. The exact inset can be read from `GeometryReader` or via the `.safeAreaInset(edge: .top)` modifier applied to a transparent proxy view." On a device with a dynamic island or notch, the status bar is ~50–60pt. With 8pt padding, the toast will render partially or fully behind the status bar text, making it visually inaccessible.
- Expected: Top padding equal to the safe-area top inset (read from `GeometryReader` or a `.safeAreaInset` proxy view), not a hard-coded 8pt.
- Impact: Toast is visible in the Simulator (where the status bar is transparent or small) but may be obscured on real hardware with a dynamic island or notch.
- Owner: `@ios-engineer`

### Minor

**#3: `notificationsMuted` UserDefaults write is one SwiftUI update cycle delayed from the binding flip**

- Where: `ContentView.swift`, `.onChange(of: notificationsMuted)` handler (lines 304-312)
- What: When the user flips the toggle in `SettingsView`, the flow is: (1) `notificationsActiveBinding.set` updates `notificationsMuted` via the `@Binding`; (2) SwiftUI propagates the binding change back to `ContentView`; (3) `onChange(of: notificationsMuted)` fires and writes to `UserDefaults`. There is one additional render cycle between the UI action and the `UserDefaults` write. In practice this is imperceptible and almost certainly no-op on the main thread. However, if the app is killed between step 1 and step 3 (e.g., by a crash immediately after toggle), the mute state is lost. The spec (§4.B) describes this pattern as acceptable; the engineer implemented it correctly per spec. Logged as minor because the spec explicitly chose this approach, but worth confirming the developer understands the one-cycle window.
- Expected per spec: Correct as-is.
- Owner: `@ios-engineer` (awareness only; fix not required)

**#4: `ParkedCarDetailView` passes `parkPinService: ParkPinService` but spec prescribes `scheduler` is default-injected, not required**

- Where: `Views/ParkedCarDetailView.swift`, line 49: `let scheduler: NotificationScheduler` (required, not defaulted in initializer declaration). But actually the `init()` at line 62 does default it: `scheduler: NotificationScheduler = .shared`. 
- What: This is actually fine — the init default covers it. `ContentView` does not pass `scheduler` explicitly (it uses the default). Non-finding; logged and cleared.

**#5: `SettingsView` missing `.presentationCornerRadius(20)` — minor deviation from spec**

- Where: `ContentView.swift`, lines 470-476. The `.settings` case sheet modifiers are: `.presentationDetents([.medium])`, `.presentationDragIndicator(.visible)`, `.presentationBackground(.regularMaterial)`. The spec (§4.B) prescribes `.presentationCornerRadius(20)`.
- What: The `case .settings:` sheet in `ContentView` does not include `.presentationCornerRadius(20)`, which all other sheet cases include (`.blockDetail`, `.parkConfirm`, `.parkedCarDetail` all have it). The setting sheet will use the system default corner radius instead of the spec's 20pt.
- Expected: `.presentationCornerRadius(20)` added to the `.settings` case sheet modifiers.
- Owner: `@ios-engineer`

### Nit

**#6: `ToastService` imports both `Foundation` and `SwiftUI` and `Observation` separately**

- Where: `Services/ToastService.swift`, lines 32-34: `import Foundation`, `import SwiftUI`, `import Observation`.
- What: The spec (§3.E code sample) shows only `import SwiftUI` (which subsumes `Foundation` and `Observation` on Apple platforms). Three separate imports is redundant. The file comment at line 29 also says "No import SwiftUI" which contradicts the actual imports. The engineer self-flagged this in the PR notes; the spec does prescribe `withAnimation` which requires SwiftUI. Non-blocking. The stale comment ("No import SwiftUI") is a nit.
- Owner: `@ios-engineer`

## What's Working

- **Guard ordering in `NotificationScheduler` is correct.** Global mute fires first (line 100), per-pin opt-out fires second (line 103). The sequential guard chain is clean and correctly models the intended priority: global mute wins, then per-pin opt-out.

- **`PinConfirmResult` struct cleanly decouples notification intent from `PinDropIntent`.** The spec's recommended approach was followed precisely. `PinDropIntent` is unchanged; the per-pin decision flows through a clean wrapper. This will not require refactoring in W7.5 or W8.

- **`ParkedCar` migration is correct and tested.** The `decodeIfPresent(...) ?? true` pattern at the right place in `init(from:)` is backed by a concrete test that decodes a real pre-W7 JSON blob (not just a mock). This is exactly the level of coverage the spec called for.

- **`ActiveSheet` enum pattern is clean.** Exactly one `.sheet(item:)` modifier in `ContentView`. All five cases handled. The new `.settings` case attached via the prescribed enum extension. No parallel sheets, no structural surgery.

- **`RuleRow` tap-to-expand is well-implemented.** The `@ViewBuilder` layout switch between `HStack` (collapsed) and `VStack` (expanded) is clean. The badge is always visible. The hint update is tied to `isExpanded`. No animation artifacts expected.
