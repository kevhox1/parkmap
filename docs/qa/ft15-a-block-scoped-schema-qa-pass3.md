## Findings

### 🔴 Blocking

- **#1: `NEW.source` is never checked by the skip condition — an author can relabel their own crowd pin `'crowd' → 'open_data'` via a single `UPDATE`, which simultaneously (a) escapes the ceiling CHECK, (b) makes the pin permanently immune to dispute-driven auto-resolve, and (c) drops the row out of Guard 2's own row count, freeing a "slot" for more spam. This is a total defeat of every abuse-control mechanism this migration adds, not just the rate limiter.**
  - Where: `supabase/02f-block-scoped-restrictions.sql:534-541` (skip condition), interacting with three other pieces of this same file/its dependencies that all gate on `source = 'crowd'`: the ceiling CHECK (`:247`, `not (source = 'crowd' and report_group_id is not null) or ...`), `auto_resolve_on_dispute()` (`:426`, `new.source = 'crowd'`), and Guard 2 itself (`:598`, `and source = 'crowd'`). Also depends on the pre-existing, column-unrestricted `pins_update_own` RLS policy (`02-pins-schema.sql:151-154`, `for update using (auth.uid() = author_id) with check (auth.uid() = author_id)` — no column list, no restriction on which fields an author may change on their own row).
  - What: the skip condition is:
    ```sql
    if tg_op = 'UPDATE' then
      if old.report_group_id is not null
         and old.source = 'crowd'
         and old.report_group_id = new.report_group_id
      then
        return new;
      end if;
    end if;
    ```
    Every clause inspects `OLD` or compares `OLD.report_group_id` to `NEW.report_group_id` — nothing here ever looks at `NEW.source`. So an `UPDATE` that keeps `report_group_id` unchanged but flips `source` from `'crowd'` to `'open_data'` (or `'hybrid'`) matches all three conditions (they're evaluated against `OLD`, which was still `'crowd'`) and is **skipped** — the rate limiter never even looks at this statement. Once relabeled:
    - The ceiling CHECK (`pins_block_scoped_ceiling_chk`) gates on `source = 'crowd' and report_group_id is not null`; with `source = 'open_data'` this collapses to `not(false and ...) = true`, vacuously satisfied regardless of `expires_at`. Any subsequent edit can set `expires_at` arbitrarily far in the future with no ceiling at all.
    - `auto_resolve_on_dispute()` checks `new.source = 'crowd'` at the moment `dispute_count` crosses 3. A relabeled row never matches, so it is now permanently immune to community dispute-driven removal — the exact mechanism `docs/ft15-tf215-temporary-block-restrictions-spec.md` §6.1/§3.3 extended specifically to cover block-scoped filming/construction reports.
    - Guard 2's own `count(*)` filters `source = 'crowd'` (`:598`). Once a row is relabeled, it stops counting toward the author's 30-row cap on all future checks — so an author can insert up to `max_rows`, relabel the batch to `'open_data'` (each relabel is itself skipped by the same hole, so it's free), and repeat indefinitely. Guard 1's distinct-group count (`:568-574`) has no `source` filter at all, so it's unaffected either way by this specific trick, but it's already separately defeated by pure id-reuse (see the file's own round-3 comment, `:558-567` — Guard 1 is *known* and *accepted* to be permanently defeated by a reused `report_group_id`; Guard 2 was the only thing actually bounding that case, and this finding removes that bound too).
    - The resulting row also then reads, to any downstream consumer keying off `source`, as government/open-data-sourced content rather than an unverified crowd report — a live navigation app surfacing it as if it were a verified NYC permit closure.
  - Expected: per spec §6/§11 ("required" trust/abuse controls), an author should not be able to unilaterally convert their own unverified report into content that is exempt from every control this file adds, by editing a single column that carries no special protection anywhere in the schema.
  - Repro (against a test project, not prod): as an authenticated (incl. anonymous-auth) user, `POST /rest/v1/pins {pin_type: 'construction', source: 'crowd', author_id: <self>, report_group_id: <fresh uuid>, expires_at: now()+interval '89 days'}` — succeeds normally, correctly rate-limited/ceiling-bound as crowd content. Then `PATCH /rest/v1/pins?id=eq.<that id> {source: 'open_data'}` — the `BEFORE UPDATE` trigger's skip condition matches (`OLD.report_group_id` unchanged, `OLD.source = 'crowd'`), no guard runs, the update succeeds. A further `PATCH ... {expires_at: '2075-01-01'}` on the now-`open_data` row also succeeds (ceiling CHECK vacuous), and a third author disputing the pin 3+ times never triggers auto-resolve (guard checks `new.source = 'crowd'`, now false).
  - Note on scope: this is **not** a defect I'm attributing to round 3's diff by itself — `pins_update_own`'s column-unrestricted grant and the `source = 'crowd'` guards on the ceiling CHECK/`auto_resolve_on_dispute()` all predate this PR. But it is a live, currently-exploitable path through the exact skip condition round 3 added, and it was uncovered directly by the adversarial question the task assigned me ("what if OLD was crowd + qualifying and NEW changes source or pin_type?"). I'm reporting it because it's real and severe, not because it's round-3's fault in isolation — but the skip condition as written is the piece that makes the relabeling itself free of any check.
  - Recommended direction (not a full design): the skip condition needs to also require `new.source = 'crowd'` (and arguably `new.pin_type = old.pin_type`, or more narrowly, reject/ignore any `UPDATE` that changes `source` away from `'crowd'` on a row that was ever a block-scoped crowd report at all — e.g. a `CHECK` making `source` effectively write-once for rows with `report_group_id is not null`, since RLS alone can't easily express "block this one column transition" without a trigger or a generated/immutable-column pattern).
  - Owner: `@backend-data`

- **#2: `created_at` is (with high but not live-verified confidence) a plain client-writable column, and both Guard 1 and Guard 2's window filters trust it unconditionally — an attacker who backdates `created_at` on every insert is permanently invisible to both guards, forever, via a pure `INSERT` loop with no `UPDATE` trickery at all.**
  - Where: `supabase/02f-block-scoped-restrictions.sql:568-574` (Guard 1) and `:593-599` (Guard 2) — both filter on `created_at > now() - (v_window_hours || ' hours')::interval`. `pins.created_at` is defined in `02-pins-schema.sql:59` as `timestamptz not null default now()` — a plain default, not a generated/immutable column, and nothing in `enforce_block_scoped_rate_limit()` or any other trigger on `pins` (checked `votes_refresh_pin_counts`, `pins_auto_resolve_on_dispute` — neither touches `created_at`) overwrites a client-supplied value. `pins_insert_crowd`'s `WITH CHECK` (`02-pins-schema.sql:143-147`) only constrains `auth.uid()`, `author_id`, `source` — nothing about `created_at`. I found no column-level `GRANT`/`REVOKE` anywhere in `supabase/*.sql` restricting which columns `authenticated`/`anon` may write on `pins` — the only grants in the repo are table/view/function-level (`grant select on ... to anon, authenticated`, `grant execute on function ...`). Standard, well-documented Supabase project defaults grant table-wide INSERT/UPDATE/SELECT/DELETE to `anon`/`authenticated` with RLS as the sole access-control layer (no per-column restriction), and this file's own round-1 QA (`docs/qa/ft15-a-block-scoped-schema-qa.md` Finding #1) already established the same fact pattern for `report_group_id` — a plain nullable column with no extra protection is fully client-controlled.
  - What: a `Postgres` `default` only applies when a column is *omitted* from the `INSERT` list; an explicit value in the payload always wins. If a client includes `"created_at": "2020-01-01T00:00:00Z"` in the JSON body of `POST /rest/v1/pins`, that value is written verbatim (subject only to the confirmation above about grants, which I could not test live). Because both guards' window queries only ever look at `created_at`, an author who always backdates every block-scoped crowd insert to well outside the 24h window is invisible to Guard 1 (`count(distinct report_group_id)`) and Guard 2 (`count(*)`) on every future check, with no upper bound — every prior row simply never satisfies `created_at > now() - 24h` for any subsequent insert's count query. Unlike Finding #1, this requires zero `UPDATE`s — it's a straight `INSERT` loop, and it does not depend on `pins_update_own` at all.
  - The row is still fully bound by the ceiling CHECK (`expires_at <= coalesce(starts_at, created_at) + duration`) — but since `coalesce` prefers `starts_at` when present, an attacker sets `starts_at = now()` explicitly (a plain client-writable column per the file's own comments) so the ceiling anchors off `starts_at`, not the backdated `created_at`. The resulting row reads as a normal, currently-active, correctly-bounded closure to every other check in the system — only the rate limiter's own window filtering is fooled.
  - Expected: per spec §6.2/AC-S7 (and the entire reason round 3 exists), the "3 groups / 30 rows per 24h" caps should bound total block-scoped crowd insertion volume regardless of client-supplied metadata.
  - Repro (against a test project, not prod, and **not empirically executed here** — see caveat below): loop `POST /rest/v1/pins {pin_type: 'construction', source: 'crowd', author_id: <self>, report_group_id: <fresh uuid each time>, starts_at: now(), expires_at: now()+interval '89 days', created_at: '2020-01-01T00:00:00Z'}`. Each iteration should insert with zero rate-limit friction, since Guard 1/Guard 2's `SELECT COUNT` queries never see any of the attacker's own prior rows as "recent."
  - Confidence and caveat: I could not execute this against a live Supabase project (no `psql`/`docker` in this sandbox, remote project explicitly off-limits). The claim that `created_at` is client-writable rests on (a) standard, well-documented Postgres/Supabase default-privilege behavior, (b) the absence of any restricting `GRANT`/`REVOKE`/trigger anywhere in this repo's SQL, and (c) this file's own established precedent for `report_group_id`. This is strong circumstantial evidence, not a live-verified fact — **recommend Kevin run one real `curl`/Postgres test with an explicit `created_at` in the payload before applying**, to either confirm or rule out this specific vector. If it rules it out (e.g. some project-level column privilege restriction I can't see from here), this finding downgrades; Finding #1 does not depend on it and stands on its own.
  - Recommended direction: don't trust client-supplied `created_at` for rate-limit windowing. Either add a `BEFORE INSERT` (not just this trigger) step that forces `new.created_at := now()` unconditionally for `source = 'crowd'` rows (cheapest fix, and arguably correct regardless of this specific exploit — an author-supplied `created_at` on their own report has no legitimate use case), or have the rate-limit window queries key off a column the trigger itself stamps rather than trusting `pins.created_at` as stored.
  - Owner: `@backend-data`

### 🟡 Significant

- **#3: The `max_rows` cap is a live-row snapshot count, not a cumulative 24h event counter — delete-then-reinsert lets an author cycle well past 30 total block-scoped crowd rows created in a day while never holding more than ~30 simultaneously.**
  - Where: Guard 2 (`:593-599`), interacting with the pre-existing, unrestricted `pins_delete_own` policy (`02-pins-schema.sql:157-159`, `for delete using (auth.uid() = author_id)` — no rate limit, no cooldown on deletes).
  - What: `count(*)` reflects the current state of the table, not a cumulative tally of inserts. An author can insert up to 29 rows (staying under `max_rows=30`), delete some or all of them, then insert more — each new batch only "sees" whatever currently exists, not what has ever existed. Distinct from the orchestrator's already-accepted note that "30 rows/24h bounds but does not eliminate abuse" (which I agree is correctly categorized as an accepted tradeoff, not a defect, and am not re-flagging): that framing describes a *bounded* daily ceiling that's simply generous enough to allow some abuse. This is different — it's not a generous-but-bounded ceiling, it's effectively unbounded over a sustained session, because the guard has no memory of deleted rows. The task specifically asked me to check "deletes-then-reinserts," so flagging it as its own distinct mechanism rather than folding it into the accepted note.
  - Expected: implicit in "30 block-scoped crowd rows per author per 24h" is that it bounds total reports created in the window, not merely rows alive at any one instant.
  - Repro: insert 29 rows (any mix of group ids), confirm Guard 2 allows it; `DELETE` 20 of them (author's own rows, unrestricted); insert 20 more — succeeds, no different signal at any single point that ~49 total rows were created in the window.
  - Recommended direction: if a true cumulative cap matters, Guard 2 needs an append-only signal (e.g. a separate log table incremented on insert, never decremented on delete) rather than counting live `pins` rows. Given `max_rows=30` is already described as "deliberately generous," this may be judged low-priority relative to Findings #1/#2 — noting it as significant, not blocking, since its ceiling on *simultaneously visible* fake closures (the thing that actually misleads a driver at any given moment) still holds even under this technique.
  - Owner: `@backend-data`

### 🟢 Minor / nit

- **#4: Guard 1's surviving self-exclusion (`report_group_id != new.report_group_id`) doesn't have `source = 'crowd'` filtering, unlike Guard 2 — meaning Guard 1 counts distinct group ids across `source` values (including any that have been relabeled to `'open_data'` per Finding #1) while Guard 2 stops counting them.** This inconsistency doesn't create a *new* bypass beyond what Finding #1 already describes (Guard 1's distinct-id cap was already fully defeated by pure id-reuse regardless of source, per the file's own round-3 comment), but it's worth noting the two guards now disagree on what counts as "this author's recent block-scoped activity" — Guard 1 says "any row with this id, any source"; Guard 2 says "any row, `source = 'crowd'` only." If Finding #1 is fixed by adding a `source` check to the skip condition, revisit whether Guard 1 should also gain a `source = 'crowd'` filter for consistency (harmless either way today, since Guard 1 is separately known-defeated by id-reuse).
- **#5: The `BEFORE INSERT OR UPDATE` trigger (no column list) fires on every `UPDATE` to every row in `pins`, not just block-scoped ones — confirmed this is cheap in practice** (the `new.report_group_id is null or new.source != 'crowd'` early return is two scalar comparisons, no query, for the overwhelming majority of rows: `parked_car`, non-crowd, non-grouped crowd pins). No performance concern at this feature's expected volume; flagging only because the task asked me to assess it explicitly.

### 💡 Out of scope (logged, not fixed)

- Both items the orchestrator pre-flagged as accepted, non-defect tradeoffs — I reviewed both and agree with the categorization, not re-litigating: (a) 30 rows/24h bounds but doesn't eliminate single-account abuse under anonymous auth (true, and inherent to any threshold-based control without stronger identity signals); (b) a legitimate large single report (~20 rows, e.g. full-avenue closure) could approach the `max_rows=30` ceiling (true, `max_rows` was sized "10x max_count" specifically to leave headroom, and Kevin's own canonical 4-row batch traces cleanly under it — a 20-row batch would land at existing-count 0..19, still under 30, so it would *not* actually reject at the sizes in the given example, but is closer to the edge than smaller batches).
- The TOCTOU race on both guards' `COUNT` reads (no row lock under READ COMMITTED) — this is the file's own already-documented, already-accepted "known limitation" (comment at `:452-461`), unchanged in character by round 3's addition of Guard 2. Not re-flagging as new.

## What's working

- Guard 2's `count(*)` design is mathematically correct **in isolation** for what it was built to fix: it genuinely closes Pass 2 Finding #1 (permanent group-id-reuse invisibility) *when `source` and `created_at` are both honest* — i.e. for an attacker who doesn't also exploit Findings #1/#2 here, the row-count cap does hold at 30. The failure mode isn't "the counting logic is wrong," it's "the inputs to the counting logic (`source`, `created_at`) are both unprotected client-writable columns," which is a different, narrower class of problem than round 2's bug.
- The insert-cheap-then-`UPDATE`-into-qualifying path (Pass 2 Finding #2) is genuinely, correctly closed for the case it was built to close — the `OLD.report_group_id is not null` clause correctly identifies "this row was not previously qualifying" and forces the guards to run. I could not find a way to reach a newly-qualifying state that evades this specific check.
- No recursion risk, no plpgsql `OLD`-not-assigned error path on plain `INSERT`, and the internal `UPDATE`s from `refresh_pin_vote_counts()`/`auto_resolve_on_dispute()`/`extend_pin_expiry()` are correctly, verifiably unaffected by the widened trigger — confirmed by reading each function's actual `SET` clause, not assumed from the file's own comment.
- The file's inline documentation continues to be unusually thorough and specific about its own reasoning (the "why not time-bound Guard 1 instead" note is a genuinely good piece of engineering judgment, independently correct on re-derivation: time-bounding the self-exclusion really doesn't close the reused-id bypass, since a reused id is still exactly one distinct value regardless of the exclusion window).
- Kevin's canonical batch is unaffected and the `max_rows` default is sized with real headroom for legitimate large reports — this wasn't a rushed fix.
