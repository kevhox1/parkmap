## Accepted deviations / tech-debt (pre-approved by Kevin, NOT findings)

### Pitch 30 deg vs spec 45 deg

Spec OQ-3 resolved to 45 deg. Code ships `static let driveModePitch: CGFloat = 30` at `MapViewRepresentable.swift:195`. The constant is named `driveModePitch`, the comment on lines 191-195 explains the rationale: MapKit silently clamps pitch to ~35 deg at the span and altitude used by the app (0.005 deg span, altitude derived from ~99,999 m via altitudeForSpan), causing camera readback to diverge from the set value; 30 deg is below the clamping threshold and the visual result is equivalent to a mild forward tilt. Kevin accepted 30 deg. Verified: the constant is present, named, and explained in the source.

Test `testDriveCamera_onDriveModeStart_setsTightSpanAndPitch` asserts `accuracy: 1.0` against `driveModePitch` (not against 45), so the test is consistent with the accepted deviation.

### Headless-window guard in syncDriveCamera

`MapViewRepresentable.Coordinator.syncDriveCamera` at lines 633-668 detects `mapView.window == nil` and, when true, attaches the mapView to the first available UIWindowScene window so MKMapView camera API calls are synchronous in the XCTest host. The engineer's claim: "in production, `mapView.window` is always non-nil."

Verification of the "never reached in production" claim: `MapViewRepresentable` is instantiated exactly once in production, at `ContentView.swift:303`. `ContentView` is the root view of the app's scene (`WeParkApp` body). By the time SwiftUI calls `makeUIView` on a `UIViewRepresentable`, the host view is part of an active UIWindowScene — `mapView.window` will be non-nil from the first draw cycle. There is no code path in the production app that creates a bare `MKMapView()` outside of `makeUIView` and then calls `syncDriveCamera` on its coordinator.

The guard is dead in production. Kevin accepted it as tech-debt (test should be restructured). Verified.

## R-1 Feedback Loop Guard (load-bearing risk)

The spec's primary risk was that `setCamera` inside `syncDriveCamera` would fire `regionDidChangeAnimated` -> `updateUIView` -> `syncDriveCamera` again, creating a tight loop.

Mitigation verified:
1. `lastDriveModeActive: Bool` declared at `Coordinator` line 401 (initialized false)
2. Guard at line 674: `guard active != lastDriveModeActive else { return }`; line 675 writes `lastDriveModeActive = active` atomically
3. `syncDriveCamera` is called from `updateUIView` at line 333-337 on every SwiftUI render cycle
4. `regionDidChangeAnimated` (line 864) does NOT call `syncDriveCamera` directly — it only updates the region binding via `onRegionChanged`
5. `updateUIView` is what calls `syncDriveCamera`, and the guard ensures it is a no-op on the second+ call with the same active value

The `testNoFeedbackLoop_multipleUpdateUIView_syncDriveCameraCalledOnce` test is not vacuous: it explicitly sets altitude to 50,000 between each call (simulating a regionDidChangeAnimated feedback event) and asserts the altitude stays at 50,000 after the subsequent syncDriveCamera call — proving the guard fires. The first transition DID reduce altitude (asserted at line 395).
