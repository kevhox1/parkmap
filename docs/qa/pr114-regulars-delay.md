## Summary

This migration does exactly what it says: it rewrites `04`'s live trigger's WHEN clause (function body untouched) and adds a race-safe, fail-open sweep that makes the Regulars head start real. I stood up a scratch Postgres 16, applied the full `01→...→07→09→08` chain, and drove an exhaustive truth table (13 pin shapes) comparing PRE-09 and POST-09 behavior byte-for-byte — every case outside "leaving_soon + positive head start" is provably identical, confirming zero regression to the live crowd-push pipeline. I live-reproduced the sweep's core mechanics (elapse-triggers-push, second-run-is-no-op, expires-before-elapse-skipped-forever, **and** resolved-before-elapse-skipped-forever — the latter not explicitly claimed or tested by the builder, added independently), a genuine two-session `FOR UPDATE SKIP LOCKED` interleaving (one row locked by session A is correctly skipped by session B and picked up by a later run — no double-dispatch, no lost pin), and per-row fail-open (a poisoned dispatch doesn't abort the rest of the sweep). The `'30 seconds'` pg_cron syntax claim checks out against both pg_cron's own upstream changelog (1.5.0, Feb 2023) and Supabase's own Cron quickstart doc, which uses the identical `'30 seconds'` literal in its own example.

The one real problem: `sweep_leaving_soon_zone_push()` is created in the `public` schema (PostgREST-exposed) with no explicit `REVOKE EXECUTE FROM PUBLIC` — Postgres grants EXECUTE to PUBLIC by default on function creation, and I confirmed live that both `authenticated` and `anon` roles can call it directly (`select public.sweep_leaving_soon_zone_push();` succeeds under `set role anon`), directly contradicting the file's own stated design ("Not exposed to anon/authenticated via PostgREST"). The file's cited precedent (`internal.invoke_film_permit_ingest()`) is actually safe for a different reason than the one it credits — it lives in the `internal` schema, which PostgREST doesn't expose, not because of its GRANT statement. This PR copied the surface-level grant convention without the schema placement that makes it actually work.

## Findings

### 🔴 Blocking

- **#1: `sweep_leaving_soon_zone_push()` is callable by any anon-key holder, contradicting its own stated design**
  - Where: `supabase/09-regulars-zone-push-delay.sql:224` (function definition, `create or replace function public.sweep_leaving_soon_zone_push()`) and `:314` (`grant execute on function public.sweep_leaving_soon_zone_push() to postgres;`)
  - What: The function is created in the `public` schema with no `REVOKE EXECUTE FROM PUBLIC` anywhere in the file. PostgreSQL grants `EXECUTE` to `PUBLIC` by default on function creation — the file's `grant ... to postgres` is additive, not a replacement, so `PUBLIC` (which includes `anon` and `authenticated`, both PostgREST-exposed) retains it. Confirmed live on the scratch DB: `pg_proc.proacl` for this function reads `{=X/postgres,postgres=X/postgres}` — the bare `=X` entry is PUBLIC's retained EXECUTE grant. Reproduced directly: `set role anon; select public.sweep_leaving_soon_zone_push();` returns successfully with no error. On the real project, this is reachable by anyone via `POST /rest/v1/rpc/sweep_leaving_soon_zone_push` using nothing but the public anon key (which ships in every client build and is not a secret).
  - Expected: Per the file's own comment (line ~307-310): *"Grant execute to postgres only... Not exposed to anon/authenticated via PostgREST: there is no product reason for a client to trigger this sweep on demand."* This is the correct intent — it's just not what the file actually does.
  - Why it matters: the function is `SECURITY DEFINER`, reads `vault.decrypted_secrets`, and issues real `net.http_post` calls carrying the service-role key to `send-community-push` for every currently-eligible pin, system-wide (bypassing RLS via SECURITY DEFINER). The blast radius is bounded (no data is returned to the caller; `zone_pushed_at`'s idempotency check means repeat calls can't double-dispatch for the same pin), but it is a genuine, unauthenticated-adjacent surface for: (a) unlimited, rate-unlimited full-table scans of `pins` triggered by any anon-key holder, and (b) forcing early dispatch of an already-scheduled action ahead of the cron's own cadence, at will, for every user's pins, not just the caller's own.
  - Root cause: the file's own comment credits `internal.invoke_film_permit_ingest()` (`02d-ingest-cron.sql`) as "the same convention" — but that function is actually safe for a *different* reason: it lives in the `internal` schema, which this repo has established throughout (`04`, `08`, `02d`) specifically as the "PostgREST does not expose this" boundary. That function's `pg_proc.proacl` has the *identical* bare `=X` PUBLIC-retained grant (confirmed live) — it's just harmless there because of schema placement, not the grant statement. `09` copied the surface-level grant line without the schema placement that makes the precedent actually work.
  - Repro:
    ```sql
    set role anon;
    select public.sweep_leaving_soon_zone_push();  -- succeeds, no error, on the file as written
    ```
  - Fix (either is sufficient; recommend (a) for consistency with the established, already-safe convention):
    - (a) Create the function as `internal.sweep_leaving_soon_zone_push()` instead of `public.sweep_leaving_soon_zone_push()`, and update the `cron.schedule(...)` command string to match (`select internal.sweep_leaving_soon_zone_push();`). `internal` schema already exists by this point in the chain (created idempotently by `04`/`08`).
    - (b) Keep it in `public` but add `revoke execute on function public.sweep_leaving_soon_zone_push() from public;` before the existing `grant ... to postgres;` line.
  - Owner: `@backend-data`

## The partial-ceremony-state walk (stated plainly)

Because **no client code path exists yet to set a non-null `regulars_head_start_seconds` or to build a `regular_edges` row** (S5, the iOS model/service layer, hasn't shipped), every intermediate ceremony state below is behaviorally inert for real users today — the only way to exercise the new code paths right now is a deliberate manual test-script insert. This safety net evaporates completely the moment S5 ships, which is exactly why the documented order still matters going forward, not because of any live risk today.

1. **07 applied, nothing else.** `pins.regulars_head_start_seconds`/`zone_pushed_at` exist but are inert — `04` is still the original trigger. Safe (additive schema only, already established by S1's own ceremony notes).
2. **07 + 09 applied, Edge Functions not yet deployed, 08 not applied.** `04`'s WHEN clause is now rewritten; the sweep and its cron job are live. Since no real pin has a non-null head start yet, this is byte-identical to today's production behavior for every real user. The cron job runs its (cheap, empty) scan every 30s with no candidates. Safe.
3. **07 + 09 applied, `send-regular-push` deployed + `send-community-push` redeployed, 08 NOT yet applied.** The Edge Functions exist but no trigger invokes `send-regular-push` yet (08 not applied) — a `leaving_soon` insert, even with a head start, gets no Regulars push, only the (correctly-deferred) zone push once the sweep catches it. `send-community-push`'s redeploy is claimed behavior-preserving (verified by PR #112's QA via a `tsc` structural diff, not re-verified in this pass). Safe.
4. **07 + 09 + 08 all applied, Edge Functions deployed.** Fully live, intended end state: a real head-start pin now fires the immediate Regulars push and the deferred zone push, closing PR #112's dual-push window exactly as designed.
5. **The one genuinely dangerous ordering, which the roadmap correctly warns against:** applying `08` / deploying `send-regular-push` **before** confirming `09`'s cron job is actually registered and running. If the sweep silently failed to register (e.g., a `pg_cron` extension hiccup) while `08` went live anyway, a head-start pin would get its immediate Regulars push but would **never** get a zone-wide push at all — a real, silent regression, not just an inert feature. This is exactly why the roadmap's explicit verification step ("confirm the sweep cron job is registered and has swept at least one test pin") must not be skipped — it is the one step in the whole ceremony that is load-bearing rather than just sequencing hygiene.
