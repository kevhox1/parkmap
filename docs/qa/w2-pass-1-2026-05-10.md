## Findings

### Blocking

None.

### Significant

**#1: `rebuildSegments` uses stale closure-captured region, not current visible region**
- Where: `TileLoader.swift`:105 — `rebuildSegments(forKeys: tileKeys(forRegion: region))`
- What: `region` is captured at the time `loadTiles(forRegion:)` is called. After the async TaskGroup finishes decoding (which may take tens to hundreds of milliseconds for a large tile set), `rebuildSegments` is called with the keys for the _old_ region. If the user panned to a new region during decoding, a second `loadTiles` call has already finished and set `segments` to the new view. The first Task then completes and overwrites `segments` with the stale set — tiles from the old viewport only — until the next camera-change event triggers a fresh load.
- Expected per spec: visible segments should always reflect the current viewport after tiles finish loading. The stale overwrite can cause visible blocks to momentarily disappear on fast panning.
- Repro: Pan map rapidly across Manhattan at zoom 15. After panning stops, the polylines for the new viewport may briefly disappear, replaced by the prior viewport's tiles, then re-appear when the next `.onEnd` fires.
- Fix direction: Track a `currentRegion` property on `TileLoader`; in the Task closure, replace `tileKeys(forRegion: region)` on line 105 with `tileKeys(forRegion: currentRegion)` so that `rebuildSegments` always reconstructs from the current viewport's keys (all of which are already in cache by that point). Owner: `@ios-engineer`.

### Minor / nit

**#2: `loadIndex()` performs synchronous file I/O on the main actor during `init()`**
- Where: `TileLoader.swift`:112-126 — `Data(contentsOf: url)` called synchronously inside `loadIndex()`, which is called from `init()` of a `@MainActor` class.
- What: `index.json` is 111 KB. Reading it synchronously on the main thread is ~1ms on a modern device (SSD-backed bundle) but violates Apple's concurrency guidelines. Under severe system load (first-launch, other background activity) it could contribute to the <2s launch target missing.
- Expected: Non-blocking resource loading preferred for main-actor types.
- Repro: Not reliably reproducible in normal conditions; only a concern under memory pressure.
- Note: Not blocking for an MVP TestFlight build. Can be deferred to W8 if launch time stays comfortably under 2s.
- Owner: `@ios-engineer`.

**#3: `import SwiftUI` appears at the bottom of `Segment.swift` (after the type declaration)**
- Where: `Segment.swift`:94
- What: `Color` is referenced in the `polylineColor` computed property at line 76, but `import SwiftUI` appears at line 94. Swift processes all imports before compilation so this compiles correctly, but the ordering is non-idiomatic and could confuse readers.
- Expected: imports at the top of the file.
- Owner: `@ios-engineer`.

**#4: `TileLoader` is `@MainActor final class` but `tileKeys()` does purely computational work on the main actor**
- Where: `TileLoader.swift`:155-185
- What: `tileKeys()` runs a nested loop over `rowMin..rowMax x colMin..colMax` (up to ~10x10 = 100 iterations at zoom 14 with buffer=2), entirely on the main actor. This is negligible CPU work but is in the critical path of every camera-change event. Not a perf problem at current tile density; flag for awareness if buffer is ever increased significantly.
- Owner: `@ios-engineer`.

### Out of scope (logged, not fixed)

**#5: No visual verification of polyline color correctness on device**
- The code path for color selection (`dominantCategory?.swiftUIColor ?? Color.gray.opacity(0.4)`) is correct per reading. Whether the colors are visually distinguishable and match Kevin's expectations requires a real device smoke. Recommended before W4 merges.

**#6: Stress test on real device (spec §7 R1) not yet done**
- Rendering 12k–40k colored polylines on MapKit `Map { }` at zoom 14–18 over Manhattan is unproven at this density. The architecture (visible-bounds culling, zoom threshold, `.onEnd` frequency) is the right mitigation. Actual frame rate measurement on iPhone 12 or iPhone 17 device required per spec R1 before proceeding past W4.

**#7: `description` property on `ParkingRule` shadows `CustomStringConvertible.description`**

However, if `CustomStringConvertible` conformance is added in the future (e.g., for debugging), this property would become the `description` override. Minor naming consideration for W3.

## What's working

- The `Bundle.main.url(forResource:withExtension:)` pattern is used consistently and correctly in both `loadIndex()` and `decodeTile(key:)`. The W1a QA finding #1 about the flat-bundle layout was clearly read and heeded — the comment on lines 17-20 of `TileLoader.swift` is a good guard for future engineers.
- Concurrency model is sound: `decodeTile(key:)` is `nonisolated async` (runs off main actor on the cooperative thread pool), cache writes happen back on `@MainActor`, no data races exist.
- The `tileSet` lookup prevents requesting non-existent tile files (the tile grid has gaps across Manhattan), and failed decodes are cached as empty arrays (`[]`) to prevent infinite retry on every pan. Both are correct behaviors.
- All 12 Category enum raw values match the JS `CATEGORIES` object keys character-for-character, including the subtle ones (`ASP_OVERNIGHT_TTHS` vs variants). The `priority` values also match the JS.
- The zoom-threshold constant (`0.1°`) is well-chosen (~11km, well above any street-level zoom) and accompanied by an inline comment explaining the rationale.
- `Segment.polylineColor` falls back to `Color.gray.opacity(0.4)` when `dominantCategory` is nil — matching the `UNKNOWN` case — which is the correct behavior for the small number of edge segments the build script might not classify.
- `.onEnd` camera frequency is the right choice. `.continuous` would fire dozens of times per second during a pan gesture, calling `loadTiles` and the `tileKeys()` loop on every frame.
