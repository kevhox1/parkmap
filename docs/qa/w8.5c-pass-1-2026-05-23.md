## Findings

### Significant

**S-1: AC-DM.23 / R-3 — One-time background location limitation note not implemented**

- Where: `ContentView.swift` `onChange(of: driveModeActive)` block (approx lines 516–540); no `UserDefaults`-gated one-time alert exists anywhere in the codebase
- What: Spec §7 R-3 explicitly requires: "W8.5c should add that note as a `UserDefaults`-gated one-time alert on first Drive Mode start." Master spec §10 AC-DM.23 states: "if not granted [Always permission], a one-time informational note explains this limitation on first Drive Mode use." Neither a `UserDefaults` key for this gate nor any alert tied to first Drive Mode start exists. The muted-voice toast IS present (OQ-3), but the background-limitation note is absent.
- Expected: On first-ever Drive Mode activation, a one-time alert (or toast) explains that parking commentary stops if the app is backgrounded during navigation (requires "When in use" permission, foreground only in W8.5c). Gated by a `UserDefaults` flag so it shows exactly once.
- Impact: Not a crash or data-loss risk. Users who background the app during a drive session will silently lose GPS and commentary with no explanation. This is particularly jarring for first-time users who may background the app to answer a call. The spec identified this as a required UX disclosure.
- Repro: First Drive Mode session → background app mid-drive → location commentary silently stops.
- Owner: `@ios-engineer` — add `UserDefaults` key (e.g., `wepark_dm_bg_note_shown`); show a one-time alert or toast in the `driveModeActive = true` onChange path if the key is not yet set.

### Minor

**M-1: Auth gate reads `CLLocationManager().authorizationStatus` twice via a transient instance instead of using `locationService.authorizationStatus`**

- Where: `DriveModeDestinationView.swift:202, 408`
- What: `handleStartDriveTap()` creates `CLLocationManager()` to read `.authorizationStatus` directly, bypassing the injected `locationService`. A second transient `CLLocationManager()` is also created inside the `.onChange(of: locationService.isAuthorized)` handler when authorization resolves to false. `CLLocationManager().authorizationStatus` works correctly in production (system-level read), but bypasses the injectable seam introduced by M-2 — meaning auth gate tests cannot simulate a `denied` status by swapping the `LocationService`.
- Expected: Auth status read from `locationService` directly (e.g., via an exposed `authorizationStatus: CLAuthorizationStatus` property, or at minimum via the existing `isAuthorized: Bool`).
- Impact: The `testStartDrive_denied_showsAlert` test (Auth gate test 2) cannot actually simulate `authorizationStatus == .denied` through the `LocationService` seam — it only verifies the view doesn't crash when `userLocation == nil`, not that the denied alert actually fires. The real denied path is code-covered but only verifiable in manual smoke.
- Owner: `@ios-engineer` — expose `authorizationStatus: CLAuthorizationStatus` on `LocationService` (already has `isAuthorized: Bool`; adding the raw status property is a 3-line change) and update `handleStartDriveTap()` to use it.

**M-2: `testDrivingContext_blockChange_callsSpeak` does not assert `speakCallCount == 2` on block-B change**

- Where: `W85cTests.swift:290–295`
- What: The test's block-B call only asserts `service.currentContext?.street == "BROADWAY"` (context changed) but does not assert that `mockVoice.speakCallCount == 2` (voice was called). The inline comment explains this is intentional because the 12-second voice min-gap guard would suppress the call in CI (test runs in <1ms). However, this means the test verifies block detection but not the voice-call path for block transitions beyond the first one.
- Expected: Either (a) reset `lastSpokenAt` on the service between calls (via a `#if DEBUG` escape hatch), or (b) a separate test that bypasses the min-gap guard and asserts speakCallCount on block change to B.
- Impact: The block-change → voice path for the second transition is covered by code inspection but not by assertion. Regression in `speakContext()` after a block change would not be caught by automated tests.
- Owner: `@ios-engineer` — advisory for W8.5d when voice frequency calibration is revisited.

**M-3: Test 6 comment/name mismatch in `testDrivingContext_sideRelativeToHeading_east_facingNorth`**

- Where: `W85cTests.swift:308`
- What: The function comment says "Heading east (90°), side E → right" but the test body uses `heading: 0` (north). The spec says "heading 0 (north), segment side 'E' → right" which matches the test body. The comment is incorrect, not the test logic. The function name `east_facingNorth` is also ambiguous (reads as "east-side when facing north" which is correct, but the leading comment says the opposite).
- Impact: Cosmetic — test logic is correct per spec. Would confuse a future engineer reading the test.
- Owner: `@ios-engineer` — nit, fix comment.

**N-2: `testDrivingVoice_speak_configuresCorrectRate` is a constant-value assertion, not a synthesizer-behavior test**

- Where: `W85cTests.swift:432–438`
- What: Test asserts `AVSpeechUtteranceDefaultSpeechRate == 0.5` (a framework constant check, not a unit behavior test). It does not verify that `DrivingVoice.speak()` actually sets the utterance rate to that value. The utterance is not easily introspectable without AVSpeechSynthesizer hooks.
- Impact: If the `DrivingVoice.speak()` implementation changed `utterance.rate` to a different value, this test would still pass. The spec requires `AVSpeechUtteranceDefaultSpeechRate` explicitly; the code uses it correctly (line 87), but the test does not verify the code path.
- Owner: `@ios-engineer` — advisory. Fully covering this would require a spy/mock on AVSpeechUtterance, which is not straightforward. The code-inspection path is reliable here; document the limitation in the test comment.

**N-3: `DrivingContextService` is re-instantiated on every Drive Mode entry**

- Where: `ContentView.swift:524–526`
- What: `let service = DrivingContextService(voice: drivingVoice)` creates a new instance each time `driveModeActive` flips to true. This resets `lastBlockKey` and `lastSpokenAt`, so the first block encountered after re-entering Drive Mode always triggers a voice cue (good) and the min-gap resets (also reasonable). However, if the user exits and re-enters Drive Mode rapidly (e.g., accidental tap), the service is recreated and the block history is lost.
- Impact: Correct behavior in the common case. Minor UX edge case only.
- Owner: `@ios-engineer` — no action required unless drive-test feedback reveals an issue.

## Engineer's Unilateral Decisions — Audit

**1. `DrivingVoice` is non-`final` to allow `MockDrivingVoice` subclassing in tests.**
Acceptable. The `@Observable` macro on a non-`final` class is valid; Swift's observation machinery does not require `final`. The mock subclass overrides `speak(_:)` with a capturing implementation, which is a standard testing pattern. The risk (unintended override semantics) is low because `DrivingVoice` is not part of a public API. The engineer's comment in the class header documents the rationale. No objection.

**2. `pickBestParkingAwareRoute` converted from static to instance method on `RouteServicing` protocol, delegating to the static implementation.**
Correct call. Tech-lead recommended this in spec §4 step 2: "make it an instance method on the protocol; the conforming class can still call the static implementation internally." `RouteService.swift:168–175` — instance method delegates to `RouteService.pickBestParkingAwareRoute(routes, ...)`. Static method preserved for internal use. Protocol conformance is clean. `testRouteService_conformsToRouteServicingProtocol` verifies the concrete type is usable as `any RouteServicing`.

**3. Manual `enumerated().filter` in `RecentDestinationsStore.delete(at:)` instead of `Array.remove(atOffsets:)` (SwiftUI-only).**
Correct call for a pure service file. `Array.remove(atOffsets:)` is a SwiftUI extension method (`import SwiftUI` required). The manual pattern is functionally equivalent: both remove elements at the specified `IndexSet` positions, preserving relative order of remaining elements. `testRecentDestinationsStore_delete_worksWithManualIndexFilter` confirms the behavior. The comment in the source explains the rationale. No objection.

**4. `AudioSessionManager.activateDriveSession()` called BOTH in `ContentView.onChange(of: driveModeActive)` AND in `DrivingVoice.speak(_:)` before each utterance.**
Redundant but harmless. The spec's intent was per-utterance activation (AC-W85c.17: "When `DrivingVoice.speak(_:)` is called, AVAudioSession is activated..."). Calling it at Drive Mode start too is belt-and-suspenders. `AVAudioSession.setActive(true)` on an already-active session is a no-op per Apple documentation. Not a bug; the per-utterance call in `speak(_:)` satisfies the AC.

**5. `DrivingContextService` re-instantiated on each Drive Mode entry (rather than a singleton or persistent instance).**
Acceptable for W8.5c. Resets block history cleanly on each session start. W8.5d will need to reconsider if session continuity across Drive Mode pause/resume is desired. Logged as N-3 above.
