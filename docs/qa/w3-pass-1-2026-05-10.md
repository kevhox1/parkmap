**Verdict:** SHIP WITH CAVEATS

## Summary

The build is clean (app target and test target both succeed on Xcode 26.4.1 / iPhone 17 simulator). All 5 R2 boundary cases are tested and 41 of 42 tests pass. The one failing test (HP-11: ASP skip-to-next) has a **wrong assertion in the test**, not a bug in the engine — the engine correctly returns 19.5 hours to May 19 (Tuesday, not suspended), and the test comment erroneously focused only on the next Friday, forgetting that ASP_TUE_FRI also applies to Tuesdays. The engine logic itself is correct. Two significant findings prevent a clean ship-it: (1) the failing test needs its assertion corrected before the test suite is trustworthy as a regression gate, and (2) the spec's AC-3 parity requirement calls for 10 sample-block categories including a bare FREE block returning `"Free"` — no test covers that case. No blocking findings.

### Significant

**#1: HP-11 test assertion wrong — test suite reports a failure**
- Where: `ios/WePark/WeParkTests/ParkingRulesEngineParityTests.swift:564` — `testHP11_ASPSuspendedSkipToNext`
- What: The test asserts `result.hours > 186.0` but the engine returns 19.5. The engine is correct: `ASP_TUE_FRI` applies to both Tuesdays and Fridays. From Mon May 18 noon, the next non-suspended ASP_TUE_FRI day is Tue May 19 (not suspended) at 7:30am — 12h to midnight + 7.5h = 19.5h. The test comment focuses only on "the next Fri May 22" and ignores May 19 Tuesday entirely. The assertion bound `> 186` is wrong; the correct assertion is approximately `result.hours > 19.0 && result.hours < 20.0`, and the test comment needs rewriting to acknowledge May 19 as the first non-suspended day. The `isSuspended` assertions for May 24/25 within the same test pass correctly.
- Expected per spec: test suite should pass with zero failures before merge.
- Repro: `xcodebuild test` — `HappyPathParityTests.testHP11_ASPSuspendedSkipToNext` fails with `XCTAssertGreaterThan failed: ("19.5") is not greater than ("186.0")`.
- Owner: `@ios-engineer`

**#2: AC-3 missing case — no test for bare FREE-category segment returning `"Free"`**
- Where: `ios/WePark/WeParkTests/ParkingRulesEngineParityTests.swift` — no HP test exercises `Category.free`
- What: The spec (§6 AC-3) requires parity tests covering "a FREE block." The engine's final fallthrough returns `SafetyLabel(text: "Free", severity: .free)` for any segment where no restriction is found — but no test actually constructs a segment with `rules: [rule(category: .free, ...)]` and asserts the output is exactly `"Free"`. The PWA returns `{ text: 'Free', severity: 'free' }` for this case; the Swift code matches, but it is untested.
- Expected per spec: AC-3 test coverage must include a FREE block.
- Repro: Any segment with a single `.free` rule should return `"Free"` — confirmed by code-tracing (the `dom == .metered` branch is skipped, `restriction.hours == 168` sentinel, falls through to `return SafetyLabel(text: "Free", ...)`), but there is no test asserting this.
- Owner: `@ios-engineer`

**#3: Tests use reasoning-based expected strings, not PWA-captured strings**
- Where: All of `HappyPathParityTests` and `TimeLabelFormatTests`
- What: The spec §4.3 says "the Swift `safetyLabel(...).text` must exactly equal the JS `actionableSafetyLabel(...).text` for the same input." The tests assert expected values that were hand-reasoned (e.g., `"No standing"`, `"paid until 7pm"`, `"Tomorrow 7:00 AM"`) but were not captured by running the live PWA at the same inputs. The format reasoning appears correct, but there are subtle platform differences that could diverge in the field (e.g., locale-dependent AM/PM spacing, Node.js vs iOS Foundation date formatting under en-US locale).
- Expected per spec: Strings should be verified against actual PWA output on the same segment data at a fixed wall-clock time before W4 signs off.
- Repro: Not a failing test — a verification gap. Recommend: load a handful of real tile segments in browser console, call `actionableSafetyLabel()` at a fixed time, and assert those exact strings in a dedicated "live parity snapshot" test.
- Owner: `@ios-engineer`

**#4: `ContentView` timer deviation from palette doc §2.2**
- Where: `ios/WePark/WePark/ContentView.swift:81-86` — `Timer.publish(every: 60, ...)`
- What: The palette doc §2.2 says recompute color "when the app enters foreground; when the map camera region settles... not on a timer." The implementation adds a 60-second timer tick. This is not strictly wrong — the timer ensures colors stay current when the app is open without camera movement — but it is an unreviewed deviation from the spec. Also note the palette doc's recompute guidance is silent about "app stays open and idle for minutes" so the timer is arguably a valid fill for that gap. The concern is the spec says "not on a timer" explicitly.
- Expected per spec: Clarify with Kevin / @designer whether a 60s timer on the main thread is acceptable, or whether an `.onAppear` + camera-change trigger is sufficient.
- Owner: `@ios-engineer`

### Minor / nit

**#5: Double `currentState` call per segment per render frame**
- Where: `ContentView.swift:104-107`
- What: `engine.currentStateColor(for: segment, at: now)` calls `currentState()`, then `engine.currentState(for: segment, at: now)` is called again on line 107 to check `== .meteredActive`. Each call re-executes `nextRestriction()` which walks the rule set. For 40,000+ segments this doubles computation per render cycle.
- Expected: A single call to `currentState()`, storing the result in a `let`, then deriving both color and `isMetered` from it.
- Repro: Not observable at current segment counts but worth fixing before stress testing.
- Owner: `@ios-engineer`

**#6: `formatMinutes` edge case at midnight (minute = 0)**
- Where: `ParkingRulesEngine.swift:582-591`
- What: `formatMinutes(0)` returns `"12am"` (h12 = ((0 + 11) % 12) + 1 = 12, ampm = "am"). The JS `fmt(0)` also produces `"12am"` (h = 0, h12 = 12). These match. However `formatMinutes(720)` = `"12pm"` (noon). Verify against the JS: h=12, ampm="pm", h12=((12+11)%12)+1=12. Match. Edge case is fine but worth noting for anyone who reads the function.
- Owner: none (informational)

**#7: No test for `meteredStatus` "Metered (free)" path (no upcoming meter)**
- Where: `ParkingRulesEngineParityTests.swift` — HP-6 and HP-7 cover "paid until" and "free until" but not the "Metered (free)" case (no metered rule at all, or a METERED rule with days=[7] that never fires).
- Expected: A test asserting `meteredStatus` returns `"Metered (free)"` for a metered segment with no upcoming activation.
- Owner: `@ios-engineer`

**#8: No accessibility labels on `MapPolyline` in ContentView**
- Where: `ContentView.swift:108` — `MapPolyline(coordinates: coords).stroke(...)`
- What: Palette doc §5.1 requires every `MapPolyline` annotation carrying severity color to have a `.accessibilityLabel` on the tap target. The polyline rendering in ContentView has no `.accessibilityLabel` or `.accessibilityHint`. This is deferred to W4 (when tap interaction is built), but it should be tracked.
- Expected per spec (palette §5.1): `.accessibilityLabel("Metered parking. Tap for details.")` style label on each tappable polyline.
- Owner: `@ios-engineer` (W4 scope)

## What's working

- The ASP_DAILY day-mask fix is present and correct. The W2 bug (`return true` for all 7 days) is replaced with `return dayOfWeek >= 1 && dayOfWeek <= 6`, matching the JS and the NYC DOT rule that Sunday is never an ASP cleaning day.
- The 14-day walker in `computeHoursUntilASP` constructs real `Date` objects (not day/minute integers) for the offset dates, which is the correct approach for suspension-skipping across month and year boundaries. The R2 requirement was specifically about this, and BC2 (end-of-month) and BC3 (start-of-year) pass.
- The `nearFutureWindow` is a named constant at 24 hours — tunable per spec recommendation. No magic number.
- Zero `Calendar.current` usage. The constraint from spec §4.3 ("All time math is in America/New_York TZ") is fully respected. The comment on line 19 of ParkingRulesEngine.swift ("Never use Calendar.current") reads like a guard rail for future engineers — good practice.
- `ASPSuspensionService` correctly uses `Bundle.main.url(forResource:withExtension:)` with no subpath construction. The W1a QA finding #1 comment is explicitly cited at the top of the file. The degradation path (empty dictionary + console warning) is clean.
- The W2 `swiftUIColor` static-category path is fully removed from both `Category.swift` (property deleted, `import SwiftUI` replaced with `import Foundation`) and `Segment.swift` (`polylineColor` property removed, `import SwiftUI` removed). The dead code path is gone, not just commented out.
- `ContentView`'s timer-based recompute (once per minute) is sensible for production use: parking rule windows are at minimum 30 minutes wide, so a 60-second tick is fine granularity. The implementation also re-evaluates on `onAppear`, so the initial render is correct.
- The `SuspensionBannerState` enum with `todaySuspended(reason:)` / `tomorrowSuspended(reason:)` / `aspInEffect` is clean API for the W7 `ASPBanner` view. W7 can be built without touching the service.
- The test infrastructure (`makeSegment`, `rule`, `etDate` helpers) is reusable and correct. Constructing `Segment` via JSON round-trip (encode → decode) is a clever workaround for a struct with no memberwise initializer exposed to the test target.
- All 42 tests ran successfully in the sandbox — the build agent's "simulator boot failed" concern was specific to their run; the sandbox had capacity in this QA pass.
