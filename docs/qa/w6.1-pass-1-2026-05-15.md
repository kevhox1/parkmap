## Summary

The core fix is correct: replacing `PassthroughSubject<UUID, Never>` with `@Published var
pendingDeepLinkCarID: UUID?` on `AppDelegate` + `ObservableObject` conformance eliminates
the event-drop race. `@ObservedObject` on `ContentView` is the right choice given
`@UIApplicationDelegateAdaptor` owns the AppDelegate instance. The dual-path routing
(`.onChange(of: pendingDeepLinkCarID)` for foreground/background-wake +
`.onChange(of: scenePhase) { .active }` for cold-kill) is correctly wired and idempotency
is properly implemented (clear before route). The test suite ran 78/0 (passed/failed)
independently. Two findings are filed: one significant (test file header comment contradicts
the actual implementation and mis-states what is covered), one minor (stale `import Combine`
comment in ContentView header is inaccurate about what Combine is still used for). No blocking
issues.

### Significant

**#1: Test file header contradicts production code on mismatched-carID behavior; cold-kill
path (scenePhase=.active) has no test.**

- Where: `W61Tests.swift` lines 19–21 (header comment); test suite generally.
- What (contradiction): The header states "Mismatched car ID leaves pendingDeepLinkCarID
  non-nil until explicitly cleared (the guard in routePendingDeepLink handles mismatches —
  the buffer must not auto-clear on mismatch, since the guard clears it in all branches)."
  This is internally contradictory and factually wrong. The actual production code
  (`ContentView.swift:793`) clears `pendingDeepLinkCarID = nil` BEFORE the second guard
  that checks `car.id == carID`. On a mismatch, the buffer IS cleared (line 793 runs, then
  the second guard fails, so no sheet presents but the buffer is gone). The header says the
  buffer "must not auto-clear on mismatch" — the opposite of what the code does. The code's
  behavior is correct; the comment is wrong.
- What (coverage gap): No test in W61Tests.swift exercises the mismatch path as implemented.
  `testW61_4` simulates the route logic with `guard buffered != nil` (not the real guard
  `guard let car = parkPinService.parkedCar, car.id == carID`), so it does not cover the
  actual mismatch scenario.
- What (cold-kill coverage gap): `testW61_2` tests `@Published`'s Combine subscriber behavior
  (current value emitted immediately on `.sink` subscription). The production cold-kill path
  uses SwiftUI `.onChange(of:)`, which does NOT emit on initial value. The test verifies a
  property of Combine that is not the mechanism the production code relies on. The actual
  cold-kill mechanism — the `scenePhase == .active` path in
  `.onChange(of: scenePhase)` — has no test.
- Expected per spec AC #6: Tests should cover the cold-kill replay behavior and the
  mismatched carID path as they are actually implemented.
- Impact: The mismatched-carID behavior works correctly in production (buffer is cleared, no
  sheet, no stuck state). The cold-kill behavior also works correctly in production (the
  scenePhase path is wired). The tests just do not cover these paths in the way the header
  claims they do, and one comment is misleading to future readers.
- Repro (misleading comment): Read `W61Tests.swift` lines 19–21 alongside
  `ContentView.swift:790–796`. The comment says the buffer is not auto-cleared on mismatch;
  the code auto-clears it unconditionally.
- Severity: Significant (not blocking — production behavior is correct; tests pass; but
  test coverage gaps and a wrong comment impair future maintainability).
- Owner: `@ios-engineer`

### Minor / Nit

**#2: `ContentView.swift` header comment at line 61 is subtly inaccurate about `.onChange`
semantics.**

- Where: `ContentView.swift` line 385: comment reads "reads it via `.onChange(of:)`, which
  fires as soon as the value changes — including when SwiftUI first attaches the modifier
  after a cold launch."
- What: The phrase "including when SwiftUI first attaches the modifier after a cold launch"
  is misleading. SwiftUI's `.onChange(of:)` in iOS 17 does NOT fire on initial value. The
  cold-launch path is handled by the scenePhase=.active handler, not by this modifier. The
  comment could mislead a future engineer into thinking the value-onChange alone handles the
  cold-kill case.
- Expected: The comment should accurately distinguish the two paths: (a) `.onChange(of:
  pendingDeepLinkCarID)` covers the foreground and background-wake cases, (b)
  `.onChange(of: scenePhase) { .active }` is the cold-kill handler.
- Impact: Documentation only; production behavior is correct.
- Owner: `@ios-engineer`

### Out of Scope (Logged, Not Fixed)

- **Residual timing edge case (background-wake):** In the background-wake scenario, there is
  a race between when `DispatchQueue.main.async { pendingDeepLinkCarID = carID }` executes
  vs when `scenePhase == .active` fires. If `.active` fires before the async block runs, the
  scenePhase path sees nil (no-op) and the value-onChange path later picks it up correctly.
  If the async block runs first, the value-onChange path handles it and the scenePhase path
  is a nil no-op. Both orderings are safe by the clear-first idempotency. However, the exact
  timing relative to the system's scene lifecycle has not been verified on a real device. This
  is the same limitation flagged in W6 and is not a regression.
- **Notifications for metered/other categories:** Unchanged from W6 deferral.
- **VoiceOver swipe-through-blocks:** Unchanged from W4 carry-over.

## High-Risk Cross-Check Results

### A. `@ObservedObject` vs `@StateObject` for AppDelegate

**Result: Correct.** `AppDelegate` is declared with
`@UIApplicationDelegateAdaptor(AppDelegate.self) var appDelegate` in `WeParkApp.swift`
(line 98). The `@UIApplicationDelegateAdaptor` property wrapper acts as the owner/storage for
the delegate instance (equivalent role to `@StateObject`). When `AppDelegate` conforms to
`ObservableObject`, SwiftUI automatically propagates it through the environment. `ContentView`
receives the instance via its initializer parameter `appDelegate: appDelegate` (line 102) and
observes it with `@ObservedObject var appDelegate: AppDelegate` (ContentView line 115).
`@ObservedObject` is correct here — ContentView does not own the instance.

### B. Thread safety of `pendingDeepLinkCarID` write

**Result: Correct.** The delegate callback `didReceive` is called on an arbitrary thread
(UNUserNotificationCenter dispatch queue). The write to `pendingDeepLinkCarID` is wrapped in
`DispatchQueue.main.async { [weak self] in self?.pendingDeepLinkCarID = carID }` at
`WeParkApp.swift:87–89`. This ensures the `@Published` mutation and the resulting SwiftUI
state update happen on the main thread. The `[weak self]` prevents a retain cycle if the
delegate is deallocated between the async dispatch and its execution (correct for a delegate).

### C. `.onChange(of:)` initial-value semantics in iOS 17

**Result: Confirmed; cold-kill path correctly handled.** iOS 17's `.onChange(of:)` does not
fire on initial value. The cold-kill scenario (value set before ContentView mounts) therefore
cannot be caught by `.onChange(of: appDelegate.pendingDeepLinkCarID)` alone. The
`.onChange(of: scenePhase) { newPhase == .active }` path at `ContentView.swift:314–321` is
the correct and sole mechanism for the cold-kill case. Both call `routePendingDeepLink(...)`.
Confirmed that the cold-kill path is correctly wired. The test coverage gap for this path
is filed as Finding #1.

### D. Triple-fire risk (foreground notification)

**Result: Safe; no double-route.** Traced through:

1. `pendingDeepLinkCarID` is written (non-nil) from the delegate.
2. `.onChange(of: pendingDeepLinkCarID)` fires with the new value → `routePendingDeepLink(carID)`:
   clears buffer to nil (line 793), then sets `activeSheet` (line 796). One route.
3. Setting buffer to nil triggers `.onChange(of: pendingDeepLinkCarID)` again with `nil`
   → `routePendingDeepLink(nil)` → `guard let carID else { return }` at line 791 fires.
   No route. Safe no-op.
4. `scenePhase` remains `.active` throughout (foreground notification). `.onChange(of:
   scenePhase)` does NOT fire. No third call.

The clear-before-route ordering (AC #4) correctly short-circuits all possible second-route
scenarios. Safe.

## What's Working

- **Root cause fix is correct and well-documented.** The `PassthroughSubject` → `@Published`
  change directly eliminates the event-drop race that caused the W6 smoke failure. The
  diff is minimal and surgical: 3 files, one conceptual change throughout.

- **Dual-path routing handles all three scenarios.** Foreground (value-onChange fires while
  app is active), background-wake (value-onChange fires as app transitions to active), and
  cold-kill (scenePhase=.active fires with buffered value already in place). Each scenario
  is covered by at least one of the two paths.

- **Idempotency is clean.** Clear-before-route ensures that even if both onChange paths fire
  in the same lifecycle event, the second call is always a no-op. No double-sheet-presentation
  is possible.

- **`@ObservedObject` choice is architecturally correct.** Given `@UIApplicationDelegateAdaptor`
  owns the AppDelegate instance, `@ObservedObject` in ContentView is the right tool. Using
  `@StateObject` would have been wrong (ContentView doesn't create the instance).

- **Test suite at 78/0 — independently verified.** First QA pass in this project where the
  `xcodebuild test` result was verified independently (prior W7 passes could not run the
  test suite due to Bash permission restrictions in that QA session).

- **No scope creep.** The PR touches exactly the three files described in the engineer's
  report. No W7 files were modified.
