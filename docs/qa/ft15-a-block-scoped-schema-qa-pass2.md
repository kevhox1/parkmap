## Findings

### 🔴 Blocking

- **#1: The rate-limit trigger's self-exclusion clause has no time-scoping — an attacker who reuses one fixed `report_group_id` forever is permanently invisible to the 3-per-24h counter, with no upper bound on repeat offenses.**
  - Where: `supabase/02f-block-scoped-restrictions.sql`, `enforce_block_scoped_rate_limit()`, the count query (lines ~485-491):
    ```sql
    select count(distinct report_group_id)
      into v_recent_count
      from public.pins
     where author_id = new.author_id
       and report_group_id is not null
       and report_group_id != new.report_group_id
       and created_at > now() - (v_window_hours || ' hours')::interval;
    ```
  - What: The `report_group_id != new.report_group_id` clause is meant to stop one legitimate multi-blockface submission (N rows, one shared group id, inserted in quick succession) from self-limiting as its own rows land one at a time. But the clause has no time bound of its own — it excludes **every** row the author has ever inserted under that same id, no matter how long ago, not just rows from "the current batch." Concretely: an attacker who always sends the exact same client-generated `report_group_id` (e.g. a single hardcoded UUID) on every `filming`/`construction` insert, forever, will have every one of those rows excluded from its own count check every single time — `v_recent_count` only ever counts *other, distinct* group ids the author has used, which stays at 0 as long as the attacker never varies the id. Nothing else in the file constrains how many rows can share one `report_group_id`, or requires distinct submissions to use distinct ids (that's purely a client-side convention the spec assumes, never enforced in SQL). This is a complete, permanent bypass of the "3 block-scoped reports per author per 24h" cap the spec calls **required** (§6 item 2, §11).
  - Expected: per spec §6.2/AC-S7, a 4th distinct report by the same author within 24h should be rejected. In practice, an attacker never needs a 4th *distinct* report at all — they can submit an unlimited number of fake closures under one id and never hit the cap.
  - Repro: as an authenticated (incl. anonymous-auth) user, pick one fixed UUID `X` once. Loop: `POST /rest/v1/pins {pin_type: 'construction', source: 'crowd', author_id: <self>, report_group_id: X, segment_id: <vary per target block>, expires_at: now()+interval '89 days'}` — every iteration succeeds; `v_recent_count` never exceeds 0 because every prior row sharing id `X` is excluded from its own count on every subsequent check. Each individual pin is still capped at ≤90 days by the (correctly-fixed) ceiling constraint, but the attacker can insert as many such pins, targeting as many blockfaces, as often as they like, with zero cooldown, indefinitely.
  - Note: this bug is not introduced by this revision — it was present, unexercised, in round 1 too (the self-exclusion clause is unchanged since the original commit). It's surfaced here because this pass was specifically scoped to adversarially test the fixed abuse controls rather than just read them, per the task's own instruction to check "the rate-limit trigger's DISTINCT-group counting."
  - Recommended direction (not a full design — leaving the fix to `@backend-data`): the self-exclusion needs to be scoped to "this batch," not "this id, ever." Options include time-bounding the exclusion itself (e.g. only exclude rows with the same `report_group_id` created within the last few minutes, treating that as "the batch currently landing"), or dropping id-based exclusion entirely in favor of a row-count-based or session-scoped batching signal that can't be replayed across days.
  - Owner: `@backend-data`

### 🟡 Significant

- **#2: The rate-limit trigger is `BEFORE INSERT` only; the pre-existing, unrestricted `pins_update_own` policy lets an author convert any of their own crowd pins into a rate-limit-exempt `filming`/`construction` report via `UPDATE`.**
  - Where: `supabase/02f-block-scoped-restrictions.sql` line ~503-505 (`create trigger pins_enforce_block_scoped_rate_limit before insert on public.pins ...`), interacting with the unmodified `pins_update_own` policy in `supabase/02-pins-schema.sql:151-154` (`for update using (auth.uid() = author_id) with check (auth.uid() = author_id)` — no column restrictions).
  - What: An author can (1) insert a cheap, unconstrained crowd pin of some other type (e.g. `block_note`, `sign_correction` — no `report_group_id` needed, so the rate limiter's own guard `if new.report_group_id is null ... then return new` skips the check entirely on this insert), then (2) `UPDATE` that same row, setting `pin_type = 'construction'`, a fresh `report_group_id`, and `expires_at` within the ceiling — all in one statement. This passes both CHECK constraints (they apply to `UPDATE` as well as `INSERT`, confirmed in AC-S8 above), but the rate-limit trigger never fires at all, because it's declared `before insert`, not `before update`. Repeating this N times produces N rate-limit-exempt fake closures. The file's own comment on the ceiling constraint explicitly reasons about exactly this class of gap ("A CHECK constraint (not a BEFORE INSERT trigger) is deliberate: it applies to UPDATE as well as INSERT... the constraint is the actual hard limit, not merely an insert-time gate") — that reasoning was correctly applied to the ceiling but not extended to the rate limiter, which remains insert-time-only.
  - Expected: the "required" rate-limit mechanism should bound the total rate of block-scoped reports an author can create by any means, not just by direct `INSERT`.
  - Repro: insert a `pin_type='block_note', source='crowd'` pin (own `author_id`, no `report_group_id`) — succeeds, untouched by the rate limiter. `UPDATE` that row: `SET pin_type='construction', report_group_id=<fresh uuid>, expires_at=now()+interval '89 days'` — succeeds; no rate-limit check ever runs on this statement. Repeat with new rows.
  - Graded 🟡 rather than 🔴 because Finding #1 alone already demonstrates the mechanism is fully broken via a simpler path — fixing #1 without also addressing this would leave a second, independent hole, so both need attention, but this one doesn't change the overall verdict on its own.
  - Recommended direction: either widen the trigger to also fire `before update of pin_type, report_group_id, expires_at on public.pins`, or otherwise ensure the count check runs on the UPDATE path that can produce a rate-limit-relevant row, not just the INSERT path.
  - Owner: `@backend-data`
