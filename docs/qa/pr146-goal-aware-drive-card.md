**Verdict:** ✅ ship it (MERGE) — one 🟡 design/documentation nit, not blocking; one verification gap disclosed below (not a code defect).

## Summary

This is a narrow, well-targeted fix: a new pure `DrivingContextService.goalAwareChipSeverity(...)` function recomputes each side's chip color from the exact same `engine.isFree(segment:from:until:ignoringMeteredPayment:)` call `ContentView.rebuildOverlays()`'s `parkUntilMode` branch uses, so the bottom card's chip color agrees with the map's binary green/red bucket whenever a goal or clock-set Park Until filter is active. Chip text is untouched, voice is untouched (named follow-up, not silently dropped), the diff is genuinely small (174/9 across 3 files + 1 new test file), and all 6 known Swift compile-failure classes are clear on this diff. CI is green: 2018/2018, 0 failures, confirmed directly from run 40261213063's logs including the exact 14 new test names. The one real design question — how a chip should color a side backed by more than one physical curb segment with mixed pass/fail results — is answered conservatively ("every segment must pass"), which is defensible for driver safety but is not quite what the PR's own code comment claims it mirrors, and it was not visually verified on-device by me (no Xcode/simctl available in this review sandbox).

## Findings

### 🔴 Blocking

None.

### 🟡 Significant

**#1: `goalAwareChipSeverity`'s "every segment must pass" rule can read red while most of the visually-painted side is green — and the code comment's analogy to `aggregateSideDetail` is not quite accurate.**

- Where: `DrivingContextService.goalAwareChipSeverity(...)` (`ios/WePark/WePark/Services/DrivingContextService.swift:721-739`), doc comment at `:709-720`.
- What: the function uses `sideSegments.allSatisfy { engine.isFree(...) }` — if a cardinal side is backed by two or more physical curb segments (confirmed as a real, documented data condition elsewhere in this codebase — `docs/w8.5b-destination-routing-spec.md:267` explicitly calls out "a block face that has multiple segments," and `docs/tile-geometry-investigation.md` discusses "sub-segments" meeting mid-block) and even ONE of them fails the goal/clock-set target, the WHOLE side's chip reads red. But `rebuildOverlays()` paints the map PER SEGMENT (`ContentView.swift:2537-2549`'s `for segment in tileLoader.segments { ... if engine.isFree(...) { freeCoords.append } else { notFreeCoords.append } }`), so the driver's actual map view in this scenario shows a mix of green and red polylines on that side — potentially mostly green with one short red stretch. The card's binary chip, in that case, disagrees with the dominant visual: red chip, mostly-green curb.
- Concrete scenario (matches the PR's own test `testMultipleSegmentsOnSide_onePasses_oneFails_overallRestricted`, which proves the mechanism but doesn't test the visual-disagreement angle): a long block-N side has a 40-foot segment with no restriction at all and a 10-foot segment with an ASP Mon/Thu sweep starting tomorrow. Under the Overnight goal, the map paints ~80% of that curb green and ~20% red. The card chip reads solid red, "Free until Tomorrow 8:00 AM" (text unchanged, still honest about the restriction) — but a driver glancing at the map and then the card could reasonably read the chip as "this whole side is bad," when 80% of it is fine.
- Is "every" the right call? On balance, yes, and I'd keep it: a false-green chip risks a ticket (the asymmetric cost that matters most for this app), a false-red chip only costs a glance at the map to find the actually-free stretch. The PWA/map already shows per-segment truth; the chip is a coarser, safety-biased summary layered on top. "Any passes" (optimistic) would be actively dangerous here. "Majority"/length-weighted would track the dominant visual better but adds real complexity (haversine length math, tie-breaking) for a card whose job is "can I trust this side," not "describe this side."
- The actual problem is narrower: the code comment at `:709-712` says this "mirrors `aggregateSideDetail`'s own conservative-min philosophy" — but `aggregateSideDetail`'s SIDE-LEVEL `.opportunity` classification is actually optimistic/ANY-wins (`if !qualifyingFree.isEmpty { ... opportunity is .free ... never .metered/.restricted ... free takes priority }`, `:649-672`). The "conservative-min" language in that function only describes a different sub-step — picking the soonest-expiring TEXT among already-qualifying free segments, not whether the side counts as free at all. So today, for a mixed side, the LEGACY chip (text/severity) would already resolve "free" if ANY segment qualifies as free-right-now, while this PR's NEW override resolves "restricted" if ANY segment fails the goal — two different aggregation philosophies (optimistic vs. pessimistic) now live side-by-side for the same underlying "collapse N segments into one chip" problem, on the same chip, depending on whether a filter is active. That's a real inconsistency a future maintainer could get confused by if they trust the comment's analogy.
- Precedent: this is the same shape of problem `docs/qa/pr133-dm2-goal-selector-ui.md` Finding #1 flagged for the map's own viewport-rung resolution ("ANY segment clears" defeating the "mostly red, no banner" guardrail) — the team has already had to correct an "ANY passes" choice once in this exact feature area because it produced a confusing mostly-one-color-but-labeled-otherwise UI. Worth having eyes on this one too, even though I think the choice here is the right one.
- Recommend: (a) fix the doc comment to stop citing `aggregateSideDetail`'s "conservative-min philosophy" as the precedent (it isn't — cite the safety-asymmetry reasoning instead, which IS a good reason); (b) add this exact mixed-segment scenario to Kevin's on-device smoke pass (not currently in the PR's 3-item checklist) so a human confirms the red-chip-over-mostly-green-curb case doesn't read as "broken" in practice; (c) no code change required before merge.
- Owner: `@ios-engineer` (doc-comment fix is trivial; the smoke-scenario addition is Kevin's call, not a code task).

Confirmed this is accurately described, not silently dropped: `CruiseVoicePolicy.swift` and `buildUtteranceText` are untouched by this diff. No action needed from me; recommend a tracked ticket per the PR's own suggestion.
- **`date:` parameter skew** — `ContentView`'s new call to `service.update(...)` at `:4933` doesn't pass `date:`, so it defaults to a freshly-computed `.nowET` at call time, while `rebuildOverlays()` elsewhere uses `lastEvaluatedAt` (a periodically-refreshed snapshot) for its own `now`. This is pre-existing (the `date:` parameter was already omitted at this call site before this PR; this PR only added the three new Park Until params), so it's not a regression this PR introduces, but it means the card's filter evaluation and the map's filter evaluation could theoretically straddle a restriction's start/end boundary by the gap between GPS ticks and the 60s overlay-rebuild tick. Pre-existing, not actionable here.
