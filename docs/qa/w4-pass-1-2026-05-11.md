## Findings

### Blocking

None.

### Significant

**#1: Safety label is not the first focusable VoiceOver element in the sheet**
- Where: `ios/WePark/WePark/Views/BlockDetailView.swift:73–111` — `headerRow` precedes `safetyLabelView` in source order
- What: VoiceOver navigates in source order by default. The `headerRow` contains three focusable elements before the safety label: the block title `Text`, the subtitle `Text`, and the `✕` close `Button`. VoiceOver reads all three before reaching the safety label. The safety label has `.accessibilityAddTraits(.isHeader)` applied, which marks it as a heading for rotor navigation but does not change sequential focus order. An `.isHeader` trait does not make it the first element VoiceOver lands on.
- Expected per spec §3.5 / palette §5.1 point 2: "This must be the first focusable accessibility element in the sheet."
- Repro: Launch VoiceOver, tap a polyline to open the sheet. VoiceOver first announces the block header title, then the subtitle, then "Close block details" (the button), then the safety label.
- Fix options: (a) Move `safetyLabelView` before `headerRow` in source order and position it visually using `ZStack` or `overlay`; (b) add `.accessibilitySortPriority(1)` to `safetyLabelView` and lower priority on the header elements; (c) mark the title and subtitle `Text` elements as `.accessibilityHidden(true)` (they're already conveyed by the close button's label and the a11y label on the tap-target Annotation).
- Owner: `@ios-engineer`

**#2: `dismissSheet()` via ✕ button may blank sheet content during the dismiss animation**
- Where: `ios/WePark/WePark/ContentView.swift:166–169` — `dismissSheet()` sets both `isSheetPresented = false` and `selectedSegmentID = nil` in the same function, which Swift batches into one render cycle
- What: When the user taps ✕, `dismissSheet()` is called. SwiftUI batches both state changes together: `isSheetPresented` flips to false (triggering the sheet dismiss animation) and `selectedSegmentID` becomes nil simultaneously. Since `selectedSegment` is a computed property that returns nil when `selectedSegmentID` is nil, the sheet content (`BlockDetailView`) loses its segment reference immediately, potentially blanking during the animation. The swipe-down path is fine: the system sets `isSheetPresented = false` via binding (triggering animation), then `onDismiss` fires after the animation completes, clearing `selectedSegmentID` when the sheet is already gone.
- Expected per spec: Sheet content should remain visible during the dismiss animation.
- Repro: Tap a polyline, open the sheet, tap the ✕ button. On slow devices, the sheet content may flash blank before the dismiss animation completes. Not reproducible in simulator at normal speed.
- Fix: Do not set `selectedSegmentID = nil` inside `dismissSheet()`. Instead, rely solely on the `onDismiss` closure to clear it (which already fires after animation). `dismissSheet()` should only set `isSheetPresented = false`.
- Owner: `@ios-engineer`

**#3: R1 stress test not run on real device (AC-W4.9)**
- Where: PR description — explicitly deferred; spec §3.6 escalation path applies
- What: No FPS measurement on a real iPhone at Manhattan zoom 14 with polylines and Annotation overlays rendering. Simulator does not predict real-device frame rates. The 40,664 total segments are viewport-gated (TileLoader only loads visible tiles), so full-load is not the concern; the concern is per-viewport render cost with two `ForEach` passes (one for polylines, one for Annotations).
- Expected per spec §3.6: ≥30fps sustained, ≥45fps target; measured FPS required in QA report.
- This is the spec's stated escalation precondition. Without it, we cannot confirm whether the Annotation layer requires zoom-threshold gating.
- Owner: Kevin / `@ios-engineer` — run on a real iPhone before W5 starts.

### Minor / nit

**#4: `dismissSheet()` called from both the onDismiss closure and directly — double clear**
- Where: `ContentView.swift:144–148` — `onDismiss` clears `selectedSegmentID`; `dismissSheet()` also clears it
- What: When the ✕ button calls `dismissSheet()`, that sets `isSheetPresented = false` which triggers the system to eventually call `onDismiss`. By then `selectedSegmentID` is already nil (from `dismissSheet()`). Double-setting nil is harmless but the intent is muddied. If finding #2 is fixed by removing the `selectedSegmentID = nil` from `dismissSheet()`, then `onDismiss` becomes the single clearing point — cleaner.
- Owner: `@ios-engineer` (address together with finding #2)

**#5: Spec calls for `.sheet(item:)` binding; implementation uses `.sheet(isPresented:)` with a separate Bool**
- Where: `ContentView.swift:144` vs `docs/w4-block-detail-spec.md` §3.2
- What: Spec §3.2 says "Use SwiftUI `.sheet(item:)` binding tied to the selected segment." The implementation uses `.sheet(isPresented: $isSheetPresented)` with a separate `isSheetPresented: Bool` and a computed `selectedSegment` property. The engineer's rationale (avoid content blanking during dismiss animation) is a valid concern, though the current implementation doesn't fully achieve it anyway (see finding #2). Behavior is functionally equivalent. Not a crash or incorrect output.
- Owner: `@ios-engineer` — low priority, address after finding #2 is resolved

**#6: `formatMinutes` duplicated in `RuleRow` vs `ParkingRulesEngine`**
- Where: `BlockDetailView.swift:299–309` — copy of private engine helper
- What: The view file contains a byte-identical copy of `ParkingRulesEngine.formatMinutes`. The comment says this is intentional to avoid a public API change. If the engine's format ever changes, the view copy becomes a fork risk. Both copies are currently identical; no divergence.
- Owner: `@ios-engineer` — consider extracting to a shared utility in a later PR

**#7: `Segment.midpoint` returns `coords[count/2]` — not a geometric midpoint for 2-coordinate segments**
- Where: `ios/WePark/WePark/Models/Segment.swift:72–77` — pre-existing from W3, used by W4's `Annotation` loop
- What: For a 2-coordinate segment (start + end), `coords.count / 2 = 1`, returning the endpoint, not the midpoint between the two. Geometrically the midpoint should interpolate between coords[0] and coords[1]. For segments with 3+ coordinates, `count/2` gives an approximately central vertex. The impact is that VoiceOver's Annotation activator is placed at the endpoint of very short 2-coordinate segments rather than their center. Not a W4 regression; pre-existing.
- Owner: `@ios-engineer` — optional improvement

### Out of scope (logged, not fixed)

**#8: Empty-rules segment returns "No data" in Swift but may return "Free" in PWA**

The PWA's `actionableSafetyLabel()` for a segment with no rules was not traced in the 10 parity samples. If the PWA returns `"Free"` for empty-rules segments, there is a parity divergence. Not verifiable without a real-device PWA session. Recommend including an empty-rules segment in the live parity snapshot PR (carry-over from W3 QA finding #3).

**#9: Annotation-based a11y approach is fragile to `MapPolyline` type inference fix**
- The engineer notes in the ContentView header that if Apple fixes the `.accessibilityLabel` type inference issue with `MapPolyline` in `@MapContentBuilder`, the `Annotation` a11y layer can be replaced with direct labels on the polylines. The current approach works but adds rendering overhead. Track for future cleanup when the SDK issue is resolved.

## What's working

- **The MapReader + haversine approach is strictly better than the spec's spec-suggested midpoint-only Annotation approach.** Taps anywhere along the polyline (not just near the midpoint) register correctly. The spec acknowledged this as an acceptable generalization.
- **All 10 AC-W4.4 parity samples trace correctly.** The engine port faithfully reproduces every case including the suspension-skip boundary (sample 10: Shavuoth → skip to Tue May 26). No discrepancies found across 7 tiles of actual segment data.
- **`selectedSegmentID` state management is conceptually clean.** Three dismiss paths each correctly clear state. The swipe-down path is especially clean: system animation runs uninterrupted, then `onDismiss` clears state.
- **Zoom-threshold gating is applied to BOTH the polyline ForEach and the Annotation ForEach.** This is the right call: at zoom levels where polylines are hidden, annotation buttons are also hidden, preventing invisible tap targets at city-wide zoom.
- **`dismissSheet()` is the single source of truth for programmatic dismiss.** The function name is clear, the two callers are explicit (✕ button and empty-map tap), and the system-dismiss path uses `onDismiss` cleanly.
- **No `Calendar.current` use anywhere in W4.** The `Date.nowET` extension is the only time source used in `BlockDetailView` (for `private let now: Date = .nowET`). The constraint is respected.
- **The `BlockDetailView` preview uses the test helper pattern** (JSON round-trip to construct `Segment`) rather than hard-coded mock data. This is the same approach as the engine tests, keeping the preview honest about real tile structure.
- **Accessibility labels on Annotation buttons match spec §3.5 exactly:** `"Parking on \(street), \(side). \(safetyLabelText). Tap for details."` and hint `"Opens the block details sheet."` The format is sensible and consistent.
