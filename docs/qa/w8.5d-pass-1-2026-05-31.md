## Findings

### Significant
**#1: Spec AC-18 claim about W7.5 Park Until hook is stale — but the code behavior is correct**
- Where: `docs/w8.5d-final-approach-spec.md` §1 (in-scope bullet), §3.5, and AC-18
- What: The spec says "The `pinDropped` publisher fires, the W7.5 'Park Until X' follow-up sheet fires naturally." The code does NOT do this, and correctly so — W7.5 was amended in pass-2 from a pin-drop-triggered flow to a standalone toolbar trigger. The `onReceive(parkPinService.pinDropped)` handler in `ContentView.swift` (line 549) only cancels old notifications and schedules new ones; it no longer presents the Park Until sheet.
- Expected (per spec): Park Until sheet fires automatically after "Park Here" confirm.
- Actual (code): After "Park Here" confirm, pin is saved, Drive Mode ends, user is left at the normal map. Park Until sheet only appears via the clock toolbar button.
- Impact: The code behavior is arguably BETTER than specified (no unwanted modal after arrival). The functional gap is that Kevin may EXPECT Park Until to auto-appear after Drive Mode arrival-confirm, but it won't. **Product decision, not a code bug.**
- Owner: `@tech-lead` to decide whether (a) update spec to reflect as-shipped W7.5 behavior, or (b) re-wire the arrival-confirm path to set `activeSheet = .parkUntil` after `endDriveMode()`.

### Minor / nit

- Where: `ios/WePark/WeParkTests/W85dTests.swift`, line 11 and line 31 baseline comment
- What: File inventory lists 12 (8 state-machine + 3 voice-gap + 1 threshold). Actual: 13, because `testFinalApproachState_justInsideApproachThreshold_isApproaching` (distance=499) was added beyond the spec list. Line 31 says "240/0 (228 + 12)" — actual is 241/0 (228 + 13).

Spec-consistent (AC-8 says strip is absent when state isn't `.approaching`). Low priority — drive-test will reveal if this feels jarring.
