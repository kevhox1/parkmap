## Findings

### Significant

**S-1: Route polyline Z-order degrades on tile data reload while Drive Mode active**

- Where: `MapViewRepresentable.swift` — `applyOverlayPayload()` vs. `syncRoutePolyline()`
- What: `applyOverlayPayload` removes and re-adds the 5 parking-state `TaggedMultiPolyline` groups plus the selected-block `SelectedPolyline`, but does NOT touch the `RoutePolyline`. `syncRoutePolyline` is called from `updateUIView` only when `route.id` changes (fast-path guard). When overlay payload generation bumps (e.g., tile data reloads), `applyOverlayPayload` re-adds all parking overlays and the selected-block overlay AFTER the existing `RoutePolyline` in the `.aboveRoads` MKMapView render stack. Result: parking state overlays and the selected-block highlight render on top of the route polyline, obscuring it.
- Expected per spec AC-W85b.11 and §4 Step D: route polyline renders above parking-state overlays and below selected-block highlight.
- Repro: Activate Drive Mode (polyline renders correctly). Trigger a tile reload by panning the map outside the current tile region and back — `rebuildOverlays` bumps `overlayPayload.generation` → `applyOverlayPayload` fires → parking overlays now render above the route polyline.
- Impact at W8.5b: Low severity in practice — W8.5b has no continuous driving, so no position-triggered tile reloads during a live route. However, the user manually panning the map (e.g., to explore their route) could trigger tile reloads and reproduce the visual defect. W8.5c will add continuous location updates which will make this reproducible on every drive.
- Fix hint: `syncRoutePolyline` should re-add the route polyline after any `applyOverlayPayload` call. One approach: after `applyOverlayPayload`, call `syncRoutePolyline` unconditionally (bypassing the fast-path `renderedRouteID == newID` guard). Alternatively: change the fast-path guard so it always re-inserts the overlay at the correct stack position, or use a higher `MKOverlayLevel` for the route polyline.
- Owner: `@ios-engineer`

### Minor

**M-1: `MKLocalSearch.start` has no timeout guard**

- Where: `DriveModeDestinationView.swift:411` — `search.start { response, error in DispatchQueue.main.async { ... } }`
- What: The spec §7 Risk 7 explicitly requires: "add a 10-second timeout guard" to prevent the "Start Drive" button being stuck in a loading/resolving state on a slow or offline connection. No `Task` with `.cancel()`, no `DispatchWorkItem` cancellation, and no timeout is implemented.
- Expected: If `MKLocalSearch.start` does not return within 10s, `isResolvingAddress` should be reset to `false` and an error message shown.
- Impact: On a slow or intermittently connected device, the user taps a suggestion and sees "Resolving address..." indefinitely. There's no way to recover without killing the app.
- Owner: `@ios-engineer` — add a `Task.sleep(for: .seconds(10))` race or `DispatchWorkItem` timeout against the search callback.

**M-2: View smoke test does not match spec §6 named test (error-path coverage gap)**

- Where: `W85bTests.swift:436-449` — `testDriveModeDestinationView_renders_withoutCrashing`
- What: Spec §6 requires `testDriveModeDestinationView_routeError_doesNotCrash` — "Construct `DriveModeDestinationView` with a mock `onRouteReady` that throws `.noRoutes`. Confirm the view renders an error message rather than crashing." The actual test constructs the view with `userLocation: nil` and asserts `host.view != nil`. This verifies the nil-user-location code path (AC-W85b.13 guard) but not the error-display code path when `RouteService.shared.fetchRoute` throws.
- Expected: A test that drives the error banner display (the `errorMessage` state populating the `errorBanner` view) via a mock route service injection.
- Impact: The `friendlyErrorMessage(for:)` function and `errorBanner` view are not unit-exercised. If any of those error-display paths regress, no test catches it.
- Practical note: `RouteService.shared` is a singleton without a protocol boundary in the current design, making error injection in a view test non-trivial. The test substitute is a reasonable pragmatic approximation. Flag for W8.5c when error paths may be exercised more heavily.
- Owner: `@ios-engineer`

### Nit

**N-1: `RecentDestinationsStore` lives in `DriveModeDestinationView.swift` — W8.5c lift advisory**

- Where: `DriveModeDestinationView.swift:44-90`
- What: Per engineer's documented unilateral decision (spec §7 process note #4), `RecentDestinationsStore` is defined inline in the view file rather than a separate `Services/RecentDestinationsStore.swift`. This is acceptable for W8.5b where access is view-local.
- Advisory: W8.5c's commentary engine and W8.5d's arrival flow may need to read or modify recent destinations (e.g., to mark a destination as arrived or to clear a destination from the session). If `RecentDestinationsStore` is imported from the view file, that import creates an architectural coupling between the commentary engine and the view layer. Recommended: lift to `Services/RecentDestinationsStore.swift` before W8.5c lands.
- Owner: `@ios-engineer` — schedule for W8.5c opening session, not a W8.5b blocker.

**N-2: `@MainActor` on `RouteService` class — M-1 advisory from W8.5a is resolved**

- Where: `W85bTests.swift:24` — `@MainActor final class W85bTests`; `DriveModeDestinationView.swift:384` — `Task { await fetchRouteAndReturn() }`
- What: The test class is correctly annotated `@MainActor` so all calls to `RouteService.pickBestParkingAwareRoute` (which inherits `@MainActor` from the class) are on the correct actor. The call site in `DriveModeDestinationView` uses `Task { await fetchRouteAndReturn() }` which correctly satisfies the main-actor constraint since SwiftUI views are implicitly `@MainActor`.
- Verdict: W8.5a's M-1 advisory ("`@MainActor` may force W8.5b callers onto the main thread") is **resolved** — the implementation chose the correct path (keep `@MainActor`, annotate test class, use structured concurrency at call sites).

## Engineer's Unilateral Decisions — Audit

1. **`pickBestParkingAwareRoute` as extension on `RouteService` (static method)** — correct call. Spec says "extension or new file" — extension is cleaner, keeps scoring adjacent to the route-fetching logic, and `static` makes it testable without a `RouteService` instance. No objection.
2. **`engine.safetyLabel(for:at:now).severity` for free/metered classification** — correct. The scoring uses `safetyLabel` severity AFTER the `dominantCategory` skip-set filter. This mirrors PWA `index.html:6312-6331` which calls `actionableSafetyLabel(seg)` (the Swift equivalent) for scoring. A segment with `dominantCategory = .free` that is currently under ASP suspension would return `.restricted` from `safetyLabel` and correctly score 0 (not +3). This is strictly more correct than a raw category check.
3. **`SearchCompleterDelegate` is `@Observable` (iOS 17+), not `ObservableObject`** — correct modern pattern. `@State` ownership in the view is the right pairing for `@Observable`. No regression risk.
4. **`RecentDestinationsStore` inline in `DriveModeDestinationView.swift`** — flagged as N-1 above. Acceptable for W8.5b; needs lifting before W8.5c.

## What's Working

- **Scoring port fidelity**: `pickBestParkingAwareRoute` is a faithful Swift port of `index.html:6298-6340`. All five skip categories, the stride formula, the 30m radius check (using `CLLocation.distance(from:)` instead of the PWA's manual equirectangular approximation — strictly more accurate), block-key dedup, weights, and duration penalty are correctly implemented. The 10 scoring tests exercise all meaningful branches and boundary conditions.
- **`@Observable` + `@State` bridge for `SearchCompleterDelegate`**: avoids the retain-cycle and rerender issues that would plague a plain struct or a `@StateObject`-owned `ObservableObject` class. The completer lives exactly as long as the view.
- **Error handling breadth**: `friendlyErrorMessage(for:)` covers all 5 `MapboxRouteError` cases with user-readable messages. The `catch error` fallback ensures no crash on unexpected throws.
- **Recent destinations deduplication**: `add()` removes an existing entry with the same name before inserting the new one at index 0. A re-navigation to "Grand Central" doesn't accumulate multiple identical entries.
- **Full-screen cover + sheet coexistence guard**: the `activeSheet == nil` guard in the Drive button correctly prevents the unsupported "two presentations simultaneously" scenario.
- **Destination pin tap absorption**: `MapViewRepresentable` absorbs taps within 30px of the destination pin to prevent spurious map-tap events. Correct forward-looking implementation for W8.5d.
- **21 tests in W8.5b** exceed the spec's target of +14, with meaningful additional coverage of dedup, MRU ordering, bonus skip-set categories, and two out-of-coverage bounding-box verifications.
