### Minor / Nit

**#1: T-W6.7 and T-W6.8 use `Thread.sleep` to wait for async cancel callback**

- Where: `NotificationSchedulerTests.swift`, `testTW67_CancelAll_RemovesRequest` and `testTW68_CancelAll_DifferentCarID_DoesNotRemoveOtherRequests`
- What: Both tests dispatch `cancelAll()` on `DispatchQueue.global()` and then `Thread.sleep(forTimeInterval: 0.1)` to wait for the `getPendingNotificationRequests` completion callback before asserting. `MockNotificationCenter.getPendingNotificationRequests` calls its completion handler synchronously, so the sleep is currently redundant — the assertions will always see the post-cancel state. However, if `MockNotificationCenter` is ever changed to call its handler asynchronously (or if the `cancelAll` implementation changes), the 100ms sleep may not be sufficient on a loaded CI machine.
- Expected: Use `XCTestExpectation` that is fulfilled inside the mock's remove callback, or restructure to call `cancelAll` synchronously and assert immediately.
- Severity: Minor — tests pass correctly today with synchronous mock. Not a production bug.
- Owner: `@ios-engineer`

**#2: T-W6.11 assertion verifies only the negative (fire day != 14) not the positive (correct fire day)**

- Where: `NotificationSchedulerTests.swift`, `testTW611_ASPSuspension_FireDatePastSuspension`
- What: The test asserts `XCTAssertFalse(fireDay == 14 && fireMonth == 5)` — confirming the fire date is not on the suspended date. It does not assert what the correct fire date IS (May 18 minus 1h lead = May 17 at some hour, or May 18 at 6am depending on Mon ASP start). The test comment itself contains a correction mid-stream ("Next non-suspended Thursday... Mon May 18 is also a valid ASP_MON_THU day — check if it's suspended... next is actually Mon May 18") without locking down the assertion to match.
- Expected: Add `XCTAssertEqual(comps.day, 17)` or `XCTAssertEqual(comps.day, 18)` (depending on the correct fire time) to verify the positive case. The engine parity tests already cover suspension skipping; this test would be stronger if it also verified the exact correct output.
- Severity: Minor — the negative assertion is sufficient to verify the scheduling respects suspension at all. The engine parity test `testHP11_ASPSuspendedSkipToNext` already verifies the hours computation.
- Owner: `@ios-engineer`

**#3: `notificationDeepLinkSubject` in AppDelegate is a strong PassthroughSubject — no `[weak self]` in `onReceive` handler**

- Where: `ContentView.swift`, `.onReceive(appDelegate.notificationDeepLinkSubject)` handler
- What: `onReceive` in SwiftUI does not create a retain cycle — SwiftUI's `onReceive` modifier manages the subscription lifetime and cancels when the view disappears. This is structurally correct. The handler is a closure over `@State` properties, which SwiftUI captures safely. No leak.
- Note: Not a bug. Logged for completeness since the AppDelegate's `DispatchQueue.main.async { [weak self] in ... }` uses `[weak self]` (appropriate for a class), and the pattern asymmetry may look odd in code review. SwiftUI's `onReceive` does not need `[weak self]` by design.
- Severity: Nit (observation only, not a finding)

## What's Working

The implementation is clean and well-structured. Specific call-outs:

- **Dependency injection for testability**: `NotificationScheduler(center: UNUserNotificationCenterProtocol)` internal init is exactly the right pattern. `scheduleForTest()` that bypasses the settings check is the correct solution to the test-entitlements problem — the production path remains untouched, and the test path validates all the business logic. Clean.

- **`previousCarID` capture pattern**: The spec §3.6 called out the sequencing subtlety explicitly. The engineer nailed it: `previousCarID = parkPinService.parkedCar?.id` is set in `confirmPinDrop()` before `save()` is called, and the `.task{}` initializer sets it on launch from the persisted car. This means pin-replace notifications are cancelled with the correct old ID even on the first replace after a cold start.

- **`getNotificationSettings` production guard**: The production `schedule()` path correctly guards on auth status before scheduling. This means the same `schedule()` call works correctly whether permission is granted, denied, or not yet determined — no special-casing at the call site. The `scheduleForTest()` bypass is minimal and clearly annotated.

- **`interactiveDismissDisabled(true)` placement**: Applied to `NotificationRationaleView` inside the sheet case (not to the sheet modifier itself), which is the correct SwiftUI 5.x pattern. Prevents accidental swipe-away that would skip the permission prompt.

- **`defer { completionHandler() }` in `didReceive:withCompletionHandler:`**: Correct guard against forgetting to call `completionHandler()` on early returns. This is the standard iOS delegate pattern and is correctly applied here.

- **`cancelAllThenSchedule` nested sequencing**: Cancel happens inside the `getPendingNotificationRequests` callback, with schedule called after cancel completes. This is correct — it prevents a window where the old notification is both pending and new one is being added.

- **Test coverage**: 15 new tests cover the full business logic matrix including the W7 mute stub, the suspension skip, the DST-safe trigger components, the identifier scheme, and the `userInfo` deep-link payload. The `testTriggerUsesEasternTime` test is particularly strong — it explicitly verifies ET vs UTC components, which is exactly the kind of test that catches timezone-related regressions.

- **W7/W7.5 integration stubs**: `notificationsMutedKey` constant reserved, guard is a provably inactive no-op. `parkUntil: Date? = nil` parameter on `schedule()`. Both are clearly annotated. W7 and W7.5 can activate their hooks without modifying `NotificationScheduler` at all. Well-designed.
