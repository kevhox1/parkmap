## Findings

### Blocking

**#1: `endDrivePillTopPadding` returns 0 on normal ASP-in-effect days — pill overlaps status bar and ASP banner**

- Where: `ContentView.swift:292-294`
- What: `private var endDrivePillTopPadding: CGFloat { bannerState == .aspInEffect ? 0 : 44 }`. When `bannerState == .aspInEffect` (the most common state — ASP is in effect on most days), the property returns `0`. The End Drive pill's VStack gets `.padding(.top, 0)`, placing it at the very top of the screen with no clearance for the status bar (~50pt) or the green ASP banner (~44pt).
- Expected per original AC-P.15/P.16: "End Drive pill does not overlap ASP banner when both active." The original (reverted #31) approach used a fixed `.padding(.top, 100)` that unconditionally cleared both status bar and banner. The PR description for #32 says the z-order fix makes the pill "sit below the ASP banner when a banner is visible." All three `SuspensionBannerState` cases render a visible banner — there is no state where the ASP banner is hidden.
- Root cause: The developer's doc-comment at line 291 reads "Zero when the banner is not showing (.aspInEffect)" which contradicts the `ASPBanner.swift` implementation. `.aspInEffect` renders a green "ASP in Effect Today" banner. The developer appears to have interpreted `.aspInEffect` as "no suspension = no banner" when in fact the banner always shows.
- Repro: On any normal weekday (ASP in effect — the majority of days), enter Drive Mode. The End Drive pill appears behind/overlapping the green ASP banner and possibly partly behind the status bar.
- Impact of today's smoke: Not caught by today's smoke because today is an ASP suspension day (`bannerState == .todaySuspended`), so `endDrivePillTopPadding` = 44 on today's smoke run. The bug only manifests on non-suspension days.
- Fix: Change the condition. All three states show the banner, so the pill always needs clearance. The simplest fix is to return a base value (e.g., `44` or the original `100`) unconditionally, or to add a fourth `.hidden` case to `SuspensionBannerState` and only return `0` for that case. The original approach of a fixed constant on the container VStack was simpler and more robust.
- Owner: `@ios-engineer`

### Significant

None.

### Minor

**#2: `usesMetricSystem` default is evaluated at view init time, not at use time**

- Where: `DriveModeBottomCard.swift:51`
- What: `var usesMetricSystem: Bool = (Locale.current.measurementSystem == .metric)` — this default is a stored property, evaluated once when the view is initialized, not at each render cycle.
- Expected: In practice this is fine — locale changes while the app is open are extremely rare and the view would be recreated on a scene transition anyway. But `formattedDistance(meters:)` calls this property at format time without checking `Locale.current`, meaning a locale change in the same app session would not update the display.
- Impact: Theoretical only. Not a regression from any prior behavior.

**#3: `endDrivePillZOrderTests` tests validate the wrong expected value**

- Where: `W85cPolishTests.swift:126-132`
- What: `testEndDrivePillOffset_aspInEffect_isZero()` asserts `offset == 0` for `.aspInEffect`. This test passes and documents the current (buggy) behavior as intended. If Finding #1 is fixed, this test should be inverted to assert offset > 0.
- Impact: The test will need to be updated when Finding #1 is fixed, or it will become a regression guard for the wrong behavior.

### Nit

**#4: Doc-comment at line 291 contradicts `ASPBanner.swift`**

- Where: `ContentView.swift:291`
- What: "Zero when the banner is not showing (.aspInEffect)" — but `.aspInEffect` shows the green banner.
- Impact: None independent of Finding #1 — fixing the logic fixes the doc-comment.
