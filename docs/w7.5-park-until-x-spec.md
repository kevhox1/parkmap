## 0. Open Questions for Kevin — Read Before Code Starts

Three decisions need Kevin's product instinct. Everything else in this spec is resolved and implementation-ready.

**OQ-W7.5-1: Should the "Parking until when?" sheet appear after EVERY pin drop, or only on first-time use?**
The spec recommends every pin drop (§3.A). Counter-argument: a power user who parks at the same block every weekday will find the prompt repetitive. Alternative: present the prompt always but add a "Don't ask again" option that writes a `UserDefaults` flag. Risk: "Don't ask again" is permanent until the user hunts it down in Settings; it undercuts discoverability for new sessions where the time matters. Kevin's call.

**OQ-W7.5-2: Should the filter map stay in binary mode (green/red) or show restricted blocks with their real state color at reduced opacity?**
The spec recommends binary (§3.B — matches PWA). Counter-argument: a user who wants to park "until 5pm" might still want to see whether a red block is NO_STANDING (dangerous, never park) vs. ASP (restricted now, but free in 20 min — maybe worth waiting). The PWA renders restricted blocks with their category color at 30% opacity for this reason (`index.html:4271-4278`). The iOS spec currently matches the PWA. If Kevin wants the iOS version to be fully binary (restricted blocks all same red/gray), say so and §3.B §5.G can be simplified.

**OQ-W7.5-3: Drive Mode integration — expose the Park Until filter inside Drive Mode (W8.5) or post-MVP?**
The filter is conceptually useful in Drive Mode ("I need to park somewhere until 6pm — route me there"). But Drive Mode (W8.5) has its own scope spec (`docs/drive-mode-scope-spec.md`). W7.5 does not touch Drive Mode. After W8 ships TestFlight, if Kevin wants the filter surfaced in Drive Mode, that becomes a W8.5 sub-feature. This spec does NOT block Drive Mode — flag here for Kevin to decide scope ordering before Drive Mode spec is written.

## 1. Problem and User Story

### The problem

The current map colors blocks by their parking state RIGHT NOW: red (restricted), orange (restriction within 6 hours), amber (metered active), green (free with no imminent restriction). This answers "can I park here now?" but does not answer the most common real-world question: "can I park here for the next 3 hours?"

A user arriving at 2pm who sees a green block may not notice that ASP starts at 3:30pm — within the `nearFutureWindow` cutoff, the block turns orange. But orange at 2pm means "restriction in the next 6 hours" — which doesn't tell them whether 3:30pm or 8pm is the restriction. The block detail sheet says "Free until Today 3:30 PM," but the user has to tap every candidate block to find that out.

The "Park Until X" filter inverts this: the user declares their constraint ("I need to leave by 5pm") and the map answers "which blocks are safe for that full window?" — one glance, no tapping required.

### User stories

**Story A — Quick-stop visitor.**
> I'm parking for a 2-hour dentist appointment starting at 1pm. I drop my pin, the "Parking until when?" sheet appears. I tap "3 PM" (the preset nearest my plan). The map remaps: blocks where no restriction falls between now and 3pm glow green. I pick the first green block, confirm. Done in 15 seconds. No tapping to read individual sign rules.

**Story B — Evening out.**
> It's 6pm Friday. I need a spot until midnight. I drop the pin, pick the "12:00 AM" preset. Most blocks in the Meatpacking District turn red (parking rules for weekend nights). A few stay green — I park there.

**Story C — Overnight.**
> I'm parking at 10pm Saturday. I need the spot until Sunday 9am (before ASP restores). I use the time picker to set 9:00 AM (tomorrow). The filter correctly walks Sunday's rules and marks blocks with Sunday-morning ASP as red.

### Why now

W7.5 is the last MVP stream before W8 (TestFlight). The PWA has proved this feature with real users (`renderParkUntilMode` at `index.html:4221`). The design questions that blocked it in W4.5 are now resolved — pin drop (W5), notification rationale (W6), and settings (W7) have established the architectural patterns W7.5 needs. Shipping it now means TestFlight beta users have the full value proposition from day one.

- **`Views/MapViewRepresentable.swift` — no structural change.** The existing 5 `MKMultiPolyline` overlay groups are reused. Park Until mode changes which segments fall into which group via `rebuildOverlays`, not via the renderer.
- **`Services/ToastService.swift` — unchanged.** The existing singleton (W7) is called with a new message when the filter is activated/cleared.
- **`Services/Constants.swift` — modified.** Add `parkUntilTargetKey: String` constant for `UserDefaults` persistence of the active filter time.
- **`WeParkTests/ParkUntilTests.swift` — new file.** ~20 new unit tests for `isFree(segment:from:until:)` (see §7).

### 2.2 Out of scope — do not build

- **Drive Mode integration.** Park Until filter in Drive Mode (route selection, heading-up overlay) is a W8.5 consideration. See OQ-W7.5-3 above.
- **Global "Park Until" filter toolbar button.** The filter is entered exclusively via the pin-drop flow (§3.A). A standalone map toolbar button (separate from pin drop) is a PRODUCT.md Tier 2 idea. Not needed for MVP — the pin-drop integration is sufficient discoverability.
- **Map-level stats overlay.** The PWA shows "42 blocks safe until 5pm | 19 blocks have restrictions" (`index.html:4282`). Skip for iOS MVP — the visual map coloring is the primary feedback; a count overlay adds clutter in a native context.
- **Multi-day windows.** The PWA handles multi-day windows by walking each calendar date (`checkParkUntilSafety` at `index.html:4285`). The iOS spec caps the target at 24 hours from now (see §4.A). Multi-day is a natural follow-on after TestFlight validates demand.
- **"Park Until" persistence across cold kill.** The filter target is cleared on app kill (see §5.F). Post-MVP, it could be persisted in UserDefaults.
- **Notification scheduling changes.** W6/W7 notification logic is not modified. The filter is a visual-only feature; notifications are still based on the parked car's pinned block, not the filter window.
- **ASP suspension banner changes.** The W7 banner logic is not modified.
- **Pre-filter notification for "your park-until time is approaching."** A "30 min until your target time" notification would be a natural extension. Post-MVP.
- **Metered-only segments.** The PWA treats metered-only conflicts as a special case (`index.html:4399-4402`). The iOS spec treats metered blocks identically to other restricted blocks — a metered block with paid hours inside `[from, until]` is not-free. If Kevin wants metered blocks to show differently, that is a follow-on.

## 3. User-Facing Design

### 3.A: Entry Point — Pin Drop Integration

**Trigger.** When `ParkPinService.pinDropped` fires (every `save()`, per `ParkPinService.swift:77`), `ContentView` presents `.parkUntil(car)` via `activeSheet`. The sheet appears immediately after the user confirms the pin, replacing the current "park confirmed" state.

The sheet always appears after pin drop — not only the first time. Rationale: the user's departure time changes every session; a persistent "parking until" default is rarely correct. A power user who parks at the same block daily can dismiss in one tap (swipe down on the drag indicator). See OQ-W7.5-1 if Kevin prefers a "don't ask again" option.

**Interaction with `ParkConfirmView`.** `ParkConfirmView` is presented first (`.parkConfirm` case). When the user confirms, `ContentView.confirmPinDrop` calls `parkPinService.save(car)`. The `pinDropped` subject fires. `ContentView` dismisses `.parkConfirm` and, in the same `onReceive` handler, sets `activeSheet = .parkUntil(car)`. This is one sheet replacing another — no concurrent sheet presentation.

**Skip path.** "Skip" button in `ParkUntilSheet` dismisses the sheet without setting `parkUntilTarget`. The map remains in normal 5-state mode. No toast is shown on skip.

**Clear path.** A "Clear filter" button appears in the map when `parkUntilMode == true`. Tapping it sets `parkUntilTarget = nil` and `parkUntilMode = false`, triggers a `rebuildOverlays`, and fires `ToastService.shared.show(message: "Park Until filter cleared")`.

### 3.B: Map Rendering in Park Until Mode

**Binary classification — matches PWA.** When `parkUntilMode == true`, segments are classified into two buckets:

| Bucket | Criteria | iOS overlay group | Color |
|---|---|---|---|
| Safe | `engine.isFree(segment:from:now until:target)` returns `true` | `freeComfortably` | Green (`ParkingColors.freeComfortably`) |
| Not safe | `isFree` returns `false` | `restrictedNow` | Red (`ParkingColors.restricted`) |

The existing 5 overlay groups are reused. In Park Until mode, segments land in only two of them (`freeComfortably` and `restrictedNow`). The `freeButRestrictionSoon`, `meteredActive`, and `unknown` groups receive zero coordinates — their overlays render nothing. This is a no-op for the renderer (zero-coordinate `MKMultiPolyline` is valid and renders nothing).

Note: "not safe" blocks include segments where `isFree` returns `false` regardless of the reason — ASP, NO_PARKING, METERED paid hours, NO_STANDING. They all render red. This is simpler than the PWA's approach of using category color at 30% opacity for unsafe blocks. If Kevin prefers the PWA's nuanced approach, see OQ-W7.5-2.

**The selected-block highlight overlay** (the 6th `MKMultiPolyline`) is unchanged in Park Until mode. The selected block retains its highlight color based on `isFree` result: green highlight if safe, red if not.

**The ASP suspension banner** (W7) is still visible in Park Until mode. If today's ASP is suspended and the user sets a target that spans an ASP window on a non-suspended date, those ASP windows still trigger `isFree == false` correctly (see §4.A for the engine logic).

**Zoom gating.** The `polylineHideSpanThreshold = 0.04` logic (viewport-polish PR #26) applies in Park Until mode — the recolored overlays hide at wide zoom just like normal mode overlays.

### 3.C: ParkUntilSheet — UI Spec

**Presentation.** Full-height sheet via `.presentationDetents([.medium])`. `.presentationDragIndicator(.visible)`. `.presentationBackground(.regularMaterial)`. `.presentationCornerRadius(20)`. Matches W7 Settings sheet presentation style.

**Header.** `"Parking until when?"` as the navigation title (`.navigationTitle`). No back button (sheet is presented, not pushed).

**Preset row.** A horizontal `ScrollView` of preset `Button` pills. Use `.buttonStyle(.bordered)` with `.tint(.green)` for the selected preset, `.tint(.secondary)` for unselected. Presets:

| Label | Value |
|---|---|
| 30 min | `now + 30 * 60` |
| 1 hr | `now + 1 * 3600` |
| 2 hr | `now + 2 * 3600` |
| 4 hr | `now + 4 * 3600` |
| Tonight | Midnight ET (start of next ET calendar day) |
| Tomorrow 9am | 9:00 AM ET on the next calendar day |

"Tonight" and "Tomorrow 9am" are computed using `Calendar.easternTime` — zero `Calendar.current` hits. "Tonight" is `Calendar.easternTime.startOfDay(for: .nowET).addingTimeInterval(24 * 3600)` (midnight between today and tomorrow ET). "Tomorrow 9am" is midnight plus 9 hours.

Tapping a preset:
1. Sets `selectedPreset` state (for tint highlight).
2. Computes `targetDate` from the preset formula.
3. Updates the custom `DatePicker` to show the same time (keeps UI consistent if user switches from preset to picker).

**Custom time picker.** Below the preset row, a `DatePicker("Custom time", selection: $customDate, in: now...maxDate, displayedComponents: [.hourAndMinute, .date])` in `.compact` display mode. `maxDate` is `now + 24 * 3600` (24h cap — see §4.A rationale). The date portion defaults to today ET; the time portion defaults to 1 hour from now. Changing the picker clears `selectedPreset`.

**Confirm button.** "Confirm" as a full-width `Button` with `.buttonStyle(.borderedProminent)`. Disabled if no target selected (no preset tapped and picker is at default). On tap:
1. Sets `ContentView.parkUntilTarget = targetDate`.
2. Sets `ContentView.parkUntilMode = true`.
3. Dismisses the sheet.
4. Triggers `rebuildOverlays`.
5. Calls `ToastService.shared.show(message: "Showing blocks free until \(formattedTime)")` where `formattedTime` uses `DateFormatter` with `timeZone = .easternTime` and format `"h:mm a"` (matches `nextRestrictionTimeLabel` format in `ParkingRulesEngine.swift:570`).

**Skip button.** Text-style button ("Skip for now") below the Confirm button. Dismisses the sheet without activating the filter.

**Accessibility.** Each preset button has `.accessibilityLabel("Park for \(label)")`. The DatePicker has `.accessibilityLabel("Custom departure time")`. Confirm button: `.accessibilityLabel("Confirm park until \(formattedTime)")`. Skip: `.accessibilityLabel("Skip, keep normal map view")`.

### 3.D: Filter Active Indicator

When `parkUntilMode == true`, a persistent banner or pill renders at the bottom of the map (inside the `ZStack`, pinned above the home indicator safe area). This signals to the user that the map is in a filtered state.

**Design.** A rounded-rectangle pill with a green dot, the text "Until [time]", and a "Clear" button. Example: `"Until 5:00 PM  [x]"`. Background: `.regularMaterial`. Use `.safeAreaInset(edge: .bottom)` on `MapViewRepresentable` (mirrors the top banner's `.safeAreaInset(edge: .top)` pattern). The pill pushes the map's bottom inset up rather than overlapping the map.

This pill does NOT appear in normal map mode. It replaces no existing UI element; it is additive.

**"Clear" action.** Tapping the `x` in the pill: sets `parkUntilMode = false`, `parkUntilTarget = nil`, triggers `rebuildOverlays`, fires `ToastService.shared.show(message: "Park Until filter cleared")`.

## 4. Architecture

### 4.A: New Engine Method — `isFree(segment:from:until:) -> Bool`

The existing `ParkingRulesEngine.currentState(for:at:)` answers "what is the state at a single point in time?" The Park Until feature needs "is this segment free for the entire interval [from, until]?" That is an interval query, not a point query.

**The PWA equivalent** is `checkParkUntilSafety` at `index.html:4285`. It walks each day in the window and checks whether any rule's time ranges overlap. The iOS implementation ports this logic directly.

**Proposed API:**

```swift
/// Returns true if the segment has no active parking restriction during [from, until].
/// "Active" means: the rule's schedule fires AND (for ASP) the date is not suspended.
/// Metered billing counts as a restriction — a metered block with paid hours inside the
/// window returns false.
///
/// Precondition: until > from. Undefined behavior if until <= from.
/// Practical cap: callers should enforce until - from <= 24 * 3600.
///
/// Port of checkParkUntilSafety at index.html:4285.
func isFree(segment: Segment, from: Date = .nowET, until: Date) -> Bool
```

**Why a new method, not extending `currentState(at:)`?** `currentState(for:at:)` returns a 5-case `CurrentState` enum that drives the normal map colors. Park Until needs a Bool at the interval level — a different question. Extending `currentState` with an optional `until:` parameter would require either a new enum case or a tuple return, adding complexity to a method that every overlay tick calls. Keeping the interval query separate preserves `currentState` unchanged and makes both callers easy to test independently.

**Algorithm:**

The method constructs a sequence of calendar dates between `from` and `until` using `Calendar.easternTime` (no `Calendar.current`). For each rule:

1. If `rule.category == .noStanding` or `.special` and `rule.anytime` is true: return false immediately (block is always restricted; it will never be free for any interval).
2. For each calendar date in the `[from, until]` window:
   - Compute the day's intersection with `[from, until]` (first day: starts at `from`; last day: ends at `until`; middle days: full day).
   - For ASP categories: check `category.isASPDay(dayOfWeek)` and `aspService.isSuspended(date)`. If the day is ASP-active and not suspended, check whether the rule's time ranges overlap the day's intersection window. If overlap: return false.
   - For NO_PARKING, TRUCK_LOADING, NO_STANDING, SPECIAL (non-anytime): check `rule.days` and `rule.timeRanges` for overlap with the day's intersection window. If overlap: return false.
   - For METERED: check `rule.days` and `rule.timeRanges` for overlap. If overlap: return false (metered billing counts as a restriction in Park Until mode, matching the PWA's `checkParkUntilSafety` behavior at `index.html:4334-4364`).

Return true if no rule produced a conflict.

**24-hour cap.** The iOS implementation caps `until - from` at 24 hours. The PWA walks multiple calendar days (`windowDates` at `index.html:4242-4247`), but multi-day is deferred (§2.2). The 24h cap means the window always spans at most two calendar dates (today + tomorrow), which keeps the inner loop simple and the per-rebuild compute budget bounded. The UI enforces the cap via the `DatePicker` `in:` range (§3.C).

**ASP suspension interaction.** When ASP is suspended on a date in `[from, until]`, that date's ASP windows are skipped (the same suspension-skip logic as `computeHoursUntilASP` at `ParkingRulesEngine.swift:471`). This is correct: a suspended ASP day does not create a restriction. If the entire window falls on suspended days, an ASP block correctly shows as free.

This means: if today's ASP is suspended and the user sets `until` to tonight, ASP blocks show green. This matches user expectation ("ASP is suspended today — I can park anywhere for ASP purposes").

**Interaction with W7 ASP banner.** The ASP banner shows the suspension state regardless of the filter. These are independent: the banner is a contextual fact about today; the filter is a segment-level computation. The engine's `aspService.isSuspended(date)` call inside `isFree` correctly handles suspended days without any banner involvement.

### 4.B: `ContentView.rebuildOverlays` — Park Until Mode Branch

`rebuildOverlays` is called from `ContentView` on the 60-second timer tick and on `overlayGeneration` changes. W7.5 adds a branch at the top of this function:

```swift
// W7.5: If Park Until mode is active, classify segments by interval-free status,
// not by current point-in-time state.
if parkUntilMode, let target = parkUntilTarget {
    let now = Date.nowET
    // Only apply filter if target is still in the future. If the target has passed
    // (user left the app overnight), silently clear the filter.
    guard target > now else {
        parkUntilMode = false
        parkUntilTarget = nil
        // Fall through to normal classification below.
        return rebuildOverlays()  // tail-call to normal path
    }
    // Partition segments into free / not-free using the interval query.
    var freeCoords: [[CLLocationCoordinate2D]] = []
    var notFreeCoords: [[CLLocationCoordinate2D]] = []
    for segment in tileLoader.segments {
        let coords = segment.coordinates  // already [CLLocationCoordinate2D]
        if engine.isFree(segment: segment, from: now, until: target) {
            freeCoords.append(coords)
        } else {
            notFreeCoords.append(coords)
        }
    }
    // Map to overlay groups: free → freeComfortably (green), not-free → restrictedNow (red).
    // freeButRestrictionSoon, meteredActive, unknown receive zero coords → render nothing.
    overlayGeneration += 1
    overlayPayload = MapViewRepresentable.OverlayPayload(
        freeComfortably:        freeCoords,
        freeButRestrictionSoon: [],
        meteredActive:          [],
        restrictedNow:          notFreeCoords,
        unknown:                [],
        selectedCoords:         selectedSegmentCoords,  // preserve highlight
        selectedState:          selectedSegmentState,
        generation:             overlayGeneration
    )
    return
}
// Normal path: existing 5-state classification follows here (unchanged).
```

The pseudocode above is illustrative; the exact variable names in the live `ContentView.swift` must be followed by `@ios-engineer`. The key constraints:
- Zero `Calendar.current` calls — `engine.isFree` uses `Calendar.easternTime` internally.
- The `selectedCoords` / `selectedState` for the highlight overlay are unchanged regardless of mode.
- The stale-target guard clears the filter automatically rather than leaving a post-midnight filter showing a stale coloring.

### 4.E: Filter Persistence

**Active session only — no UserDefaults persistence on first ship.**

`parkUntilTarget` and `parkUntilMode` are `@State` in `ContentView`. They do not survive app kill. Rationale: the most common case is that the target time has passed by the time the user relaunches; persisting a stale filter and then immediately clearing it on relaunch adds complexity for zero benefit. The `rebuildOverlays` stale-target guard (§4.B) handles the case where the user puts the app to background for hours and returns.

**On app foreground.** The `scenePhase == .active` handler already runs `bannerState = aspService.suspensionState(at: .nowET)`. Add to the same handler: check whether `parkUntilTarget` is past (`target < .nowET`) and clear the filter if so. This ensures a user who backgrounded past their target time sees the normal map when they reopen.

**No `parkUntilTargetKey` constant needed** (spec §2.1 listed it speculatively — removed because we do not persist to `UserDefaults` in v1). `@ios-engineer` should not add this constant.

## 5. Design Decisions — Resolved

### 5.A: UI Integration — Pin Drop, not Standalone Toolbar Button

**Decision: pin drop integration only, no standalone toolbar button.**

Rationale (confirming the HANDOFF tech-lead recommendation): the Park Until filter is most useful when the user is actively looking for a spot, which is exactly when they drop a pin. Surfacing the prompt immediately after pin confirmation catches the user at the moment of highest intent. A standalone toolbar button requires the user to discover it separately and remember to use it before — or separately from — parking. The PWA's approach (a dedicated filter mode toggled from a header control) made sense for a desktop-class UI with more screen real estate; on iPhone, the sheet-after-pin pattern is lower friction.

The "Clear filter" pill (§3.D) provides the only other entry point: it is the escape hatch to return to normal mode, not an entry point to set a new target. To change the target time, the user drops a new pin (or re-pins the same spot) and goes through the prompt again.

### 5.B: Replace vs. Layer — Binary (Replace) Mode

**Decision: Park Until mode REPLACES the 5-state coloring with binary green/red.**

The PWA (`index.html:4270-4278`) replaces the coloring: safe blocks show green, unsafe blocks show the category color at 30% opacity. The iOS spec simplifies further: unsafe blocks show red at normal opacity. Binary is cleaner for the primary use case (find a spot fast) and avoids the complexity of the 30% opacity calculation in the overlay payload.

The existing 5-state mode resumes immediately when the filter is cleared. No state is lost — `currentState(for:at:)` is never modified.

### 5.C: Time Picker UX — Presets First, DatePicker Second

**Decision: horizontal preset pill row as primary interaction, `DatePicker` in `.compact` style as secondary.**

Rationale: the vast majority of park sessions target a round time horizon (1 hour, 2 hours, tonight). Presets eliminate the need to manipulate the picker for common cases. The `.compact` DatePicker is available for unusual departures (e.g., "I need to leave at 4:45 PM"). The picker's `displayedComponents: [.hourAndMinute, .date]` allows cross-midnight targets without showing a full calendar.

SwiftUI `DatePicker` with `displayedComponents: .hourAndMinute` only does not support targets on a different day. Including `.date` as a component allows the user to pick tomorrow if needed (still within the 24h cap). The picker defaults to today's date so the most common case requires no date navigation.

### 5.D: Currently-Restricted Blocks — Red, Full Opacity

**Decision: blocks that are restricted right now (e.g., ASP active at 2pm) but where the user's target window still overlaps the restriction window are shown red.**

A block that is ASP-active right now (`currentState == .restrictedNow`) and where ASP continues until 9:30am — but the user's target is 3pm — is `isFree == false`. It renders red. This is correct: the user cannot park there now, and even if they could, there is a restriction during the window.

A block that is ASP-active right now but where the ASP window ends at 9:30am and the user's target is 1pm (no other restrictions) is also `isFree == false` because the current window is active at `from = now`. The user cannot park there now. Red is correct.

**Edge case: "currently red but free for my window if I wait 30 min."** The filter does not model "park later." It answers "can I park NOW and stay until X?" The `from` parameter is always `Date.nowET`. A block that is red now is a "not now" answer regardless of the target time.

### 5.E: Filter Persistence — No Cross-Session Persistence in v1

**Decision: filter does not survive app kill.**

See §4.E. In v1, `parkUntilTarget` is in-session only. The background-foreground stale-target guard handles the case where the user re-enters the app after the target time has passed without a kill.

Post-MVP: if TestFlight feedback reveals users frequently want to restore the filter after kill (e.g., they are spending an afternoon in the city and want the filter to persist across lunch), add `UserDefaults` persistence with the stale-target guard at load time.

### 5.F: Filter Cleared When User Drops a New Pin

**Decision: dropping a new pin re-presents `ParkUntilSheet` with a fresh prompt, clearing the previous filter.**

This is a natural consequence of the `onReceive(pinDropped)` handler always presenting `.parkUntil`. When the user confirms a new pin, the old filter target is implicitly stale. The new `ParkUntilSheet` prompt lets them set a new target. If they skip, `parkUntilMode` is set to `false` and `parkUntilTarget` is set to `nil`.

### 5.G: ASP Suspension Interaction — Suspension Is Respected

**Decision: `isFree` respects ASP suspension dates — a suspended date's ASP windows do not create a conflict.**

This is implemented inside `computeHoursUntilASP`-equivalent logic in `isFree`: the same `aspService.isSuspended(date)` guard that the existing engine uses in `computeHoursUntilASP` (line 471 of `ParkingRulesEngine.swift`) is applied per calendar date inside `isFree`. If ASP is suspended today and the user's window covers today's ASP window, that window is skipped. The block shows green.

This means: Park Until respects the same suspension calendar that the W7 ASP banner reads. The feature is internally consistent.

## 10. Out-of-Scope Follow-Ups

These were considered during spec authoring and explicitly deferred, with rationale.

**Drive Mode integration (OQ-W7.5-3).** W8.5 Drive Mode will need its own decision on whether to expose the Park Until filter (e.g., "I need a spot until 6pm — highlight reachable-in-5-min green blocks on the route"). That decision belongs in the Drive Mode scope spec, not here. `isFree(segment:from:until:)` is already the correct engine API for that use case — no changes needed to the engine method when Drive Mode spec is written.

**Multi-day windows.** The 24h cap is a conservative v1 choice. Users who park for multi-day trips (Thanksgiving, multi-day errands) are underserved. Post-TestFlight, the `isFree` implementation can be extended to walk multiple calendar dates (the PWA's `windowDates` pattern at `index.html:4242`) with no change to the API signature — just removing the 24h cap from the engine and the DatePicker range.

**"Park Until" time persistence.** If TestFlight feedback reveals users want to restore the filter after kill, add `UserDefaults` persistence. The `isFree` result would need a stale-target guard at load time (the same guard already present for the in-session foreground case).

**Standalone toolbar button / manual mode entry.** Kevin may discover that some users want to set the filter before dropping a pin (e.g., scan for spots before committing). A toolbar button or a map mode toggle would enable this. Deferred — pin-drop integration is the right first entry point; observe TestFlight usage before adding another.

**"Park Until" notification.** A notification 30 minutes before the user's target time ("Your parking window ends at 5:00 PM — 30 minutes to go!") would be a natural extension of W6 notifications. This would require the target time to be persisted alongside the parked car (a `ParkedCar.parkUntilTarget: Date?` field). Post-MVP — the 1-hour-before-restriction notification (W6) covers the safety case; the Park Until notification is a convenience enhancement.

**Stats overlay.** The PWA shows "42 blocks safe until 5pm | 19 blocks have restrictions" at the bottom of the screen in Park Until mode (`index.html:4282`). This is informational and does not affect parking decisions. Skipped for iOS MVP — the visual map coloring is sufficient. Can be added to the filter-active pill if TestFlight reveals users want the count.

**Metered-only nuance.** The PWA treats metered-only conflicts as a special sub-state (`meteredOnly: true` in `index.html:4400-4402`). The iOS spec treats metered blocks the same as other restricted blocks (red). If Kevin wants metered-only conflict blocks shown differently (e.g., amber instead of red, since metered is "not free but not a ticketing risk"), that is a follow-on change to `isFree`'s return type.

**W4.5 `nearFutureWindow` interaction.** The `isFree` interval query is independent of `nearFutureWindow`. A block that is "free comfortably" in normal mode (green, restriction > 6h away) may still return `isFree == false` if the restriction falls inside `[from, until]`. This is correct and intentional — Park Until is more precise than the ambient map color. No interaction with the W4.5 threshold constant.

## 12. As-Shipped Amendments (2026-05-18)

The original spec above describes the design before any smoke testing. Kevin's smoke pass-1 and pass-2 caught three UX issues that changed the shipped design. This section documents the deltas; the rest of the spec is preserved as a record of the design conversation.

### Pivot 1 — Standalone toolbar trigger (was: pin-drop trigger)

**Original spec §3.A:** "When `ParkPinService.pinDropped` fires (every `save()`), `ContentView` presents `.parkUntil(car)` via `activeSheet`. The sheet appears immediately after the user confirms the pin."

**Kevin's smoke pass-1 finding:** Pin-drop trigger creates a commit-before-discover workflow. User picks a block first, THEN learns whether their time constraint fits. The right pattern is filter-first: enter Park Until mode → see all matching blocks → choose where to park. Matches the PWA's `renderParkUntilMode` UX.

**As shipped (pass-2 commit 296ad76):**

- New `clock.fill` toolbar button in the top-right recenter button stack. Tap to open the sheet at any time.
- `ActiveSheet.parkUntil` case has no associated value (was `parkUntil(ParkedCar)`). Filter is car-agnostic.
- `Views/ParkUntilSheet.swift` no longer takes a `car` parameter.
- `.onReceive(parkPinService.pinDropped)` handler no longer sets `activeSheet = .parkUntil(...)`. The W6 notification logic in that handler is preserved unchanged.
- Filter no longer clears on pin drop. The user can enter Park Until mode → see green blocks → drop a pin on one → filter persists so they can verify the choice. Filter clears only via: X-on-pill, stale-target auto-clear (foreground re-entry after target passes), or pin-clear ("I left").

**OQ-W7.5-1 resolution superseded.** The "every pin drop" decision from the original spec is no longer relevant — the sheet no longer appears on pin drop at all.

### Pivot 2 — 7-day cap (was: 24-hour cap)

**Original spec §3.C / §4.A:** "`maxDate` is `now + 24 * 3600` (24h cap)." Justified by simplifying the inner loop.

**Kevin's smoke pass-2 finding:** Can't pick a date further out than tomorrow. Real use cases want 48-72h (weekend parking, Fri→Mon overnight). The 24h cap is artificially low.

**As shipped (pass-3 commit b0e37c1):**

- `maxDate` raised from `now + 24 * 3600` to `now + 7 * 24 * 3600`.
- The engine's `isFree(from:until:)` per-day walk already handles multi-day windows correctly (covered by existing tests).
- 7 days is a soft cap — the engine itself has no upper bound. DatePickers feel awkward past a week; if users want longer they can re-park.

### Pivot 3 — Relative-date-aware time format (was: bare "h:mm a")

**Original spec §3.E:** Format `"h:mm a"` (matches `nextRestrictionTimeLabel` format).

**Kevin's smoke pass-2 finding:** "Until 9:00 AM" is ambiguous when the target is tomorrow (or further). Easy to misread which day.

**As shipped (pass-3 commit 04d2061):**

`ParkUntilSheet.formatTime(_:)` is now relative-date-aware. Single source of truth for the confirm button label, the bottom pill, and the success toast.

| Day diff (ET calendar) | Output shape |
|---|---|
| 0 (today) | `9:00 AM` |
| 1 (tomorrow) | `Tomorrow 9:00 AM` |
| 2-6 | `Mon 9:00 AM` (weekday abbreviation) |
| 7+ | `May 25, 9:00 AM` |

Matches Apple's pattern in Maps and Reminders: omit date when redundant with "today," include explicitly otherwise.

### What was NOT changed

- **The engine `isFree(segment:from:until:)`** — unchanged from pass-1. The 20 unit tests in `ParkUntilTests.swift` pass without modification.
- **The 6 preset pills + DatePicker secondary** — unchanged.
- **Binary green/red recolor in `rebuildOverlays`** — unchanged (OQ-W7.5-2 "full red" still applies).
- **Stale-target guard on `.scenePhase = .active`** — unchanged.
- **Pin-clear ("I left") clears the filter** — preserved (still in `onClearPin`).
- **In-session-only persistence** (no UserDefaults) — unchanged.
- **All W6.1 / W7 / viewport-polish invariants** — preserved.

### Test count

96 (post-viewport-polish baseline) → 116 (with +20 W7.5 engine tests). No new tests added in pass-2 or pass-3 — the UX changes are SwiftUI view code, exercised by smoke.
