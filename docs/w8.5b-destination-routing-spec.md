## §0 — Open Questions for Kevin (read before code starts)

Eight product decisions need Kevin's input. The spec has been written with a recommended answer for each; Kevin's answers determine exact implementation shape. These are ordered by how early they block engineering.

**OQ-1: Drive Mode entry point in ContentView — where does the "Drive" button live?**
The toolbar already has: gear button (top-left), find-me + find-my-car + clock.fill (top-right). Adding a fourth button to the top-right stack is possible but crowding.
Options:
- A. Fourth button in the top-right stack using `map.fill` or `car.fill` SF Symbol.
- B. A persistent bottom pill/button (like the ParkUntilPill) in the bottom safe-area inset, separate from the map overlay cluster.
- C. A new "Drive somewhere" CTA inside the main body of the map (e.g., centered below the map when parked car is not set).
Recommendation: **Option A** — fourth top-right toolbar button, `location.fill.viewfinder` or `arrow.triangle.turn.up.right.diamond.fill` SF Symbol. Consistent with existing toolbar idiom; W8.5c+ will add more Drive Mode controls that integrate naturally with this placement.

**OQ-2: Destination search results layout — list inside a detent sheet, or floating panel?**
`MKLocalSearchCompleter` fires delegate callbacks as the user types; results need to display somewhere.
Options:
- A. A medium/large `.sheet` (or `.presentationDetents([.medium, .large])`) that contains the text field + results list below it. User types in the sheet, picks a result, sheet closes.
- B. A floating panel (e.g., `VStack` overlaying the map, pinned to top, showing an input bar + results list below). Dismisses when user picks a result or taps away.
- C. Full-screen cover presentation with a search field at top + results list below (familiar iOS Safari / Apple Maps search pattern).
Recommendation: **Option C** — full-screen cover. `MKLocalSearchCompleter`-backed search inside a full-screen view matches Apple Maps' own entry pattern and avoids the complexity of floating panel z-ordering with `MKMapView`. The map is not useful to see during destination entry. This also avoids the `ActiveSheet` single-sheet limitation — a fullscreen cover can coexist with a sheet.

**OQ-3: "Start Drive" confirmation step vs. instant start — does picking a destination immediately start Drive Mode, or is there a "Go" / "Start" button?**
The W8.5c-f Drive Mode stack (voice, heading-up rotation, wake lock) is a high-commitment mode. The user should be intentional about entering it.
Options:
- A. Picking a destination immediately starts Drive Mode (no intermediate step). Fastest path, fewest taps.
- B. After picking a destination, a "Start Drive" button appears (in the destination search view, or as a confirmation overlay). Tapping it enters Drive Mode.
Recommendation: **Option B** — "Start Drive" button. W8.5b ships destination input + route render without voice/rotation (W8.5c), so for W8.5b the distinction is moot mechanically — but the code path should be structured so the Drive Mode activation (voice, wake lock, heading-up) is explicit and easy for W8.5c to plug into. A "Start Drive" button call-site is the clean seam.

**OQ-4: Route alternatives rendering — show all alternatives, or only the scoring-chosen route?**
`RouteService.fetchRoute(from:to:alternatives:true)` returns up to 3 routes. After `pickBestParkingAwareRoute` picks one, should the others be visible?
Options:
- A. Render only the chosen route as a blue polyline. Clean, unambiguous. Matches PWA behavior (`renderRouteOnMap(drivingMapboxRoute)` at `index.html:6286` renders only the chosen route).
- B. Render all alternatives as dimmed gray polylines, chosen route as a bold blue polyline. Allows user to see tradeoffs.
- C. Show a chooser UI before starting Drive Mode so user can pick among the alternatives.
Recommendation: **Option A** — chosen route only. Matches PWA; keeps the map uncluttered. The scoring algorithm is transparent to the user — they trust WePark to pick the best route. Option B adds rendering complexity (need to track N overlays, clean them up on cancel) for marginal user value at this stage.

**OQ-5: Recent destinations list capacity — 5 or 10 entries? And how does the user clear them?**
Options:
- A. 5 entries. Long-press to delete individual entries. No bulk clear.
- B. 10 entries. Long-press to delete individual entries. No bulk clear.
- C. 5 entries. Individual delete via swipe-to-delete (standard iOS list pattern). Bulk clear in Settings.
Recommendation: **Option C** — 5 entries, swipe-to-delete on each. 5 is enough for real-world NYC usage (recurring destinations: home/work/gym + a few frequent spots). Swipe-to-delete is the iOS idiom that users expect on a list. Bulk clear in Settings (a "Clear recent destinations" row) defers to future Settings scope.

**OQ-6: Destination pin visual — which SF Symbol and color to distinguish from the parked-car pin?**
The parked-car pin (W5) uses a `mappin.circle.fill` annotation view with a blue tint. The destination pin needs to be visually distinct at a glance.
Options:
- A. `mappin.circle.fill` in red (iOS Maps default).
- B. `flag.fill` in green or teal — goal-state semantics.
- C. `star.circle.fill` or a custom destination icon in purple (iOS Maps destination color).
Recommendation: **Option A** — `mappin.circle.fill` in red. Apple Maps uses red for destinations; it is the most legible contrast to the existing blue car pin. Teal/green would create ambiguity with the green free-parking overlays.

**OQ-7: Out-of-coverage destinations — what if user picks an address outside the Manhattan tile grid (e.g., Hoboken, JFK, Yonkers)?**
`AppConstants.isInManhattanCoverage(_:)` (viewport-polish, PR #26) defines the bounding box: 40.700–40.882 N, -74.020 to -73.907 W.
Options:
- A. Allow routing but show a toast warning: "Limited parking data outside Manhattan." Route polyline draws; parking scoring still runs (with degraded coverage at route edges).
- B. Block: show an error sheet/toast if the destination falls outside the bounding box. User must pick a different destination.
Recommendation: **Option A** — allow with warning. Routing itself always works (Mapbox will route anywhere). The parking scoring gracefully returns no-data for out-of-coverage segments (they're simply absent from the loaded tile set). A toast warning informs the user without blocking a legitimate use case (e.g., routing from uptown Manhattan to Hoboken — the route passes through coverage and the parking data for the Manhattan portion still has value).

**OQ-8: Route polyline color and stroke weight — match PWA's `#0066ff` blue, or use system accent?**
Options:
- A. `#0066ff` (PWA-parity blue, `UIColor(red: 0, green: 0.4, blue: 1, alpha: 1)`).
- B. `.systemBlue` (`UIColor.systemBlue`) — adapts to dark mode automatically.
Recommendation: **Option B** — `systemBlue`. System color handles dark/light mode and high-contrast accessibility modes automatically. The PWA hex is close to `systemBlue` in light mode; the benefit of exact parity is low.

## §1 — Summary

W8.5b delivers the destination-input and route-rendering face of Drive Mode. The user taps a Drive entry button, types a destination (powered by `MKLocalSearchCompleter` — no third-party search API), selects a suggestion, taps "Start Drive," and sees a blue route polyline drawn on the existing `MKMapView` with a destination pin. The route shown is the parking-awareness-scored best route from up to 3 Mapbox alternatives — a direct Swift port of `pickBestParkingAwareRoute` (`index.html:6298–6340`). The user's last 5 destinations are persisted in `UserDefaults` and shown when the search field is empty. Recent destinations can be cleared individually via swipe-to-delete.

W8.5b has no voice, no heading-up rotation, no arrival flow — those are W8.5c and W8.5d. "The user can pick a destination and see a route drawn" is the complete acceptance statement.

## §4 — Implementation Plan

### Step A — Drive Mode entry point in ContentView (0.5 session)

Add a Drive Mode toolbar button to `ContentView`. This is purely additive to the existing top-right toolbar stack (gear + find-me + find-my-car + clock.fill pattern from W7.5).

New state to add in ContentView:
```swift
@State private var driveModeActive: Bool = false
@State private var activeRoute: DriveRoute? = nil
@State private var driveDestinationCoordinate: CLLocationCoordinate2D? = nil
@State private var showDriveModeDestination: Bool = false
```

Toolbar button taps `showDriveModeDestination = true` → presents `DriveModeDestinationView` as a full-screen cover (`.fullScreenCover(isPresented: $showDriveModeDestination)`). Note: full-screen cover does NOT conflict with `activeSheet`'s `.sheet(item:)` modifier — they are separate SwiftUI presentation modifiers and can coexist.

When `DriveModeDestinationView` completes with a chosen destination + route:
1. `driveDestinationCoordinate = destination`
2. `activeRoute = route`
3. `driveModeActive = true`
4. Dismiss `DriveModeDestinationView`

Add a "End Drive" / "X" overlay when `driveModeActive == true` that clears all three state vars and removes the route polyline + destination pin.

### Step B — `DriveModeDestinationView.swift` (1.0 session)

This is the largest discrete chunk of W8.5b. Build it as a standalone `View` file (not a sheet managed through `ActiveSheet`) presented via `.fullScreenCover`.

**Internal state:**
```swift
@State private var query: String = ""
@State private var completerResults: [MKLocalSearchCompletion] = []
@State private var selectedCompletion: MKLocalSearchCompletion? = nil
@State private var resolvedCoordinate: CLLocationCoordinate2D? = nil
@State private var resolvedName: String? = nil
@State private var isLoadingRoute: Bool = false
@State private var routeError: String? = nil
@StateObject private var completerDelegate = SearchCompleterDelegate()
```

**`MKLocalSearchCompleter` wiring:**
`MKLocalSearchCompleter` is not natively `@Observable` — it requires a delegate. Pattern: a small `SearchCompleterDelegate: NSObject, MKLocalSearchCompleterDelegate` that is either a `@StateObject`-owned `ObservableObject` or an actor. The delegate updates `completerResults` on the main actor. The `completer.queryFragment` is set inside `.onChange(of: query)`.

Region hint: set `completer.region` to the current `ContentView` region (passed in as a let parameter) so suggestions are NYC-biased from the first keystroke.

**Layout:**
```
NavigationStack or plain VStack:
  - TextField("Where to?", text: $query)  ← first responder on appear
  - if query.isEmpty:
      - Section("Recent") { ForEach(recentDestinations) }
  - else:
      - Section("Suggestions") { ForEach(completerResults) }
  - if resolvedCoordinate != nil:
      - Button("Start Drive") { fetchRouteAndReturn() }
  - Button("Cancel") { dismiss() }
```

**Completion → coordinate resolution:**
Tapping a suggestion calls `MKLocalSearch(request: MKLocalSearch.Request(completion: completion)).start { response, error in ... }` to resolve the suggestion to a `CLLocationCoordinate2D`. This is the same pattern Apple Maps uses internally. On success, `resolvedCoordinate` + `resolvedName` are set and the "Start Drive" button becomes visible.

**"Start Drive" action (`fetchRouteAndReturn`):**
1. Guard: `resolvedCoordinate` not nil; user location available from `locationService.userLocation`.
2. If user location is nil: show error "Location unavailable. Enable location access in Settings." No route fetch.
3. If user location is available: `isLoadingRoute = true`.
4. Call `await RouteService.shared.fetchRoute(from: userLocation, to: resolvedCoordinate, alternatives: true)`.
5. Call `RouteService.pickBestParkingAwareRoute(_ routes, segments: tileLoader.segments)`.
6. Check `AppConstants.isInManhattanCoverage(resolvedCoordinate)` — if false, queue a warning toast to fire after dismissal (see Step D).
7. Save destination to recent list (Step E).
8. Call `onRouteReady(DriveRoute, CLLocationCoordinate2D)` closure (passed in from ContentView).
9. Dismiss.

**Error handling:** If `fetchRoute` throws `.missingToken`, `.network`, `.http`, `.noRoutes`, set `routeError` string and display it as a inline banner (not a sheet) inside the view. User can retry or cancel. No crash path.

**Inputs from ContentView (passed as let properties or closures):**
```swift
let currentRegion: MKCoordinateRegion           // for completer region hint
let segments: [Segment]                         // for scoring
let userLocation: CLLocationCoordinate2D?       // origin for route fetch
let onRouteReady: (DriveRoute, CLLocationCoordinate2D) -> Void
```

### Step C — `pickBestParkingAwareRoute` in RouteService (0.5 session)

Port of `index.html:6298–6340` (~40 lines). Add as an extension on `RouteService` or as a `static` method — `static` is preferable so it is testable without constructing a full `RouteService` instance.

**Port notes:**

The PWA iterates `segmentLayers` (the in-memory segment array) and checks each segment's `dominantCategory` against a skip set of non-parking categories, then tests whether the segment midpoint is within 30m of any sampled route geometry point.

Swift equivalent:

```swift
static func pickBestParkingAwareRoute(
    _ routes: [DriveRoute],
    segments: [Segment],
    engine: ParkingRulesEngine,
    now: Date = .nowET
) -> DriveRoute? {
    // ...
}
```

Key porting decisions:

1. **Skip set:** PWA skips `NO_STANDING`, `NO_PARKING`, `SPECIAL`, `TRUCK_LOADING`, `UNKNOWN`. Map to `Category` enum values: `.noStanding`, `.noParking`, `.special`, `.truckLoading`. `unknown` in Swift is the absence of a dominant category or an empty-rules segment. The scoring function should skip segments where `engine.safetyLabel(for:at:now).severity == .restricted` OR `dominantCategory` is in the skip set — this mirrors the PWA's intent more precisely than a raw category check, since the label engine already handles ASP state.

2. **Stride / sample points:** PWA uses `Math.max(1, Math.floor(coords.length / 60))` — sample ~60 points from the route geometry. Use the same stride formula. Route geometry `[CLLocationCoordinate2D]` from `DriveRoute.geometry`.

3. **30m radius test:** PWA uses equirectangular approximation: `dx = (sp[0] - segMid[1]) * 111320 * cos(segMid[0] * π/180)`, `dy = (sp[1] - segMid[0]) * 111320`. Use `CLLocation(latitude:longitude:).distance(from:)` instead — cleaner in Swift and accurate for 30m threshold. Note: segment midpoint is `seg.line[seg.line.count / 2]` which is `[lat, lng]` order (per W2 — coordinate order is `[lat, lng]` in tile data, confirmed by HANDOFF.md W2 row).

4. **Block dedup:** PWA uses `blockKey = seg.street + '|' + seg.from + '|' + seg.to`. Use `"\(seg.street ?? "")|\(seg.from ?? "")|\(seg.to ?? "")"`. The same `blockKey` dedup prevents double-counting a block face that has multiple segments.

5. **Scoring weights:** PWA: `free → +3`, `metered → +1`, duration penalty `route.duration / 600` (seconds → 1 point per 10-minute penalty). Preserve these weights exactly — do not tune in this PR.

6. **Fallback:** If `routes` is empty → return `nil`. If `routes.count == 1` → return `routes[0]` without scoring. If scoring throws / all routes score equally → return `routes[0]` (Mapbox primary).

7. **`@MainActor` note:** `RouteService` is `@MainActor`. `pickBestParkingAwareRoute` does no async work — it is a pure CPU-bound scoring pass over in-memory arrays. Keeping it `@MainActor` is consistent with the class annotation. The input arrays (`routes`, `segments`) are already on the main actor. If the scoring loop is slow for very large segment arrays (unlikely — ~39k segments, ~60 sample points, early-exit at 30m match), the engineer can measure; optimization is out of scope here.

### Step D — Route polyline + destination pin in MapViewRepresentable (0.5 session)

**New inputs to `MapViewRepresentable`:**

```swift
let activeRoute: DriveRoute?
let destinationCoordinate: CLLocationCoordinate2D?
```

**Route polyline:**

Add a 7th overlay tag: `case routePolyline = 6`. When `activeRoute` changes (detected via `updateUIView`), remove the old route polyline overlay (if any) and add a new `MKPolyline(coordinates:count:)` from `activeRoute.geometry`. Tag it as `.routePolyline`.

In `mapView(_:rendererFor:)`, add a case for the route polyline tag: `MKPolylineRenderer` with `strokeColor = UIColor.systemBlue`, `lineWidth = 5`, `lineCap = .round`, `lineJoin = .round`. Z-order: route polyline should render above the parking state overlays (below the selected-block highlight). Achieve this by inserting the route polyline overlay at the correct index in `mapView.overlays` — `MKMapView` renders overlays in insertion order (later = on top). Insert the route polyline after the 5 state groups but before the selected-block overlay.

When Drive Mode is exited (`activeRoute` becomes `nil`), remove the route polyline overlay.

**Destination pin:**

Subclass pattern (matching the existing `CarPinAnnotation` from W5):

```swift
private final class DestinationPinAnnotation: MKPointAnnotation {}
```

When `destinationCoordinate` changes:
- Remove existing `DestinationPinAnnotation` from `mapView`.
- If non-nil: create a new `DestinationPinAnnotation` at the coordinate, set `title = resolvedName`.
- Add to `mapView`.

In `mapView(_:viewFor:)`:
```swift
if annotation is DestinationPinAnnotation {
    let view = mapView.dequeueReusableAnnotationView(withIdentifier: "dest")
        as? MKMarkerAnnotationView ?? MKMarkerAnnotationView(annotation: annotation, reuseIdentifier: "dest")
    view.markerTintColor = .systemRed
    view.glyphImage = UIImage(systemName: "mappin")
    return view
}
```

This is visually distinct from `CarPinAnnotation` (which renders in blue).

Tap handling: destination pin taps do NOT open a sheet in W8.5b (deferred — no arrival flow yet). If the tap hits the destination annotation, absorb the tap without triggering `onTap` (same pattern as `CarPinAnnotation` tap disambiguation in W5).

### Step E — Recent destinations persistence (0.5 session)

New `Codable` struct (place in `DriveModeDestinationView.swift` or a small dedicated file):

`UserDefaults` key: `Constants.recentDestinationsKey`.

Swipe-to-delete: use `.onDelete(perform:)` on the `ForEach` in the recents list. The delete closure removes the entry and re-persists.

**New constant in `Constants.swift`:**
```swift
static let recentDestinationsKey = "wepark_recent_destinations"
```

### Step F — Out-of-coverage warning (0.25 session)

In `DriveModeDestinationView.fetchRouteAndReturn()`, after resolving the route:

```swift
if !AppConstants.isInManhattanCoverage(resolvedCoordinate) {
    // Queue toast to fire after dismissal (ToastService.shared.show is @MainActor)
    DispatchQueue.main.asyncAfter(deadline: .now() + 0.3) {
        ToastService.shared.show(message: "Limited parking data outside Manhattan")
    }
}
```

The 0.3s delay ensures the toast appears after the full-screen cover dismissal animation completes (sheet + map are visible before the toast).

### Step G — "End Drive" UI in ContentView (0.25 session)

When `driveModeActive == true`, show an "End Drive" button overlay (e.g., a `.safeAreaInset(edge: .bottom)` pill or a top-left overlay button). Tapping it:

```swift
activeRoute = nil
driveDestinationCoordinate = nil
```

`MapViewRepresentable` reacts to `activeRoute = nil` and `destinationCoordinate = nil` by removing the route polyline + destination pin overlays.

Drive Mode state does NOT need to survive app kill at W8.5b — session state only. W8.5c will own the full Drive Mode session lifecycle.

## §5 — Acceptance Criteria

These extend and refine the AC-DM.4–AC-DM.6 criteria from `docs/drive-mode-scope-spec.md` §10. The QA agent will verify each as a smoke-testable or unit-testable checklist item.

**Entry and exit**

- [ ] **AC-W85b.1** A "Drive" toolbar button is present on the main map screen. Tapping it presents the `DriveModeDestinationView`. A "Cancel" / "X" control dismisses the view and returns to the normal map without entering Drive Mode.
- [ ] **AC-W85b.2** The `DriveModeDestinationView` text field becomes first responder automatically on presentation (keyboard appears without an extra tap).
- [ ] **AC-W85b.3** Tapping "End Drive" (or an equivalent dismiss control visible during active Drive Mode) clears `driveModeActive`, removes the route polyline, and removes the destination pin from the map. The map returns to its pre-Drive-Mode overlay state.

**Destination search**

- [ ] **AC-W85b.4** Typing a partial NYC address (e.g., "Spring St") in the text field triggers `MKLocalSearchCompleter` and displays at least one suggestion within 2 seconds on a live network connection.
- [ ] **AC-W85b.5** Selecting a suggestion resolves it to a `CLLocationCoordinate2D` and reveals a "Start Drive" button. The text field shows the selected address text. The results list is replaced by the selected state.
- [ ] **AC-W85b.6** The keyboard is dismissed when a suggestion is selected.
- [ ] **AC-W85b.7** When the text field is empty, the recent destinations list appears (if any exist). When the field has text, suggestions replace the recents list.

## §7 — Risks and Known Gotchas

**1. `MKLocalSearchCompleter` is not `@Observable` — delegate bridge required.**
`MKLocalSearchCompleter` is an `NSObject`-based UIKit type. Its results arrive via `MKLocalSearchCompleterDelegate`. The engineer must bridge this into SwiftUI state via an `NSObject` wrapper class that is owned by `@StateObject`. Do NOT put `MKLocalSearchCompleter` directly inside a SwiftUI `View` struct — it is a reference type and will be re-created on every render. Recommended pattern:

```swift
@Observable
final class SearchCompleterDelegate: NSObject, MKLocalSearchCompleterDelegate {
    var results: [MKLocalSearchCompletion] = []
    let completer = MKLocalSearchCompleter()
    override init() {
        super.init()
        completer.delegate = self
        completer.resultTypes = [.address, .pointOfInterest]
    }
    func completerDidUpdateResults(_ completer: MKLocalSearchCompleter) {
        results = completer.results
    }
    func completer(_ completer: MKLocalSearchCompleter, didFailWithError error: Error) {
        results = []
    }
}
```

Set `completer.queryFragment` from the `query` binding in `.onChange(of: query)`.

**2. Full-screen cover + `ActiveSheet` coexistence.**
SwiftUI's `.fullScreenCover` and `.sheet(item:)` ARE supported on the same host view — they are separate modifiers. However, presenting both simultaneously is undefined behavior. Guard: only present `DriveModeDestinationView` when `activeSheet == nil`. Add a `guard activeSheet == nil else { return }` check in the Drive Mode entry button action.

**3. `MapViewRepresentable` overlay insertion order.**
`MKMapView.addOverlay(_:level:)` with `.aboveRoads` or `.aboveLabels` does not control ordering among overlays at the same level — they render in insertion order. The route polyline must be inserted after the 5 state `MKMultiPolyline` groups but before the selected-block highlight. The current code in `MapViewRepresentable` uses `mapView.addOverlay` without `level:`. The engineer should verify overlay insertion order matches the intended Z-order by inspecting `mapView.overlays` in a debug build before submitting.

**4. `@MainActor` on `RouteService.pickBestParkingAwareRoute`.**
`RouteService` is `@MainActor` (per W8.5a). The scoring loop iterates up to ~39k segments × 60 sample points — worst case ~2.3M haversine calls. In practice most segments are outside 30m and the `CLLocation.distance(from:)` check will short-circuit for the vast majority. However, if this runs synchronously on the main actor for a noticeable duration (>16ms on screen), it will cause dropped frames. The engineer should profile in the Instruments Time Profiler for a real Manhattan route during W8.5b QA. If it exceeds 16ms, move scoring to a background actor and `await` it. This is a likely non-issue at ~39k segments (the PWA runs the equivalent loop in JS without observable lag) but should be verified.

**5. `CLLocation.distance(from:)` vs. equirectangular approximation.**
The PWA uses a fast equirectangular approximation for the 30m threshold check. `CLLocation.distance(from:)` uses Vincenty's formula (accurate to 0.01mm). For 30m thresholds in Manhattan, the difference is negligible (<0.1mm error). `CLLocation.distance(from:)` is the correct iOS idiom and avoids replicating the trig. Use it.

**6. Segment midpoint coordinate order.**
Per HANDOFF.md W2 row and tile data confirmation: segment `line` arrays are `[lat, lng]` order, not GeoJSON `[lng, lat]`. The PWA scoring code at `index.html:6318` accesses `segMid[0]` as latitude and `segMid[1]` as longitude (consistent with `[lat, lng]`). In Swift, `Segment.line: [[Double]]` — the midpoint is `CLLocationCoordinate2D(latitude: line[mid][0], longitude: line[mid][1])`. Do NOT accidentally swap these — the bug would cause all segments to score 0 (midpoints would be in the ocean) without a crash.

**7. `MKLocalSearch` resolution adds a network hop per suggestion tap.**
Each tap on a completer suggestion fires `MKLocalSearch.start` to resolve to a coordinate. This is a live network call. If the user is offline or on a slow connection, resolution will time out. Handle the `.localSearch.start` error path with an inline error message ("Couldn't resolve address — check connection"). Do not leave the "Start Drive" button in a loading state indefinitely — add a 10-second timeout guard.

**8. Recent destinations `CLLocationCoordinate2D` is not `Codable`.**
`CLLocationCoordinate2D` does not conform to `Codable`. Store `latitude: Double` + `longitude: Double` separately in the `RecentDestination` struct and reconstruct via a computed `var coordinate`. This is already noted in §4 Step E — the engineer should not attempt `JSONEncoder().encode(coordinate)` directly.

**9. Info.plist — no new build-setting keys in W8.5b.**
W8.5b does not add any new build settings or Info.plist keys (the Mapbox token wiring is already complete from W8.5a). No PlistBuddy smoke check is required for this PR. If the engineer adds any new Info.plist key (e.g., `NSLocationWhenInUseUsageDescription` — verify it already exists from W5.1), add the PlistBuddy check to the PR checklist: `PlistBuddy -c "Print :YOUR_KEY" <built>.app/Info.plist`.
